# SECURITY.md

Модель безпеки, довіри та порядок повідомлення про вразливості для BRAVO
(архівація, обслуговування та контроль резервних копій BRAVO/LIMS).

Цей документ описує **фактичний поточний стан** репозиторію, а не
запланований чи бажаний. Пункти, які ще не реалізовані, позначені явно й
відповідають нумерації (P0/P1/P2) зовнішнього плану аудиту безпеки, за
яким вони відстежуються поза цим репозиторієм.

## 1. Підтримувані версії

### Продукт

`VERSION.json` — єдине джерело правди для версії пакета. Актуальна версія
задокументована в [CHANGELOG.md](CHANGELOG.md); підтримується лише
найновіший `packageVersion` на гілці `master` (`releaseChannel: "stable"`).
Старіші версії не отримують окремих security-патчів — оновлення означає
атомарну заміну всього комплекту (див. розділ 10 [README.md](README.md)).

### Операційна система та PowerShell

Формальна модель трьох рівнів (`Get-BRAVOOSSupportTier`,
`modules\BRAVO.Compatibility`):

| Рівень | Системи |
|---|---|
| **Supported** | Windows Server 2019+, Windows 10/11, Windows PowerShell 5.1+ |
| **Legacy best-effort** | Windows Server 2012 R2, Windows Server 2016, Windows 8/8.1 (без гарантій) |
| **Unsupported** | Windows 7, Windows Server 2008 R2, PowerShell 3.x і старіше |

На `Unsupported` production-запуск блокується (код завершення `30`) без
явного `BRAVO_ALLOW_UNSUPPORTED_OS=1`. Деталі — розділ 1 README.md.

## 2. Порядок повідомлення про вразливості

**Канал.** Репозиторій `ekucher/ARCHIV_LIMS_MONOLITH` приватний, тому
доступ до Issues мають лише запрошені співавтори — повідомлення про
вразливість подавайте Issue з міткою `security` або напряму власнику
репозиторію (`@ekucher`). Якщо репозиторій колись стане публічним,
основним каналом має стати GitHub Security Advisory (Security →
Advisories → *Report a vulnerability*), а не Issue.

**Що вказати.** Версію (`VERSION.json.packageVersion` і `buildId`),
гілку й `sourceCommit`, кроки відтворення, потенційний вплив.

**Час реакції** (робочі дні, орієнтир для приватного репозиторію з
одним супроводжувачем):

| Етап | Строк |
|---|---|
| Підтвердження отримання | 2 робочі дні |
| Первинна оцінка (severity, чи підтверджено) | 5 робочих днів |
| Виправлення критичної вразливості | 7–14 календарних днів |
| Розкриття | лише після виправлення або за погодженою датою |

Якщо вразливість уже експлуатується, позначте це в заголовку — тоді
строки вище не діють, реакція негайна.

## 3. Модель секретів

Секрети (SFTP login/password, SMB login/password, пароль архівів 7-Zip,
Slack/Discord webhook URL, назва та код установи) зберігаються **лише** у
Windows Credential Manager — окремо для поточного адміністратора
(ручні запуски) і для `NT AUTHORITY\SYSTEM` (заплановані завдання),
`-StoreFor Both` при `BRAVO_CREDENTIALS_SETUP.ps1`/`BRAVO_SETUP.ps1`.
`BRAVO.config` містить лише fallback-значення назви установи, коду й
префікса архівів для першого запуску — реальні секрети в конфігураційний
файл ніколи не записуються (розділ 4 README.md).

Захист під час виконання:

- пароль 7-Zip передається утиліті лише через redirected standard input,
  не в аргументи процесу (self-test `Secrets/SevenZipPasswordUsesStdin`
  контролює регресію);
- `Protect-BRAVOLogSecret` (`modules\BRAVO.Logging`) маскує SFTP URL із
  паролем, паролі 7-Zip (обидві форми, `-password=` і `-p`), Slack/Discord
  webhook-токени — у всіх трьох runtime (Archive/Health/Maintenance) через
  єдину точку логування (`Write-Log`/`Write-BRAVOLog`/`Write-HealthLog`);
- catch-блоки навколо завантаження `BRAVO.config` і читання Credential
  Manager маскують `$_.Exception.Message` одразу при захопленні винятку —
  ці шляхи друкуються в консоль до того, як спрацює єдина точка масковки
  (self-test `Runtime/CredentialAndConfigErrorsMaskedAtCapture`);
- SFTP-пароль очищається зі script-scope змінних одразу після побудови
  SFTP URL; програмний Health API (`Invoke-BRAVOHealthCheck`) очищає
  `Login`/`sftpUrl`/`smbCredential` у `finally` навіть після ранньої
  помилки (self-test `Health/ProgrammaticApiClearsCredentialState`).
- запит публічної IP-адреси для сповіщень (`api.ipify.org`,
  `checkip.amazonaws.com`) вимкнено за замовчуванням
  (`PublicIPLookupEnabled = $false`) — зайва зовнішня залежність, яка
  розкриває стороннім сервісам факт і час запуску backup.

**Секрет у пам'яті процесу (аудит #5).** Читання з Credential Manager
повертає `SecureString`, а не звичайний рядок: у .NET рядок незмінний,
тому його **неможливо занулити** — копія пароля лишалась би в керованій
купі до збирання сміття й могла потрапити в дамп процесу або pagefile.
Декодування blob'а йде в `char[]` (масив можна очистити) з посимвольним
додаванням у `SecureString`, після чого і масив байтів, і масив символів
зануляються; повного відкритого пароля не існує в керованій пам'яті на
жодному кроці.

| Шлях | Плейнтекст |
|---|---|
| SMB (`PSCredential`) | **не створюється взагалі** — `New-BRAVOSecureCredential` |
| SFTP URL для WinSCP | потрібен: `sftp://user:pass@host` — рядок за побудовою |
| Пароль 7-Zip | потрібен: передається через stdin |

`ConvertFrom-BRAVOSecureSecret` — єдина точка перетворення в плейнтекст;
проміжна некерована копія (BSTR) зануляється детерміновано через
`ZeroFreeBSTR`, не чекаючи GC.

**Чесна межа:** рядок, повернутий цією функцією, лишається звичайним
managed string — незанулюваним. Зміна прибирає зайві копії (насамперед у
самому джерелі, де раніше копія створювалась при кожному читанні) і
робить кожне перетворення видимим у коді, але не усуває плейнтекст як
такий: WinSCP приймає URL, а не `SecureString`. Повне усунення потребує
переходу на SFTP-автентифікацію ключем. Покрито самотестами `Secrets/*`.

**Відомі межі:** SFTP/SMB автентифікація — лише логін/пароль, не
ключова (audit P1.9 рекомендує SFTP key authentication — не
реалізовано). WinSCP не веде окремого session log із секретами (нічого
додатково не приховувати), але й не використовує `gMSA` для scheduled
tasks.

## 4. Модель довіри до Tools (`7za.exe`, `WinSCP.*`)

**Основний захист — version-controlled `TOOLS_MANIFEST.json` у режимі
`Enforce` (блокує запуск).**

Заплановані завдання виконуються від `NT AUTHORITY\SYSTEM`, тому
підмінений `7za.exe` або `WinSCP.com` отримав би найвищі права в
системі. Це найнебезпечніший сценарій цього репозиторію, і саме його
закриває еталонний маніфест:

- `Tools\TOOLS_MANIFEST.json` лежить у тому самому каталозі, що й самі
  утиліти, містить SHA-256
  **усіх семи** виконуваних файлів `Tools/` (`7za.exe`, `7za.dll`,
  `7zxa.dll`, `DragExt64.dll`, `WinSCP.com`, `WinSCP.exe`,
  `WinSCPnet.dll` — підміна DLL не менш небезпечна за підміну `.exe`)
  і потрапляє на сервер разом з комплектом;
- `Test-BRAVOToolManifestIntegrity` (`modules\BRAVO.Compatibility`)
  звіряє хеші на старті. У режимі `Enforce` (типово):
  **Archive і Maintenance зупиняються з кодом завершення `32`**
  (`ToolIntegrityViolation`), Archive додатково надсилає критичне
  сповіщення;
- **Health не запускає інструменти, цілісність яких не підтверджена.**
  Небезпечний не запис на SFTP, а сам ЗАПУСК `WinSCP.com` чи
  завантаження `WinSCPnet.dll`: підмінений бінарник виконає довільний
  код з правами облікового запису завдання (`SYSTEM`), і read-only
  перевірка стає повноцінним носієм шкідливого коду. Тому
  `Test-SFTPHealthConfiguration` пропускає всю SFTP-гілку (єдиний шлях,
  яким Health торкається `Tools/`; 7-Zip він не використовує взагалі),
  а сам Health завершується кодом `32`. Локальні перевірки — служби,
  вільне місце, вік локальних копій — інструментів не запускають і
  виконуються далі: саме вони й лишаються корисними, коли підозрюється
  підміна;
- `$global:toolIntegritySettings.Mode = "Warn"` лишає стару поведінку
  (тільки попередження) — тимчасовий режим міграції, не для постійної
  експлуатації;
- **маніфест ніколи не створюється й не оновлюється автоматично.**
  Відсутній, порожній або пошкоджений маніфест у режимі `Enforce` — це
  теж відмова: інакше найпростішим способом обійти перевірку було б
  просто видалити еталон. Функція, здатна записати новий baseline на
  production-сервері, знецінює саму перевірку — зловмисник, що має права
  підмінити `7za.exe`, тим самим доступом перепише й еталон;
- **сторонній `.exe`/`.dll`/`.com` у `Tools/` теж блокує запуск** у
  режимі `Enforce`. Причина — DLL side-loading: щоб виконати довільний
  код, зловмиснику не обов'язково підміняти `WinSCP.exe` чи `7za.exe`.
  Windows шукає залежності насамперед у каталозі самого виконуваного
  файлу, тому достатньо *підкласти* DLL з відповідним іменем — жоден
  хеш у маніфесті при цьому не зміниться, бо самі інструменти лишились
  недоторканими. Легітимна додаткова залежність вноситься в
  `TOOLS_MANIFEST.json` свідомо, через код-рев'ю.

**Перемикачі безпеки в `BRAVO.config` перевіряються окремо (код `34`).**
Конфігурація навмисно не входить до `RUNTIME_MANIFEST.json`: вона різна
на кожному сервері (шляхи, розклад, увімкнені компоненти), спільного
еталонного хешу для неї не існує. Через це вона лишалася єдиним файлом
комплекту, який можна змінити без сліду, — а в ній є перемикачі, що
вимикають самі перевірки:

| Перемикач | Що вимикає |
|---|---|
| `$global:toolIntegritySettings.Mode = "Warn"` | підмінений `7za.exe`/WinSCP більше не блокує запуск |
| `$global:backupConsistency.Mode ≠ "VSS"` | архів читається з live-каталогу, файли належать різним моментам часу |

Рядок у текстовому файлі коштує зловмиснику дешевше, ніж підміна
бінарника, і лишає менше слідів. Тому `Test-BRAVORuntimeSecuritySettings`
(`BRAVO_RUNTIME_GUARD.ps1`) читає ці значення **розбором AST**
(`[Parser]::ParseFile`), не виконуючи конфігурацію: завантажити
`BRAVO.config` означало б виконати довільний PowerShell-код ще до
перевірки.

Свідоме послаблення лишається можливим, але вимагає **двох дій у двох
різних місцях**: правки конфігурації й змінної середовища
`BRAVO_ALLOW_WEAKENED_SECURITY=1` — за тим самим зразком, що
`BRAVO_ALLOW_UNSUPPORTED_OS`. Друга дія лишає слід поза комплектом.

Чесна межа: перевіряються лише літерали. Значення, обчислене виразом
(`$m = "Warn"; Mode = $m`), статично не читається — і саме тому теж
блокує, інакше обхід був би дешевшим за пряме послаблення. Покрито
самотестами `ConfigSecurity/*`.

**Захист від відкату версії (код `35`).** Усі перевірки вище звіряють
комплект із його **власним** маніфестом. Старий комплект — внутрішньо
узгоджений — пройде їх бездоганно, разом із вразливостями, які відтоді
закрили, і без перевірок, яких у ньому ще не існувало. Найпростіший
спосіб вимкнути `Enforce` — не ламати його, а розгорнути версію, де його
ще не було.

Тому сервер запам'ятовує найвищу версію, яку на ньому запускали
(`LOGS\BRAVO_VERSION_STATE.json`: `highestVersion`, `sourceCommit`,
`recordedAt`), і відмовляється виконувати старішу. Свідомий відкат —
через `BRAVO_ALLOW_DOWNGRADE=1`.

Чесна межа: файл стану лежить поруч із логами, і той, хто має права
підмінити комплект, зазвичай має права й видалити цей файл. Перевірка не
робить відкат неможливим — вона робить його помітним і таким, що
потребує ще однієї свідомої дії. Проти випадкового відкату (розгорнули не
той архів) вона працює повністю. На відміну від маніфеста, пошкоджений
або відсутній файл стану **не** блокує: він не є еталоном довіри, і його
втрата не мусить зупиняти backup. Покрито самотестами `VersionState/*`.

Оновлення інструментів — свідома дія на робочій станції, не на сервері:
`ci\Update-BRAVOToolsManifest.ps1` (без `-Apply` лише показує
розбіжності), далі `git diff -- TOOLS_MANIFEST.json`, потім коміт разом
із самим бінарником і код-рев'ю.

Покрито самотестами `ToolManifest/*` (підміна, видалення файлу,
видалення маніфесту, пошкоджений маніфест, сторонній файл, заборона
автостворення, відповідність маніфесту реальним `Tools/`) та
`ExitCodes/ToolIntegrityViolationPriority`.

**Додатковий шар — trust-on-first-use (TOFU), лише виявлення дрейфу:**

`Get-BRAVOToolIntegrityRecommendation` (`modules\BRAVO.Compatibility`) на
першому запуску мовчки фіксує SHA-256 кожного інструмента в
`Tools\TOOLS_INTEGRITY.json`. На кожному наступному запуску звіряє
контрольну суму — розбіжність **лише попереджає** (`WARNING` у лозі),
production-запуск не блокується. Якщо файл був підмінений до першого
запуску, підміна стане еталонною.

**Явно не реалізовано** (аудит P0.2/P0.3 — потребує реального
сертифіката підпису коду, якого у цього репозиторію немає):

- немає перевірки Authenticode-підпису `WinSCP.*` (маніфест звіряє
  SHA-256, але не підтверджує, що файл справді від виробника);
- (реалізовано — див. розділ 4.1 нижче) захист самого
  PowerShell-комплекту;
- заплановані завдання все ще запускаються з `-ExecutionPolicy Bypass`
  (немає підписаних `.ps1`/`.psm1`/`.psd1`, немає переходу на
  `RemoteSigned`/`AllSigned`);
- немає підписаного (GPG) git tag і підписаного release artifact.

Залишкові межі саме для `Tools/`: якщо зловмисник має права на запис у
робочу копію репозиторію (або на канал доставки комплекту), він може
підмінити бінарник **разом** із `TOOLS_MANIFEST.json` — тоді хеші
збіжаться. Захист від цього — код-рев'ю змін маніфесту й контроль
доступу до репозиторію, а не сама перевірка. На сервері ж маніфест
захищений тим самим ACL, що й решта runtime (розділ 5).

## 4.1. Цілісність PowerShell-комплекту (аудит P2)

`Tools/` захищає `TOOLS_MANIFEST.json`, але підмінити можна й сам код:
`BRAVO_ARCHIV.ps1`, будь-який модуль, `VERSION.json`. Цей шар закриває
`RUNTIME_MANIFEST.json` — еталонні SHA-256 **54 файлів** комплекту
(`.ps1`, `.psm1`, `.psd1`, `VERSION.json`, `TOOLS_MANIFEST.json`).

**Перевірка виконується ДО `Import-Module`** — інакше довелося б
виконати саме той код, який ще не перевірено. Тому вона живе в окремому
`BRAVO_RUNTIME_GUARD.ps1`, який **не має жодної залежності** від решти
комплекту (лише .NET-типи): якби функція жила в `BRAVO.Compatibility`,
треба було б завантажити модуль, щоб перевірити модулі.

Усі три entrypoint (`BRAVO_ARCHIV.ps1`, `BRAVO_HEALTH.ps1`,
`BRAVO_MAINTENANCE.ps1`) dot-source-ять guard першим рядком і при
порушенні завершуються кодом **`33`** (`RuntimeIntegrityViolation`,
пріоритет вищий за `32`). Блокує будь-що з трьох: змінений хеш,
відсутній файл із маніфесту, **підкинутий сторонній `.ps1`/`.psm1`**
(він може бути dot-source-нутий або підхоплений як модуль). Відсутній
чи пошкоджений маніфест — теж відмова.

Оновлення: `ci\Update-BRAVORuntimeManifest.ps1` (без `-Apply` лише
показує розбіжності) на робочій станції, далі `git diff`, коміт разом зі
змінами коду. CI-крок «Integrity manifests are current» не дасть змержити
комплект із застарілим маніфестом — інакше свіжо розгорнутий комплект
заблокував би сам себе на першому ж запуску.

### Що цей шар НЕ закриває (не обходьте мовчки)

1. **Сам guard і сам entrypoint уже виконуються**, коли перевірка
   починається. Вони входять до маніфесту, тому підміна буде помічена —
   але вже після того, як їхній код відпрацював. Повне закриття цієї
   межі потребує Authenticode-підпису й `ExecutionPolicy AllSigned`
   (аудит P0.3, не реалізовано).
2. **`BRAVO.config` навмисно не входить до маніфесту** — він редагується
   на кожному сервері (шляхи, розклад, увімкнені компоненти), спільного
   еталонного хешу для нього не існує. Натомість послаблення захисту
   через конфігурацію зроблено **гучним**: якщо
   `toolIntegritySettings.Mode` не `Enforce`, усі три runtime пишуть
   `WARNING` про те, що підміна інструментів не заблокує запуск.
3. `BRAVO_RUNTIME_INTEGRITY_MODE=Warn` (змінна середовища) послаблює
   перевірку комплекту — аварійний шлях відновлення. Це не додає нового
   вектора атаки: хто може змінити змінні середовища запланованого
   завдання, той уже має права підмінити й сам маніфест.

Покрито самотестами `RuntimeManifest/*` (підміна модуля, відсутній файл,
підкинутий скрипт, видалений і пошкоджений маніфест, заборона
автостворення, відповідність маніфесту комплекту, порядок
guard-перед-Import у кожному entrypoint) та
`ExitCodes/RuntimeIntegrityViolationPriority`.

## 5. Модель ACL

`BRAVO_TASKS_INSTALL.ps1` (за `schedulerSettings.RequireProtectedRuntime`,
типово увімкнено):

- відмовляється встановлювати `SYSTEM`-завдання з каталогу профілю
  користувача (`Desktop`/`Documents`/`Downloads`);
- рекурсивно захищає весь корінь runtime, включно з `Tools` і всіма
  наявними дочірніми файлами — читання/виконання для `Users`, повний
  контроль для `Administrators`/`SYSTEM`;
- прапорці успадкування ACL застосовуються лише до каталогів (файл із
  `InheritanceFlags` кидає `FileSystemAccessRule` помилку);
- у разі помилки під час встановлення повертає попередній стан завдань
  (rollback).

## 6. Обмеження Credential Manager

Windows Credential Manager прив'язаний до облікового запису: запис,
створений для поточного адміністратора, недоступний `SYSTEM`, і навпаки.
`-StoreFor Both` створює обидва записи явно. Якщо забути про це при
ручному налаштуванні (лише `CurrentUser`), заплановане завдання під
`SYSTEM` не побачить credentials і впаде з кодом `31`
(`CredentialsUnavailable`).

Не використовується `gMSA` (group Managed Service Account) — кожен сервер
має власні незалежні записи Credential Manager під локальним `SYSTEM`,
без централізованого керування обліковими даними для кількох серверів.

## 7. Політика оновлення

Оновлення — атомарна заміна всього комплекту (виконувані `.ps1`,
`VERSION.json`, документація, весь каталог `modules`) поверх копії
`BRAVO.config`; секрети в config не переносяться (уже в Credential
Manager). Немає підписаного release artifact і немає окремого release
manifest із хешами файлів — цілісність самого release-пакета залежить
від каналу, яким він потрапляє на сервер (перевірте це самостійно,
наприклад SHA-256 архіву дистрибутиву поза цим репозиторієм).

Немає підписаних git tags (`git tag -a`, без `-s`/GPG) — теги на кшталт
`v4.2.13` є контрольними точками для diff/rollback, а не криптографічним
підтвердженням автентичності релізу.

## 8. Що НЕ покрито цим документом

- Threat model (активи, конкретні вектори атак) — окремий документ
  [THREAT_MODEL.md](THREAT_MODEL.md). Він містить розділ «Залишковий
  ризик» для кожного сценарію; найбільший незакритий — ransomware на
  SFTP-призначення (немає immutable-сховища).
- SFTP/SMB key-based автентифікація, `AppLocker`/`WDAC`, `gMSA` — не
  реалізовано.
- GitHub branch protection (required status checks, заборона прямого
  push у `master`) — CI (розділ нижче) існує й запускається на кожен
  push/PR, але поки що нічого не заважає змержити чи запушити повз
  зелений статус. Спробу ввімкнути через `gh api
  .../branches/master/protection` заблоковано самим GitHub: ця функція
  на приватних репозиторіях вимагає GitHub Pro
  (`403 Upgrade to GitHub Pro or make this repository public`) — не
  забутий крок, а обмеження поточного тарифного плану.

## 8.1. CI (аудит AUD-001)

GitHub Actions (`.github/workflows/ci.yml`), раннер `windows-latest`
(проєкт цільово Windows PowerShell 5.1, не PowerShell 7 — між ними вже
траплялись реальні поведінкові розбіжності в цьому репозиторії), запуск
на кожен push і PR у `master`/`developer`:

- парсинг усіх `.ps1`/`.psm1`/`.psd1` (`static-checks`);
- UTF-8 BOM обов'язковий для `.ps1`/`.psm1`/`.psd1`, заборонений для
  `.md` (та сама конвенція, що вручну підтримувалась досі);
- валідність усіх JSON-файлів (`VERSION.json` тощо);
- `PSScriptAnalyzer` — два проходи (деталі в розділі 8.2 нижче):
  блокуючий security-набір із `PSScriptAnalyzerSettings.psd1` і
  інформаційний прохід для решти правил;
- заборонені патерни (`Invoke-Expression`, мережеве завантаження коду,
  секрет в аргументах процесу, `ExecutionPolicy Bypass` поза
  installer/task definitions) — розділ 8.2;
- повний `BRAVO_SELF_TEST.ps1`;
- сканування секретів (`gitleaks`, окрема Linux-джоба — самому
  скануванню вмісту git-історії ОС не важлива).

**Явно НЕ ввімкнено:** required status checks і заборона прямого push у
`master` (GitHub branch protection) — CI лише запускається й показує
статус, але поки не блокує merge технічно. Причина — не забутий крок, а
обмеження тарифного плану GitHub (розділ 8 вище).

## 8.2. Статичний аналіз: блокуючий security-набір

**Проблема попередньої моделі (виправлено):** CI блокував лише
`Severity=Error`, тоді як більшість корисних правил PSScriptAnalyzer
повертає `Warning`. Додатково `PSAvoidUsingInvokeExpression`,
`PSAvoidUsingConvertToSecureStringWithPlainText`,
`PSAvoidUsingUsernameAndPasswordParams` та інші виключались **глобально**
через `-ExcludeRule`. Навіть якщо кожне наявне місце мало пояснення,
глобальний виняток означав, що **новий** небезпечний код у будь-якому
файлі теж мовчки пройде CI.

**Поточна модель** — `PSScriptAnalyzerSettings.psd1` у корені:

1. **Блокуючий прохід** — рівно набір `IncludeRules` (секрети та облікові
   дані, виконання довільного коду, hardcoded ComputerName, зламані
   хеш-алгоритми, порівняння з `$null`, аліаси cmdlet). Жодне з цих
   правил **не** виключається глобально. Кожне обґрунтоване місце має
   точковий `[Diagnostics.CodeAnalysis.SuppressMessageAttribute]` із
   полем `Justification` біля конкретної функції — видимий при код-рев'ю
   разом зі змінами. Тому нове входження завалить CI, навіть якщо поруч
   уже є легітимне обґрунтоване використання.
2. **Інформаційний прохід** — усі інші правила, лише `::warning` без
   блокування (`PSAvoidUsingWriteHost` для інтерактивної консолі
   допоміжних скриптів, `PSAvoidGlobalVars` як контракт між
   `BRAVO.config` і runtime-модулями — усталена архітектура, не
   недогляд).

Обґрунтовані suppressions на сьогодні (усі — секрет уже з Windows
Credential Manager або необхідний міст до .NET/зовнішнього API, не
хардкод у джерелі): `New-BRAVOPlainTextCredential`, `New-BRAVOSftpUrl`
(`BRAVO.Credentials`); `Invoke-BRAVOSevenZipIntegrityTest`,
`Invoke-BRAVOSevenZipExtraction` (`BRAVO.Compatibility`);
`Test-SevenZipArchiveIntegrity` (`BRAVO.ArchiveHelpers`);
`Read-SecretEntries`, `Restore-CredentialOperationSnapshots`
(`BRAVO_CREDENTIALS_SETUP.ps1`); `Test-SftpReadOnlyAccess`,
`Test-SmbReadOnlyAccess` (`BRAVO_DRY_RUN.ps1`). Плюс три suppressions
для **хибних спрацювань** правила на параметрах, чия назва містить
«Credential», але які не є секретом (`$CredentialSettings`,
`$CredentialComponent`).

**Окремий крок — заборонені патерни.** Те, чого PSScriptAnalyzer не
ловить взагалі або ловить лише як AST (пропускаючи входження всередині
рядків). Кожен пункт — те, чого в цьому репозиторії немає й не повинно
з'явитись: `Invoke-Expression`/`iex`; мережеве завантаження коду
(`DownloadString`, `DownloadFile`, `Net.WebClient`); секрет у
`-ArgumentList` процесу; `ExecutionPolicy Bypass` поза allowlist із
шести файлів, де він легітимний (перезапуск через UAC і визначення
завдань Планувальника — розділ 4). Рядки-коментарі ігноруються (у
репозиторії є приклади команд запуску в коментарях).

**Регресія перевірена:** синтетичний файл із `ConvertTo-SecureString
-AsPlainText`, `Invoke-Expression` і `[string]$Password` блокується
всіма трьома відповідними правилами; синтетичний файл із чотирма
забороненими патернами ловиться всіма чотирма, а той самий текст у
коментарі — ігнорується.

Повернення глобального виключення охороняється самотестом:
`StaticAnalysis/SecurityRulesAreBlocking` і
`StaticAnalysis/NoGlobalSecurityRuleExclusions`.
