# OPERATIONS.md — операторський runbook

Що робити, коли BRAVO повідомив про проблему. Документ призначений
адміністратору установи, який побачив помилку й не має контексту
розробки.

Розподіл ролей між документами:

| Документ | Відповідає на питання |
|---|---|
| [README.md](README.md) | як налаштувати й експлуатувати |
| [SECURITY.md](SECURITY.md) | яка модель безпеки і чому саме така |
| [THREAT_MODEL.md](THREAT_MODEL.md) | від чого захищаємось і що лишається відкритим |
| **OPERATIONS.md** | **щось зламалось — які дії зараз** |

## Головне правило

**Не «лікуйте» помилку цілісності вимкненням перевірки.** Видалити
маніфест, перевести режим у `Warn`, видалити «зайвий» файл із `Tools\` —
це не усунення причини, а вимкнення сигналізації. Якщо підозра на
підміну підтвердиться, ви втратите єдиний доказ.

Другий за важливістю принцип: **зламаний backup гірший за відсутній,
але перезаписаний хороший backup — гірший за обидва.** Перш ніж
запускати `BRAVO_ARCHIV.ps1` вручну «щоб виправити», переконайтесь, що
не затираєте останню відому хорошу копію.

## `20` — пропущено, lock зайнятий

**Симптом.** Завдання завершилось миттєво, у лозі — повідомлення про
зайнятий lock.

**Що означає.** Інший екземпляр Archive або Maintenance ще виконується.
Це штатний захист від паралельного запису в ті самі архіви, а не
помилка.

**Чого не робити.** Не видаляти `BRAVO_OPERATION.lock` і не завершувати
процес за PID, не звіривши `hostname` у самому файлі: PID міг бути
перевикористаний іншим процесом.

**Діагностика.**

```powershell
Get-Content "C:\ProgramData\BRAVO\Locks\BRAVO_OPERATION.lock" | ConvertFrom-Json
Get-Process -Id <pid> -ErrorAction SilentlyContinue | Select-Object Id, ProcessName, StartTime
```

**Виправлення.** Якщо процес живий — нічого не робіть, це нормальне
перекриття довгих завдань; збільште `OperationLockWaitMinutes`. Якщо
процес мертвий (сервер перезавантажився під час архівації), lock
залишився осиротілим — тоді його видалення безпечне.

**Ескалація.** Якщо код `20` повторюється кілька днів поспіль —
архівація не встигає у вікно, потрібен перегляд розкладу.

## `30` — некоректна конфігурація

**Симптом.** Перший `[ERROR]` одразу після
`=== ПЕРЕВІРКА СУМІСНОСТІ СИСТЕМИ ===`.

**Що означає.** `BRAVO.config` не пройшов валідацію, або ОС/PowerShell
у рівні `Unsupported`.

> **Гола `.NET`-помилка замість зрозумілого повідомлення (виправлено
> 2026-08-24).** Якщо `BRAVO_SETUP.ps1`/`BRAVO_SELF_TEST.ps1`/
> `BRAVO_DRY_RUN.ps1` завершуються з "Не вдалося завантажити
> BRAVO.config ...: Ссылка на объект не указывает на экземпляр
> объекта" (raw NullReferenceException) — реальний DEV-майданчик
> підтвердив, що причина типово PowerShell <4.0 (`Get-BRAVOOSSupportTier`
> класифікує це як `Unsupported` незалежно від версії ОС). Повідомлення
> тепер додає прямий висновок `Get-BRAVOOSSupportTier` до причини —
> перевірте `$PSVersionTable.PSVersion` і оновіть Windows Management
> Framework до PowerShell 5.1. BRAVO не бекпортить сумісність із
> PowerShell 3.x — це свідомо нижче baseline.

> **"Не вдалося визначити BackupRoot: ... вимагає визначеного
> EffectiveLIMSRoot" при УЖЕ встановленій і запущеній службі BRAVO.**
> Перевірте `DisplayName` реальної служби: `Get-Service BRAVO | Select
> DisplayName` (або `Get-CimInstance Win32_Service -Filter
> "Name='BRAVO'" | Select DisplayName`). Discovery ідентифікує службу
> BRAVO за Name ТА DisplayName одночасно (навмисний захист від хибного
> співставлення з чужим сервісом) — з 2026-08-24 приймає обидва відомі
> реальні варіанти написання, `"BRAVO Service"` і `"BRAVO Server"`
> (`maintenanceSettings.Services.BravoDisplayName` у `BRAVO.config`, за
> замовчуванням масив з обома). Якщо на вашому сервері DisplayName
> інший за обидва — допишіть його третім елементом списку (не
> замінюйте наявні два).

**Чого не робити.** Не встановлювати `BRAVO_ALLOW_UNSUPPORTED_OS=1`
як спосіб «прибрати помилку» — це свідоме зняття гарантій, а не
виправлення.

**Діагностика.**

```powershell
.\BRAVO_SETUP.ps1 -ValidateOnly
```

Відтворює ту саму перевірку без production-дій і без елевації.

**Виправлення.** Виправити названий у помилці розділ `BRAVO.config`.
Після правки — повторний `-ValidateOnly` до чистого результату.

**Ескалація.** Якщо `-ValidateOnly` зелений, а production-запуск усе
одно дає `30` — це розбіжність контекстів (див.
[вручну працює, за розкладом — ні](#вручну-працює-а-за-розкладом--ні)).

## `31` — недоступні credentials

**Симптом.** `credentialInitializationError` або
`archiveCredentialInitializationError` у консольному виводі.

**Що означає.** Немає або порожній запис Windows Credential Manager для
потрібного компонента — найчастіше він створений для адміністратора,
але не для `SYSTEM`.

**Чого не робити.** Не вписувати пароль у `BRAVO.config`. Секрети в
конфігурацію не записуються ніколи (SECURITY.md, розділ 3).

**Діагностика.**

```powershell
.\BRAVO_CREDENTIALS_SETUP.ps1 -Action Test -Component Required -StoreFor Both
```

**Виправлення.**

```powershell
.\BRAVO_CREDENTIALS_SETUP.ps1 -Action Ensure -Component Required -StoreFor Both
```

`-StoreFor Both` обов'язковий: заплановані завдання читають сховище
`SYSTEM`, ручні запуски — сховище адміністратора.

**Ескалація.** Якщо запис існує для обох контекстів, а помилка
лишається — можлива зміна пароля на боці SFTP/SMB.

## `32` — порушено цілісність інструментів

> **Рівень S1.** Заплановані завдання виконуються від
> `NT AUTHORITY\SYSTEM`. Підмінений `7za.exe` або `WinSCP.com` отримав
> би найвищі права в системі.

**Симптом.** `ЦIЛIСНIСТЬ IНСТРУМЕНТIВ ПОРУШЕНО` на старті логу. Archive
і Maintenance зупинились; Health пропустив SFTP-гілку, але виконав
локальні перевірки.

**Що означає.** Каталог `Tools\` розійшовся з `TOOLS_MANIFEST.json`:
змінився хеш, зник файл, з'явився сторонній `.exe`/`.dll`/`.com`, або
сам маніфест відсутній чи пошкоджений.

**Чого не робити.**

- **не видаляти** `TOOLS_MANIFEST.json` — у режимі `Enforce` це теж
  відмова, і ви лише знищите еталон;
- **не запускати** `ci\Update-BRAVOToolsManifest.ps1 -Apply` на
  сервері — це легітимізує те, що там зараз лежить, яким би воно не
  було;
- **не переводити** `$global:toolIntegritySettings.Mode` у `Warn`;
- не видаляти «зайвий» файл до того, як зафіксували його копію.

**Діагностика.** Спершу зафіксуйте докази:

```powershell
Get-ChildItem "C:\Program Files\BRAVO-Toolkit\Tools" -File |
    Get-FileHash -Algorithm SHA256 |
    Select-Object Hash, Path | Format-Table -AutoSize
Get-ChildItem "C:\Program Files\BRAVO-Toolkit\Tools" -File |
    Select-Object Name, Length, CreationTime, LastWriteTime
```

Потім звірте з `TOOLS_MANIFEST.json` у репозиторії й з тим, хто мав
доступ до сервера у вікні між `LastWriteTime` і зараз.

**Розвилка.**

*Оновлення інструментів було свідомим* (ви або колега оновлювали
7-Zip/WinSCP): на **робочій станції**, не на сервері —
`ci\Update-BRAVOToolsManifest.ps1 -Apply`, `git diff`, код-рев'ю, коміт
разом із бінарником, розгортання нового комплекту.

*Оновлення свідомим не було:* це інцидент. Сервер від мережі не
від'єднуйте, доки не зняли копію `Tools\` і логів — але й backup не
запускайте. Далі — [ransomware або масове
видалення](#ransomware-або-масове-видалення-копій), розділ про
компрометацію.

**Ескалація.** Будь-який непояснений `32` — S1 негайно. Один
непояснений файл у `Tools\` достатній: DLL side-loading не потребує
підміни самого `WinSCP.exe`.

## `33` — порушено цілісність PowerShell-комплекту

> **Рівень S1.** Те саме, що `32`, але для власного коду BRAVO.

**Симптом.** `ЦІЛІСНІСТЬ КОМПЛЕКТУ ПОРУШЕНО` — найперший рядок виводу,
ще до завантаження модулів.

**Що означає.** Файл комплекту розійшовся з `RUNTIME_MANIFEST.json`,
зник, або в комплекті з'явився сторонній `.ps1`/`.psm1`/`.psd1`.

**Чого не робити.** Те саме, що для `32`: не видаляти маніфест, не
запускати `ci\Update-BRAVORuntimeManifest.ps1 -Apply` на сервері, не
редагувати `.ps1` «на місці, щоб швидко полагодити». Редагування файлу
комплекту прямо на production і є найчастішою невинною причиною цього
коду — і саме тому вона не повинна бути дозволена мовчки.

**Діагностика.**

```powershell
# Guard друкує повний перелік розбіжностей і не вимагає модулів
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "C:\Program Files\BRAVO-Toolkit\BRAVO_RUNTIME_GUARD.ps1"
```

Звірте `VERSION.json.sourceCommit` на сервері з тим, що ви розгортали.

**Виправлення.** Розгорнути комплект заново з репозиторію (атомарна
заміна каталогу, README розділ 10). Не точкове копіювання окремих
файлів.

**Ескалація.** Якщо `sourceCommit` на сервері не відповідає жодному
коміту, який ви розгортали — S1, інцидент.

### Окремий випадок: `сторонні скрипти в комплекті`

Найчастіша реальна причина коду `33` на свіжому сервері — і майже ніколи
не атака.

**Симптом.** `ЦІЛІСНІСТЬ КОМПЛЕКТУ ПОРУШЕНО: сторонні скрипти в
комплекті: Tools\...`.

**Що означає.** У каталозі runtime лежить `.ps1`/`.psm1`/`.psd1`, якого
немає в `RUNTIME_MANIFEST.json`. Типово це залишки попереднього
розкладання (у старих версіях скрипти жили в `Tools\`), розпакований
поверх архів або копія «щоб було».

Маніфест правий: він не знає, що цей файл робить, а комплект
виконується від `SYSTEM`.

**Чого не робити.** Не оновлюйте маніфест на сервері, щоб «узаконити»
знахідку — так ви підпишете будь-що, що там опинилось. Маніфест
оновлюється лише в репозиторії, разом із кодом.

**Виправлення.** Прибрати зайве з runtime — перемістити, а не видалити,
доки не переконаєтесь, що воно нікому не потрібне:

```powershell
Get-ChildItem "C:\Program Files\BRAVO-Toolkit\Tools\*.ps1" | Select-Object Name, Length, LastWriteTime
Move-Item "C:\Program Files\BRAVO-Toolkit\Tools\<файл>.ps1" C:\Temp\ -Force
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "C:\Program Files\BRAVO-Toolkit\BRAVO_RUNTIME_GUARD.ps1"
```

**Профілактика.** Розгортайте атомарною заміною каталогу, не
копіюванням поверх: копіювання поверх лишає файли, яких у новій версії
вже немає. `BRAVO_DRY_RUN.ps1` тепер виконує ту саму перевірку, тому
проблема видно ще до першого запуску за розкладом.

### Окремий випадок: `не вдалося завантажити BRAVO_RUNTIME_GUARD.ps1`

Той самий код `33`, але інше повідомлення й **інша причина**: guard на
місці, проте не виконався. Найчастіше це не атака, а політика виконання.

**Симптом.** `Файл ... не имеет цифровой подписи` / `is not digitally
signed`, `PSSecurityException`, `UnauthorizedAccess`.

**Що означає.** На сервері діє `ExecutionPolicy AllSigned` (зазвичай через
доменну GPO), а комплект BRAVO не має Authenticode-підпису — це
задокументована межа моделі (`THREAT_MODEL.md` розділ 3). Заплановані
завдання від цього не страждають: вони запускаються з
`-ExecutionPolicy Bypass`. Страждає лише ручний запуск із консолі.

**Діагностика.**

```powershell
Get-ExecutionPolicy -List
```

**Виправлення — ручний запуск.** Так само, як це робить планувальник:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "C:\Program Files\BRAVO-Toolkit\BRAVO_ARCHIV.ps1"
```

Прямий виклик `C:\Program Files\BRAVO-Toolkit\BRAVO_ARCHIV.ps1` під `AllSigned` не
працюватиме й не має працювати.

**Чого не робити.** Не знижуйте `ExecutionPolicy` машини до
`Unrestricted`, щоб «полагодити». `AllSigned` — сильніший контроль за
все, що є в BRAVO; вимкнути його заради зручності означає послабити
сервер, а не виправити комплект. Правильне закриття — Authenticode-підпис
комплекту (потребує сертифіката, `RELEASE_CHECKLIST.md` розділ 2).

**Ескалація.** Якщо політика виконання **не** `AllSigned`, а guard усе
одно не завантажується — це вже S1: файл пошкоджено або підмінено, і
запуск заблоковано правильно.

## `34` — конфігурація послаблює захист

> **Рівень S1**, якщо ви цього не робили. S3, якщо робили свідомо.

**Симптом.** `КОНФІГУРАЦІЯ ПОСЛАБЛЮЄ ЗАХИСТ` на старті, до завантаження
модулів.

**Що означає.** У `BRAVO.config` вимкнено один із перемикачів, на яких
тримається решта: `toolIntegritySettings.Mode = "Warn"` (підмінений
`7za.exe`/WinSCP більше не блокує запуск) або
`backupConsistency.Mode ≠ "VSS"` (архів читається з live-каталогу).

`BRAVO.config` навмисно не входить до `RUNTIME_MANIFEST.json` — він
різний на кожному сервері, спільного еталонного хешу не існує. Саме
тому він лишався єдиним файлом комплекту, який можна змінити без сліду,
і саме тому ці два перемикачі перевіряються окремо: розбором AST, без
виконання файлу.

**Чого не робити.** Не встановлюйте `BRAVO_ALLOW_WEAKENED_SECURITY=1`,
щоб «прибрати помилку». Змінна існує для свідомої тимчасової міграції, і
її сенс саме в тому, що вона лишає слід **поза** комплектом: щоб
послабити захист, потрібні дві дії в двох різних місцях.

**Діагностика.** Повідомлення називає конкретний перемикач і його
значення. Далі — хто і коли редагував конфігурацію:

```powershell
Get-Item "C:\Program Files\BRAVO-Toolkit\BRAVO.config" | Select-Object LastWriteTime, Length
git -C <робоча копія> diff -- BRAVO.config   # якщо конфігурація версіонується
```

**Виправлення.** Повернути `Mode = "Enforce"` і `Mode = "VSS"`. Якщо
послаблення справді потрібне (міграція, оновлення інструментів) —
встановіть змінну середовища явно, з датою й причиною в журналі змін
установи, і приберіть її одразу після завершення міграції.

**Ескалація.** Якщо ніхто не редагував конфігурацію — це S1: у
зловмисника рядок у текстовому файлі коштує дешевше, ніж підміна
бінарника, і лишає менше слідів.

## `35` — відкат на старішу версію

**Симптом.** `ВІДКАТ ВЕРСІЇ: розгорнуто X, тоді як на цьому сервері вже
запускали Y`.

**Що означає.** `VERSION.json.packageVersion` розгорнутого комплекту
нижчий за найвищий, який на цьому сервері колись запускали (записаний у
`C:\ProgramData\BRAVO\State\BRAVO_VERSION_STATE.json`).

Усі інші перевірки звіряють комплект із його **власним** маніфестом.
Старіший комплект пройде їх бездоганно — разом із вразливостями, які
відтоді закрили, і без перевірок, яких у ньому ще не існувало.
Найпростіший спосіб вимкнути режим `Enforce` — не ламати його, а
розгорнути версію, де його ще не було.

**Чого не робити.** Не видаляйте `BRAVO_VERSION_STATE.json`, щоб
«скинути» перевірку. Якщо відкат свідомий, для цього є явна змінна;
якщо ні — ви знищите єдиний слід того, що на сервері колись була новіша
версія.

**Діагностика.**

```powershell
Get-Content "C:\ProgramData\BRAVO\State\BRAVO_VERSION_STATE.json" | ConvertFrom-Json
Get-Content "C:\Program Files\BRAVO-Toolkit\VERSION.json" | ConvertFrom-Json |
    Select-Object packageVersion, buildId, sourceCommit
```

Звірте `sourceCommit` обох: він однозначно вказує, який саме код
розгорнуто й який був раніше.

**Розвилка.**

*Відкат свідомий* (аварійне повернення на попередній реліз після
невдалого оновлення): встановіть `BRAVO_ALLOW_DOWNGRADE=1`, зафіксуйте
причину в журналі змін установи, приберіть змінну після повернення на
актуальну версію.

*Відкат не планувався:* найімовірніше розгорнули не той архів. Розгорніть
актуальний комплект із репозиторію. Якщо ніхто нічого не розгортав — S1.

**Ескалація.** Непояснений відкат — S1: це працездатний спосіб тихо
повернути сервер у стан до всіх виправлень безпеки.

> **Чесна межа.** Файл стану лежить поруч із логами, і той, хто має
> права підмінити комплект, зазвичай має права й видалити цей файл.
> Перевірка не робить відкат неможливим — вона робить його помітним і
> таким, що потребує ще однієї свідомої дії. Проти випадкового відкату
> вона працює повністю.

## `36` — недостатньо прав (лише `BRAVO_HEALTH.ps1`)

**Симптом.** `КРИТИЧНА ПОМИЛКА: BRAVO HEALTH запущено без прав
адміністратора...` або `ПОМИЛКА СЕРЕДОВИЩА` / `Недоступний шлях: ...` на
старті, без жодного `[N/5]`-кроку або лише з `[1/5] Середовище й
цілісність інструментів ... ERROR`.

**Що означає.** `BRAVO_HEALTH.ps1` запущено вручну без прав
адміністратора. Один із трьох випадків:

- **Explicit `-NonInteractive` без elevation** — власний argv процесу
  (`[Environment]::GetCommandLineArgs()`, точний, не substring) містить
  окремий елемент `-NonInteractive`. UAC свідомо не показується: немає
  інтерактивної сесії, яка могла б на нього відповісти.
- **UAC скасовано** — інтерактивний ручний запуск, але користувач
  натиснув Cancel у діалозі підвищення прав.
- **`UnauthorizedAccessException` при записі** в `LOGS` / `TEMP` —
  обліковий запис бачить ці каталоги (їх створив `SYSTEM`), але не може
  в них писати. Це виявляє ранній preflight, ДО будь-якого реального
  health-check. Якщо причина НЕ в правах (диск повний, `PathTooLong`,
  файлова система) — див. [код 37](#37--недоступні-logstemp-не-через-права-лише-bravo_healthps1),
  не 36.

У всіх трьох випадках жодна реальна перевірка (служби/локальні
копії/SFTP/SMB) не виконувалась.

**Чого не робити.**

- Не послаблюйте ACL каталогу комплекту (`icacls ... /grant Users:M` і
  подібне), щоб «дозволити» ручний запуск без адміністратора. Рішення —
  запускати з правами адміністратора (UAC підхопить це автоматично), а
  не відкривати запис звичайним користувачам.
- Не інтерпретуйте цей код як SFTP-проблему: SFTP-перевірка при коді 36
  не виконувалась узагалі, на відміну від `50`/`70`.

**Діагностика.**

```powershell
# Заплановане завдання (SYSTEM) цей код НЕ повертає — воно завжди elevated.
# Якщо код 36 з'явився в історії Планувальника, а не з ручної консолі —
# перевірте обліковий запис завдання BRAVO_ARCHIV_HEALTH:
.\BRAVO_TASKS_DIAGNOSE.ps1 -TestAccess
```

**Розвилка.**

*Ручний запуск, звичайна консоль:* повторіть запуск від імені
адміністратора (правою кнопкою → «Запуск від імені адміністратора», або
підтвердьте запит UAC, який `BRAVO_HEALTH.ps1` тепер показує сам).

*Планове завдання `BRAVO_ARCHIV_HEALTH` повертає 36:* це S2, не S3 —
завдання від `SYSTEM` ніколи не повинно бачити UAC і не повинно
провалювати preflight на власних `LOGS`/`TEMP`. Перевірте, чи не
змінили ACL каталогу комплекту, і чи завдання дійсно виконується від
`SYSTEM` (`BRAVO_TASKS_DIAGNOSE.ps1 -TestAccess`).

**Ескалація.** Поодинокий код 36 при ручному запуску — S3, очікувана
поведінка (просто повторіть з правами адміністратора). Якщо цей код
дає **заплановане** завдання — S2.

## `37` — недоступні `LOGS`/`TEMP` не через права (лише `BRAVO_HEALTH.ps1`)

**Симптом.** `ПОМИЛКА СЕРЕДОВИЩА` / `Не вдалося використовувати runtime
TEMP/LOGS: ...` на старті, з конкретною причиною в тексті (НЕ «потрібні
права адміністратора»).

**Що означає.** Той самий ранній write-probe у `LOGS`/`TEMP`, що й код
36, але виняток — **не** `UnauthorizedAccessException`: диск повний,
`PathTooLong`, пошкоджена файлова система, або жоден кандидат
тимчасового каталогу взагалі не створюється. Права адміністратора тут
нічого не виправлять.

**Чого не робити.**

- Не давайте пораду «запустіть адміністратором» — вона правильна для
  коду 36, але не для 37.
- Не послаблюйте ACL.

**Діагностика.** Читайте текст помилки дослівно — там конкретна
`.Exception.Message` (наприклад «There is not enough space on the
disk», «The specified path, file name, or both are too long»).
Перевірте вільне місце на диску з `LOGS`/`TEMP` і саму доступність
шляху (`Test-Path`).

**Розвилка.** Усуньте конкретну причину (звільніть місце, виправте
шлях, перевірте диск) і повторіть запуск.

**Ескалація.** S3 при разовому диску, що майже заповнений; S2, якщо
код 37 дає заплановане завдання `BRAVO_ARCHIV_HEALTH` (SYSTEM теж
залежить від тих самих `LOGS`/`TEMP`).

## `40` — провал локальної архівації (часто VSS)

**Симптом.** `[ERROR]` у секції `АРХІВАЦІЯ <компонент>`.

**Що означає.** Архів не створено. Найчастіша причина — недоступний
VSS Snapshot Set. MODEL, BLOG і BRAVOEXCH читаються з одного point-in-time;
same-volume sources використовують одну shadow copy, multi-volume sources —
кілька shadow copies в одному set. При
`backupConsistency.Mode = "VSS"` архівація з live-каталогу **свідомо не
виконується**. Неузгоджений архів гірший за відсутній, бо створює
хибну впевненість.

**Чого не робити.** Не перемикати `backupConsistency.Mode` на читання
live-каталогу, щоб «хоч якийсь backup був». Ви отримаєте архів, у якому
різні файли належать різним моментам часу — і дізнаєтесь про це під час
відновлення.

**Діагностика.** У лозі шукайте компонент `VSS` і код
`Win32_ShadowCopy.Create` (текстове пояснення виводиться поруч).

```powershell
vssadmin list writers   # усі writers мають бути Stable, No error
vssadmin list shadowstorage
Get-Service VSS, swprv | Select-Object Name, Status, StartType
Get-WmiObject Win32_ShadowCopy | Select-Object ID, VolumeName, InstallDate
```

Після kill/timeout перевірте
`C:\ProgramData\BRAVO\State\BRAVO_VSS_OWNERSHIP.json`. Наступний Archive
після отримання machine-wide lock автоматично прибирає лише записані там
BRAVO-owned Shadow IDs і видаляє state після успіху. Не редагуйте owner або
список ID вручну й не запускайте масове `vssadmin delete shadows /all`:
пошкоджений/чужий state навмисно блокує автоматичне видалення.

**Типові причини.**

| Симптом у лозі | Причина |
|---|---|
| `том не підтримує VSS` | джерело на мережевому диску або non-NTFS томі |
| `недостатньо місця` | вичерпано shadow storage — розширте `vssadmin resize shadowstorage` |
| writer у стані `Failed` | перезапустіть відповідну службу, потім `swprv` |
| persisted orphan cleanup failed | перевірте exact IDs у `BRAVO_VSS_OWNERSHIP.json`, VSS/WMI і права SYSTEM; state не видаляється до успішного cleanup |
| `VSS service/class/diskshadow capability incomplete`, джерела на різних томах | `diskshadow.exe` відсутній — типово на клієнтських Windows 10/11 (підтверджено 2026-09-01: відсутній на кількох build 19045/22H2 Pro-машин, на відміну від Windows Server, де він штатний). Перевірте `Test-Path "$env:SystemRoot\System32\diskshadow.exe"`. Якщо це очікувана клієнтська машина без нього — розмістіть `MODEL`/`BLOG`/`BRAVOEXCH` на одному томі (тоді достатньо однотомного `Win32_ShadowCopy.Create`); багатотомні джерела без `diskshadow.exe` наразі не підтримуються — не спроба обійти цю вимогу, а свідома fail-closed відмова. |

**Ескалація.** Якщо VSS не відновлюється — S2, але з жорстким
дедлайном: доки VSS зламаний, щоденних backup **немає взагалі**.

### Archive preflight: перевірка вільного місця (двоступенева модель)

Провал preflight-кроку `Перевірка вільного місця` в `BRAVO_ARCHIV` теж
завершується кодом `40` (`Результат: ПОМИЛКА`, `Причина: Недостатньо
вільного місця або не вдалося перевірити локальні диски: ...`) — архіви
при цьому **не створювались взагалі**, попередні валідні копії
недоторкані.

Перевірка двоступенева:

1. **Фіксований поріг** `Limits.MinimumFreeSpaceGB` (типово 20 GB) на
   кожному локальному Fixed-диску, крім `Limits.ExcludedDrives` —
   загальний захист від переповнення диска.
2. **Розрахункова оцінка** потреби НАЙБЛИЖЧОГО backup: для кожного
   увімкненого компонента (MODEL/BLOG/BRAVOEXCH) береться розмір
   останнього hash-підтвердженого валідного архіву + запас
   `Limits.EstimatedSpaceMarginPercent` (типово 25%); компоненти на
   одному фізичному диску сумуються. Компонент без валідної історії
   (перший запуск, bootstrap) з оцінки пропускається.

Як читати результат:

- **Крок `OK`, але в лозі WARNING** виду `Диск D:: вільно N GB — нижче
  фіксованого порогу 20 GB, але розрахункова потреба X GB покрита (...)
  — продовжуємо (WARNING, не блокує).` — штатний стан: фіксований поріг
  провалено, але розрахунок для ТОГО САМОГО диска доводить достатність,
  тож backup продовжується. Негайні дії не потрібні; заплануйте
  звільнення/розширення місця в робочому порядку, бо запас тане.
- **Крок `ERROR` з `залишилось N GB, потрібно мінімум 20 GB`** — диск
  нижче порогу і БЕЗ розрахункового виправдання (на ньому немає жодного
  оціненого компонента — bootstrap або диск не бере участі в backup).
  Послаблення тут свідомо не застосовується.
- **Крок `ERROR` з `розрахункова потреба X GB ..., доступно лише Y GB`**
  — недостатність саме за оцінкою; вона блокує завжди, незалежно від
  того, чи проходить фіксований поріг.

**Чого не робити.** Не піднімайте `ExcludedDrives`/не знижуйте
`MinimumFreeSpaceGB`, щоб «пропихнути» backup: якщо блокує розрахункова
оцінка — місця реально не вистачить і 7-Zip/VSS впаде посеред роботи,
лише пізніше і брудніше.

**Ескалація.** Якщо вільного місця менше за розрахункову потребу
найближчого backup — S1: наступна архівація не пройде.

## `43` — не вдалося відновити дані (`BRAVO_DATA_RESTORE.ps1`)

> **`BRAVO_MAINTENANCE.ps1` теж може завершитися `43`** — коли реставрація
> MODEL через `bravocmd repair` не підтвердилась (перервано/ненульовий код або
> repair дав критичні зміни) і виконувався відкат із before-архіву.
> Перевірте журнал Maintenance:
> - `rollback=SUCCESS` / «модель не постраждала» — модель консистентна,
>   служби піднято автоматично; реставрацію треба повторити наступним
>   прогоном (плановий слот не позначено виконаним).
> - `rollback=FAILED` / «цілісність моделі НЕ встановлено» — **служби BRAVO
>   свідомо НЕ піднято** (fail-closed), quiescence-маркер лишається suppressed;
>   потрібне ручне відновлення MODEL із before-архіву
>   (`<ArchiveRoot>\MODEL\<prefix>_before_<timestamp>.mdz`) перед запуском служб.
>
> before-архів реставрації недоторканий до підтвердженої консистентності —
> це ваша копія для ручного відкату. Самоперевірка реставрації
> (before-CSV + порівняння розмірів) виконується **завжди**, незалежно від
> `-DisableSizeCheck` (цей прапорець керує лише окремим кроком «.md > ліміт»).
>
> **Перш ніж припускати реальну втрату даних:** перевірте файли, позначені
> як "ФАЙЛ ВІДСУТНІЙ", прямо на диску (`Get-Item <шлях>`) — на реальному
> DEV-LIMS (2026-08-24) підтверджено false-positive: антивірус з активним
> real-time-захистом (`Get-MpComputerStatus`, `RealTimeProtectionEnabled`)
> без винятку для `LIMS\Model`/`ARCHIV` тримав щойно записані гігабайтні
> `.md`-файли залоченими довше за retry-вікно перевірки (`Compare-FileSizes`
> повторює сканування до 12 разів з паузою 15с — сумарно до 3 хв., але
> сканування кількох ГБ real-time-антивірусом теоретично може перевищити
> й це). Якщо `Get-Item` показує файл з очікуваним розміром, а Maintenance
> усе одно звітує "ФАЙЛ ВІДСУТНІЙ" — додайте виняток антивірусу:
> `Add-MpPreference -ExclusionPath "<LIMSRoot>\Model"` (і за потреби
> `\ARCHIV`) — це канонічний фікс, retry-вікно в коді лише другий рубіж
> захисту з обмеженим бюджетом. Після підтвердження цілісності вручну —
> приберіть quiescence-маркер (`%ProgramData%\BRAVO\State\
> BRAVO_SERVICE_QUIESCENCE.json`, розділ "Аварійне відновлення служб"
> вище) і запустіть служби вручну.
>
> **Друга й окрема причина того самого симптому (виправлено в коді,
> 5.3.0).** Якщо помилка "ФАЙЛ ВІДСУТНІЙ" повторюється **детерміновано
> з тим самим набором файлів**, незалежно від тривалості retry-вікна, і
> зберігається навіть одразу після rollback із щойно підтвердженого
> цілісним архіву — це вже НЕ ознака антивірусу (той дав би плаваючий,
> зменшуваний з часом результат). На реальному DEV-LIMS (ДНДІЛДВСЕ,
> найбільша/найглибша модель серед майданчиків) причиною була ненадійна
> `Get-ChildItem -Recurse`-enumeration каталогу MODEL на великому дереві —
> виправлено переходом `Compare-FileSizes` на прямий `[IO.DirectoryInfo]`
> `::EnumerateFiles`, той самий механізм, що вже використовує перевірка
> розмірів `.md` перед реставрацією. На поточному білді (з цим фіксом)
> додаткових дій не потрібно. Якщо детермінований варіант симптому виник
> на білді, що вже містить цей фікс — це новий, ще не задокументований
> випадок; ескалюйте з повним журналом Maintenance, а не повторюйте
> AV-виняток.

**Симптом.** `BRAVO_DATA_RESTORE.ps1` завершився кодом `43`; у підсумку
компоненти мають статус `ПОМИЛКА`, `ВІДКОЧЕНО` або `ПОМИЛКА ВІДКАТУ`.

**Статуси компонентів у підсумку.**

| Статус | Що це означає для даних |
|---|---|
| `ВІДНОВЛЕНО` | компонент справді відновлено з backup |
| `ВІДКОЧЕНО` | попередній стан повернуто; `.prerestore_*` уже перейменовано назад |
| **`ПОМИЛКА ВІДКАТУ`** | **відкат почався й не завершився — стан каталогу не гарантований; потрібне ручне повернення (процедура нижче), `.prerestore_*` збережено** |
| `ПОМИЛКА` | відновлення цього компонента не вдалося |
| `НЕ ВИКОНУВАВСЯ` | черга до компонента не дійшла |

**Що означає.** Відмовила сама операція відновлення: не знайдено COMPLETE
generation, компонент неповний у manifest, бракує артефактів чи місця, не
вдалося зупинити служби, знести поточні дані вбік (move-aside), розпакувати
архів, пройти post-verify — або служби не піднялися назад після відновлення.
Коди `41`/`42` називають конкретнішу причину (пошкоджений архів, невалідний
SHA512) і мають пріоритет над `43`.

**Що при цьому НЕ сталося.** Жоден файл не розпаковується поверх наявних
даних: ціль завжди щойно створений порожній каталог. Попередні дані
InPlace-відновлення зберігаються поруч як `<каталог>.prerestore_<timestamp>`
і **ніколи не видаляються автоматично**. Якщо збій стався на другому чи
третьому компоненті, вже відновлені компоненти цього прогону відкочуються
автоматично (статус `ВІДКОЧЕНО`) — production не лишається зі змішаними
generation.

**Чого не робити.** Не видаляйте `.prerestore_*` до того, як переконаєтесь у
працездатності LIMS: це єдина копія даних, які були до відновлення. Не
запускайте відновлення повторно «наосліп», не прочитавши причину в журналі —
якщо move-aside не вдався через відкриті файли, повтор дасть той самий
результат, доки процес-власник тримає каталог (його ім'я вже є в журналі
поруч із помилкою).

**Діагностика.**

```powershell
# Останній журнал відновлення
Get-ChildItem "<runtimeLogRoot>\BRAVO_DATA_RESTORE_*.log" |
    Sort-Object LastWriteTime | Select-Object -Last 1

# Які generation узагалі придатні (read-only, без елевації)
.\BRAVO_DATA_RESTORE.ps1 -ListGenerations -ConfigPath ".\BRAVO.config"

# Стан керованих служб
Get-Service | Where-Object { $_.Name -in @('<BravoName>', '<ExchangeApiName>') }
```

**Ескалація.** Невдалий rollback (`КРИТИЧНО: rollback не вдався` у журналі)
— S1: дані не втрачені, але production у проміжному стані й потребує ручного
повернення саме тією командою, яку надрукував журнал.

### Окремий випадок: процес перервано під час InPlace-відновлення

Kill процесу, перезавантаження або BSOD у момент InPlace-відновлення
лишають систему в проміжному стані: автоматичний відкат виконатися не встиг.

**Симптоми.**

- існує `<live-каталог>.prerestore_<timestamp>`, а сам live-каталог
  відсутній або порожній чи неповний;
- служби `BRAVO`, `exchangAPI`, `BravoWeb` зупинені й не піднімаються самі;
- у журналі відновлення немає рядка `Завершення з кодом`.

**Дані не втрачені**: `.prerestore_*` — це ваші попередні дані під іншим
іменем (перейменування каталогу, не копіювання).

**Повернення до стану перед відновленням.**

Порядок нижче навмисно розділений на перевірки й дію: `Remove-Item`
виконується **лише** після того, як ви на власні очі побачили, що
preserved-копія існує, а live-каталог справді неповний. Пропускати
перевірки не можна — саме `.prerestore_*` є єдиною копією ваших
попередніх даних.

Крок 0. Визначте компонент і потрібну копію за журналом перерваного
прогону: які компоненти вже оброблялися і які каталоги він рухав.

```powershell
$log = Get-ChildItem "<runtimeLogRoot>\BRAVO_DATA_RESTORE_*.log" |
    Sort-Object LastWriteTime | Select-Object -Last 1
Select-String -Path $log.FullName -Pattern 'знесено вбік|Відкат|Компонент .* відновлено'
```

Крок 1. Задайте шляхи одного компонента (повторіть процедуру для кожного,
який був у роботі) і **перевірте, що саме є на диску**. `$prerestore` —
ТОЧНЕ значення з рядка `Поточні дані знесено вбік: <live> -> <prerestore>`,
знайденого у журналі перерваного прогону в Кроці 0 (не вигадане/підставлене
ім'я):

```powershell
$live = "<live-каталог>"                                       # напр. D:\LIMS\MODEL
$prerestore = "<точний шлях .prerestore_* з рядка Кроку 0>"     # копія попередніх даних

Test-Path -LiteralPath $live
Test-Path -LiteralPath $prerestore
```

Крок 2. **Копія обов'язкова.** Якщо `$prerestore` не існує — зупиніться:
цей компонент не проходив move-aside, і видаляти щось у `$live` не можна.

```powershell
if (-not (Test-Path -LiteralPath $prerestore)) {
    Write-Host "ЗУПИНІТЬСЯ: preserved-копії немає, live чіпати не можна" -ForegroundColor Red
}
```

Крок 3. Порівняйте обсяг: неповний live від перерваного розпакування
зазвичай помітно менший за копію. Якщо live **більший або рівний**
prerestore — не видаляйте його, розберіться спершу (можливо, відновлення
встигло завершитись).

```powershell
$liveStats = if (Test-Path -LiteralPath $live) {
    Get-ChildItem -LiteralPath $live -Recurse -File -Force -ErrorAction SilentlyContinue |
        Measure-Object -Property Length -Sum
} else { $null }
$prerestoreStats = Get-ChildItem -LiteralPath $prerestore -Recurse -File -Force -ErrorAction SilentlyContinue |
    Measure-Object -Property Length -Sum

"live:       файлів $(if ($liveStats) { $liveStats.Count } else { 'каталогу немає' }), байтів $(if ($liveStats) { $liveStats.Sum } else { 0 })"
"prerestore: файлів $($prerestoreStats.Count), байтів $($prerestoreStats.Sum)"
```

Крок 4. Приберіть **тільки** неповний live — і лише якщо він існує. Якщо
каталогу немає, цей крок пропускається повністю (переходьте до кроку 5).

```powershell
if (Test-Path -LiteralPath $live) {
    Remove-Item -LiteralPath $live -Recurse -Force
}
```

Крок 5. Поверніть попередні дані під оригінальним іменем. `Rename-Item`
навмисно **не** перезаписує наявний каталог: якщо на цьому кроці ви
отримали помилку — значить, live ще існує, поверніться до кроку 3 і не
застосовуйте примусове переміщення.

```powershell
Rename-Item -LiteralPath $prerestore -NewName (Split-Path $live -Leaf)
```

Крок 6. Запустіть **лише ті** служби, чий залогований намір відновлення
(`restart-after-recovery`) дорівнює `YES` — **не** ті, що були буквально
`Running` на момент аварії. BRAVO примусово зупиняє (квієсценція) УСІ
керовані служби перед move-aside, незалежно від їхнього стану на момент
знімка, а не лише ті, що вже працювали. Поточна політика наміру
відновлення (`Get-BRAVODataRestoreServiceSnapshot`):

- `Running` на момент знімка → restart intent `YES`;
- `StartPending` на момент знімка → restart intent `YES` (служба ще
  тільки запускалась, але оператор мав намір, щоб вона працювала);
- `Stopped` / `StopPending` / `Paused` / `ContinuePending` /
  `PausePending` / будь-який інший стан → restart intent `NO`.

Точний запис для КОЖНОЇ керованої служби пишеться в журнал одразу після
знімка стану, ще ДО move-aside (саме тому доступний навіть якщо прогін
перервався до фінального автоматичного restart-кроку — kill/BSOD/
завершення PowerShell):

```powershell
Select-String -Path $log.FullName -Pattern 'Знімок служби'
# Приклад рядка:
#   Знімок служби BRAVO: initial=Running, restart-after-recovery=YES
#   Знімок служби ExchangeApi: initial=StartPending, restart-after-recovery=YES
#   Знімок служби BravoWeb: initial=Stopped, restart-after-recovery=NO
```

Використовуйте **виключно** запис саме цього перерваного прогону (той
самий лог-файл, що й Крок 0/`$prerestore`) — так само, як для вибору
`.prerestore_*`-копії, ніколи не вгадуйте намір відновлення за поточним
станом служб після перезавантаження/аварії: він міг змінитися незалежно
від того, що BRAVO мала намір відновити. Якщо очікуваний запис "Знімок
служби" відсутній або неповний (наприклад, прогін перервався ще до
знімка стану служб) — **зупиніться** і розберіться вручну, не
запускайте служби навмання.

```powershell
# Поточний стан для порівняння (включно з BravoWeb, якщо вона керована —
# Get-BRAVODataRestoreServiceSnapshot зупиняє й відновлює її так само, як
# BRAVO і exchangAPI, коли BravoWebEnabled увімкнено в конфігурації):
Get-Service '<BravoName>', '<ExchangeApiName>', '<BravoWebName>' | Select-Object Name, Status, StartType

# Запускати у зворотному до зупинки порядку (canonical: BRAVO -> exchangAPI
# -> BravoWeb, той самий порядок, що Restore-BRAVODataRestoreServices
# застосовує автоматично) і ТІЛЬКИ ті, у яких restart-after-recovery=YES
# у знайденому запису:
Start-Service '<BravoName>'
Start-Service '<ExchangeApiName>'
Start-Service '<BravoWebName>'
```

Служба з `restart-after-recovery=NO` має залишитися зупиненою — її
стан не є наслідком аварії. Службу зі `StartType = Disabled` не
намагайтеся піднімати: її відключив адміністратор, і `Start-Service`
все одно завершиться помилкою.

Крок 7. Перевірте систему:

```powershell
.\BRAVO_HEALTH.ps1 -ConfigPath ".\BRAVO.config" -NoPause
```

**Якщо `.prerestore_*` кілька (від різних спроб) — НІКОЛИ не беріть
найстаріший чи найновіший "за замовчуванням".** Приклад, чому це небезпечно:
успішне відновлення №1 лишає `.prerestore_t1`; пізніше відновлення №2
створює `.prerestore_t2` і саме воно переривається. Production
безпосередньо перед перериванням — це стан, знесений у `.prerestore_t2`,
а не `.prerestore_t1`: узявши найстаріший `t1`, ви відкотите компонент на
ОДНУ generation далі, ніж треба, а для кількох компонентів так можна
отримати змішаний набір generation (MODEL з однієї, BLOG з іншої).

Timestamp у назві — лише допоміжний доказ, не самостійний алгоритм вибору.
Єдине правильне джерело — рядок `Поточні дані знесено вбік: <live> ->
<prerestore>` у журналі САМЕ ТОГО перерваного прогону (Крок 0). Якщо
журнал не дає однозначної відповіді, ЯКА копія належить перерваному
прогону, — **зупиніться й розберіться вручну**, не вгадуйте.

**Ніколи не видаляйте `.prerestore_*` під час цієї процедури.** Після
успішного кроку 5 копія перестає існувати під старим іменем сама (її
перейменовано назад у live). Видаляти вручну можна лише зайві копії
попередніх спроб — і лише після того, як LIMS підтверджено працює.

Повторне відновлення запускайте лише після того, як система повернулась у
відомий стан і причину переривання усунуто.

## `50` — помилка SFTP

**Симптом.** Один із незалежних етапів `SFTP: резервні копії`,
`SFTP: BAZA_APP`, `SFTP: BAZA_WWW` має `ERROR` або `WARNING`.

**Що означає.** З'єднання, автентифікація або передача не вдались.
Локальний архів при цьому вже створено.

**Чого не робити.** **Не змінюйте `sftpHostKey`, щоб «запрацювало».**
Невідповідність fingerprint — це або зміна ключа сервера (тоді її має
підтвердити адміністратор SFTP окремим каналом), або
man-in-the-middle. Підганяння значення під те, що прийшло по мережі,
знімає єдиний захист від другого сценарію.

**Діагностика.**

```powershell
Test-NetConnection -ComputerName <sftp-host> -Port 22
.\BRAVO_TASKS_DIAGNOSE.ps1 -ConfigPath ".\BRAVO.config" -TestAccess
```

**Розвилка.**

| Симптом | Дія |
|---|---|
| `Цей хост невідомий` / `host unknown` | DNS: ім'я SFTP-хоста не резолвиться — див. нижче |
| порт 22 недоступний | мережа/файрвол, SFTP не винен |
| автентифікація відхилена | `31`-процедура для credentials |
| **fingerprint не збігається** | **зупиніться.** Підтвердьте новий ключ у адміністратора SFTP голосом або іншим каналом; лише після цього оновіть `sftpHostKey` |

**Ескалація.** Непідтверджена зміна fingerprint — S1.

### Окремий випадок: `Цей хост невідомий` (host unknown)

Це не автентифікація й не файрвол, а **невдале розв'язання імені**.

Ім'я SFTP-хоста BRAVO не бере з конфігурації напряму: воно будується з
логіна (`BRAVO_SFTP_LOGIN`) і шаблону (`sftpHostTemplate`) —
`Resolve-BRAVOSftpHostName`. Тому найчастіша причина — не мережа, а
помилка в логіні або шаблоні.

```powershell
# Ім'я, яке фактично складається
$login = Get-BRAVOCredentialSecret -Target 'BRAVO_SFTP_LOGIN'
Resolve-DnsName ($sftpHostTemplate -f $login)
```

**Перевірте спершу, чи це взагалі мережа.** Якщо тестове сповіщення
проходить (`BRAVO_DRY_RUN.ps1 -SendTestNotification` дає HTTP 204), а
SFTP-хост не резолвиться — інтернет і DNS працюють, і справа саме в
імені хоста.

## `51` — помилка SMB/NAS

**Симптом.** Секція `КОПІЮВАННЯ АРХІВІВ НА NAS/SMB`.

**Що означає.** UNC-шлях недоступний або облікові дані відхилені —
зазвичай саме **від `SYSTEM`**, тоді як вручну шлях відкривається.

**Діагностика.**

```powershell
.\BRAVO_TASKS_DIAGNOSE.ps1 -ConfigPath ".\BRAVO.config" -TestAccess
```

Перевіряє доступ саме від `SYSTEM`, а не від вашого облікового запису —
це і є суть проблеми в більшості випадків.

**Ескалація.** S2. Локальні копії й SFTP при цьому працюють, тож
критичної втрати немає.

## Глобальні вимикачі зовнішніх сховищ і local-only режим (5.2.2)

**Що це.** `componentSettings.SFTP.Enabled` і `componentSettings.SMB.Enabled` —
головні вимикачі відповідного destination. `$false` вимикає ВСІ
автоматичні мережеві операції (архіви, BAZA-синхронізацію,
Health-моніторинг, `BRAVO_DRY_RUN.ps1` проби) і знімає вимогу
креденшелів — дочірні прапорці (`ArchiveUpload`, `ArchiveCopy`,
`BAZA_*_SFTP`) при цьому НЕ змінюються: `Enabled = $true` відновлює
попередню поведінку без повторного налаштування дочірніх флагів.
Відсутній ключ (конфіг 5.2.1 і старіші) трактується як `$true` —
оновлення саме по собі не змінює поведінку.

**Коли використовувати.**

| Сценарій | Override |
|---|---|
| Сервер без SFTP | `componentSettings.SFTP.Enabled = $false` |
| Сервер без SMB/Samba/NAS | `componentSettings.SMB.Enabled = $false` |
| Local-only сервер | обидва `= $false` — **валідна production-конфігурація** |

Задавайте через `BRAVO.local.config` (приклад — `BRAVO.local.config.example`).

**Що продовжує працювати в local-only режимі:** локальна архівація
`MODEL`/`BLOG`/`BRAVOEXCH`, локальна BAZA, службовий Health, локальний
backup Health, notifications. Scheduled завдання
`BRAVO BAZA Synchronization` не реєструється (installer вважає це
валідним DISABLED-станом, diagnose — `[SKIP]`).

**Що лишається доступним попри вимикач** (операторська дія, не
автоматика): `BRAVO_DATA_RESTORE.ps1 -Source SFTP` (disaster recovery),
`BRAVO_BAZA_RECONCILE.ps1`, явне додавання SFTP/SMB-креденшелів через
`BRAVO_CREDENTIALS_SETUP.ps1`.

**Manual `-SyncBAZA` при `SFTP.Enabled = $false`:**
`BRAVO_ARCHIV.ps1 -SyncBAZA` завершується чистим `SKIPPED`, `ExitCode = 0`,
без жодного звернення до Credential Manager чи WinSCP.

**Обмеження — читайте уважно.** `componentSettings.SMB.Enabled = $false`
**не** блокує UNC-шляхи в `pathSettings` (наприклад, якщо `BackupRoot`
явно вказаний як `\\server\share\...`) — це окремий, не пов'язаний з
`componentSettings.SMB` механізм валідації шляхів. Якщо потрібен
справжній local-only без будь-якого мережевого шляху, переконайтесь, що
`pathSettings.BackupRoot`/`LIMSRoot`/`SystemLogRoot` теж локальні.

**Ескалація.** Не застосовно — це конфігураційне рішення оператора, не
збій. `Health`/`Dry Run` рендерять явний PASS/SKIPPED з причиною
(`componentSettings.SFTP.Enabled = $false` / `SMB.Enabled = $false`),
не WARNING і не ERROR.

## Профілі реставрації: 24/7 vs сервер робочого часу

Планова реставрація моделі (`Restore.Day`/`Restore.Time`, типово нд
03:00) обмежена вікном `Restore.WindowStart–WindowEnd` (типово
21:00–03:00). Пропущений слот (сервер був вимкнений) підхоплюється
за профілем `maintenanceSettings.Restore.BootRestoreMode`:

**`"None"` (default) — сервер 24/7.** Recovery-завдання не
реєструється (наявне вимикається інсталятором). Пропущену реставрацію
виконує наступний плановий `BRAVO_MAINTENANCE` (23:55) у межах вікна.
Слідкуйте, щоб `Maintenance.DailyAt` лишався всередині вікна
реставрації — на цьому профілі це єдиний автоматичний шлях.

**`"HoldServices"` — сервер робочого часу** (вимикається ввечері й
нічного вікна ніколи не бачить). Інсталятор Планувальника:
1. переводить служби BRAVO/exchangAPI на **Automatic (Delayed
   Start)** (канонічна функція `Set-BRAVOBootRestoreServiceStartType`,
   модуль BRAVO.System; Manual/Disabled не чіпаються);
2. реєструє `BRAVO_RESTORE_RECOVERY` з одним boot-тригером
   (затримка 0, без repetition).

При старті сервера Recovery запускається РАНІШЕ за відкладені служби,
і якщо є пропущений слот — виконує реставрацію **поза вікном**,
утримуючи служби зупиненими (клієнти не встигають зайти в програму до
заміни моделі), після чого запускає їх. Fail-open: якщо задача не
відпрацювала, служби стартують самі (delayed auto) — доступність LIMS
важливіша, спроба повториться наступним стартом. Перезавантаження
серед робочого дня з pending-реставрацією додасть ~10 хв простою
одразу після нього — свідома поведінка.

Під час boot-реставрації плановий `BRAVO_HEALTH` (запускається з
`-SkipIfBackupTaskRunning`) побачить зайнятий `BRAVO_OPERATION.lock` і
завершиться як `Deferred` — це нормально. Ручний запуск
`BRAVO_HEALTH.ps1` БЕЗ цього прапорця у ті хвилини чесно поскаржиться
на зупинені служби — дочекайтесь завершення Recovery.

До 5.2.0 Recovery мав daily-тригер о `WindowStart` (пропущена
реставрація виконувалась о 21:00, а не у планове 23:55) і
boot-repetition кожні 15 хв протягом 8 год (будив завдання вхолосту
ще довго після успішної реставрації — інцидент на сервері BRAVO 2026-08-20). Обидва
механізми прибрано.

## BAZA: incremental append-only синхронізація

`BAZA_APP`/`BAZA_WWW` — окремий вид навантаження порівняно з рештою
BRAVO: накопичувальний каталог (>50 ГБ, сотні тисяч файлів), файли
ніколи не змінюються після появи, лише додаються, а на SFTP `-delete`
заборонено назавжди. Повне порівняння дерева (`synchronize
remote`/`-preview`) на кожному циклі для такого обсягу — сама вартість
операції listing/stat/compare, а не переданих байтів, і вона ж була
джерелом false-positive Health-алертів на легітимно нові файли.
`backupMonitoring.SFTP.BAZA.Mode = "IncrementalAppendOnly"` (типово)
вмикає інший двигун — `BRAVO.BazaSync` (окремий модуль,
`modules\BRAVO.BazaSync\`), який Archive і Health використовують
спільно. `Mode` = будь-яке інше значення (напр. `"Legacy"`) повністю
вимикає новий двигун і повертає старий шлях без жодної зміни поведінки.

### Sync Cycle і Cutoff

Кожен цикл синхронізації має власний `CycleId`
(`20260813_120000_a17f`) і **Cutoff** — момент, коли синхронізація
зняла знімок локального каталогу. Файли, присутні в цьому знімку,
належать поточному циклу; файли, що з'явились ПІСЛЯ (навіть через
секунду після завершення sync), — це `NewAfterCutoff`, і вони
**завжди INFO, ніколи alert**: вони належать наступному циклу, а не є
помилкою поточного. Членство в cutoff визначається **знімком циклу**
(перелік шляхів, побачених на момент cutoff), а не persisted state і не
`LastWriteTime`: pre-cutoff кандидат, свідомо не записаний у state
(несумісне ім'я, remote-конфлікт, audit-drift), — НЕ «новий після
cutoff»; а файл, доданий після знімка зі старою датою модифікації
(backdated), — рахується. Головний інваріант: `SYNC -> VERIFY -> HEALTH
RESULT` — Health оцінює результат КОНКРЕТНОГО завершеного циклу, а не
довільний стан каталогу «просто зараз».

### Fast Health проти Full Audit

- **Fast Health** виконується на кожному звичайному циклі: оцінює вже
  готовий `SyncResult` (статус циклу, `pendingWithinCutoff`, `failed`,
  результат публікації checkpoint, збій періодичного Full Audit) —
  жодного нового SFTP-порівняння дерева. Оцінка працює за **success
  whitelist**: нормальний здоровий результат можливий **лише** для
  `Status=COMPLETE`; `INCOMPLETE` (напр. збій запису стану після
  успішних передач), `ERROR`, `STATE_INVALID`, `STATE_NOT_INITIALIZED`,
  `MUTATION_VIOLATION`, `INCOMPATIBLE_NAME`, `REMOTE_CONFLICT`,
  `AUDIT_DRIFT`, `RECONCILIATION_REQUIRED` і будь-який
  невідомий/майбутній статус — завжди unhealthy (fail visible, не fail
  open). Якщо в одному циклі
  співіснують кілька категорій проблем (мутації, audit-drift,
  remote-конфлікти, несумісні імена) — одна визначає Status/Message, а
  решта видимі в Info того самого прогону.
- **Full Audit** — окрема дорога реконсиляція: повне порівняння
  локального й віддаленого дерева (та сама вже наявна
  `Get-BAZASFTPComparison`/WinSCP `CompareDirectories`, що й раніше —
  двигун не дублює цю логіку, лише повторно використовує її). Full
  Audit виконується на **першому запуску** (bootstrap — нижче) і
  періодично, кожні `BAZA.FullAuditEveryDays` днів (типово 7), **а не
  на кожному циклі**. Він ловить дрейф, якого incremental-план
  структурно не бачить — наприклад, файл, підтверджений раніше
  (`Verified=true`), але хтось вручну видалив його на SFTP: Full Audit
  виявляє це й позначає файл на повторну передачу.

  **Збій періодичного Full Audit не зникає мовчки.** Якщо плановий
  аудит не вдався (наприклад, обірвалось з'єднання), incremental sync
  цього циклу все одно виконується і файли передаються, але
  `SyncResult` несе `FullAuditAttempted=true`/`FullAuditSucceeded=false`/
  `FullAuditError`, а Fast Health підіймає щонайменше **WARNING** —
  «синхронізовано, але періодична повна верифікація не відбулась»
  ніколи не рапортується як «все повністю верифіковано». `LastFullAuditUtc`
  при цьому лишається старим, тож наступний цикл спробує аудит знову.

### Де зберігається стан

`%ProgramData%\BRAVO\State\BAZA\<Component>.state.json` (шлях
конфігурується через `BAZA.StateRoot`; корінь спільний з рештою
persisted state BRAVO). Для кожного вже переданого файлу зберігається
`RelativePath`/`Size`/`LastWriteTimeUtc`/`UploadedUtc`/`Verified`.
**Це НЕ Durable Operation Journal** — вузькоспеціальний індекс лише
для BAZA-синхронізації, окремий механізм. Файли з `Verified=true` і
незмінним локальним розміром пропускаються без жодного звернення до
SFTP (`AlreadyVerified` у звіті) — саме це і прибирає O(усі файли)
вартість. `LastWriteTime` — лише допоміжний сигнал, ніколи не єдине
джерело істини: новий файл зі старим `LastWriteTime` (перенесений,
відновлений з бекапу) все одно підхоплюється, бо рішення "новий чи ні"
базується на присутності в state, а не на таймстемпі.

### Bootstrap (перший запуск)

На production SFTP вже може лежати >50 ГБ. Перший запуск нового
двигуна **не перезавантажує все заново**: виконує один Full Audit,
позначає вже наявні на SFTP файли як `Verified=true` без жодного
upload, і лише тоді переходить до звичайного incremental-плану.
Bootstrap — **виключна відповідальність `BRAVO_ARCHIV`** (він завжди
виконується першим за розкладом). Якщо `BRAVO_HEALTH.ps1` запущено
самостійно, а стану ще немає (Archive жодного разу не запускався),
синхронізація зупиняється **до** побудови плану з контрольованим
`Status=STATE_NOT_INITIALIZED` і **нульовою** кількістю передач:
standalone Health ніколи не трактує «стану ще немає» як «всі локальні
файли нові» і не намагається залити 50+ ГБ сам. Health-повідомлення
прямо каже: incremental стан не ініціалізовано, спершу виконайте
bootstrap через `BRAVO_ARCHIV`.

### Мутації (append-only invariant)

Якщо у локального файлу, вже позначеного `Verified=true`, змінився
**розмір або `LastWriteTimeUtc`** — це порушення append-only
інваріанта (перезапис тим самим обсягом, але з новим часом модифікації,
теж рахується). Типова політика `BAZA.MutationPolicy = "Fail"`: файл
**не** перезаписується на SFTP мовчки, синхронізація цього циклу
отримує `Status=MUTATION_VIOLATION`, Health підіймає CRITICAL з іменем
файлу; попередні/поточні розмір і час модифікації — у
`MutationViolations`. Це **не** timestamp-only discovery: шлях,
відсутній у state, — завжди НОВИЙ файл і передається незалежно від
того, який у нього timestamp.
Це майже завжди означає, що якийсь процес поза BRAVO модифікує файли в
каталозі BAZA_APP/BAZA_WWW — знайдіть його, перш ніж щось міняти в
конфігурації.

#### Розв'язання мутацій (BRAVO_BAZA_RECONCILE)

Коли заміна файлів виявилась **легітимною** (типовий випадок: документи
перегенеровано самим застосунком BRAVO — реальний інцидент 2026-08-21,
5 ЗВТ-PDF у BAZA_APP), розв'язання виконується одним інструментом:

    BRAVO_BAZA_RECONCILE.ps1 -Component BAZA_APP -ListOnly
    BRAVO_BAZA_RECONCILE.ps1 -Component BAZA_APP -Accept 'Eqv\ЗВТ_11-116.pdf','Eqv\ЗВТ_11-117.pdf'
    BRAVO_BAZA_RECONCILE.ps1 -Component BAZA_APP -AcceptAll   # запитає підтвердження RECONCILE

Для кожного прийнятого файлу інструмент: (1) перейменовує СТАРУ версію на
SFTP у `<ім'я>.replaced_<дата>` (нічого не видаляє; історію додатково
тримають снапшоти сховища), (2) прибирає запис зі стану атомарним записом
модуля. НОВУ версію заллє наступний плановий цикл `BRAVO_ARCHIV`;
контроль — ранковий Health. Збій rename лишає state неторкнутим
(fail-closed) — просто повторіть команду.

**Перевірка легітимності перед прийняттям.** Якщо заміна йшла через
застосунок, у `TraceSRV.out` (поруч із `bravo.exe`) буде повний слід:
шукайте за ASCII-частиною імені (`Select-String -Path <BRAVO_ROOT>\TraceSRV.out
-Pattern '11-116'`); сума байтів послідовних `sp_filewrite` дорівнює
розміру нового локального файлу, а `getdef` по номеру сесії (`>N ...`)
ідентифікує співробітника. Жодного сліду в трейсі при зміненому файлі =
модифікація повз застосунок — розберіться, хто пише в BAZA, перш ніж
приймати.

**Ручний fallback** (без інструмента) — уроки інциденту, які легко
наступити повторно:

- `Files` у `<Component>.state.json` — **hashtable за RelativePath**, не
  масив: шукайте через `$state.Files.PSObject.Properties['Eqv\ім''я.pdf']`.
- Читання/запис стану — **лише** `[IO.File]::ReadAllText/WriteAllText` з
  UTF-8 (без BOM): голий `Get-Content -Raw` у PS 5.1 читає ANSI і мовчки
  калічить кирилицю в ключах, а `Set-Content` записує це назад.
- **Просто видалити ключ недостатньо**: наступний цикл побачить «новий»
  файл, а remote-шлях зайнятий іншим розміром → `REMOTE_CONFLICT` (той
  самий блок під іншим ім'ям). Спершу приберіть/перейменуйте стару
  remote-версію, потім видаляйте ключ.
- Автоматична політика перезапису (`MutationPolicy` ≠ `Fail`) свідомо НЕ
  підтримується: вона б дозволила ransomware/пошкодженим файлам мовчки
  поширитись у хмару. Рішення завжди за оператором.

#### Опційне поріг-based авто-архівування (масштаб: багато незалежних майданчиків)

Для розгортань із великою кількістю незалежних майданчиків клієнтів (кожен
LIMS у своїй мережі, без вхідного доступу для централізованого керування)
ручний обхід кожного сервера при кожній append-only мутації не
масштабується. `backupMonitoring.SFTP.BAZA.AutoArchiveMutationThreshold`
(`BRAVO.config`) задає поріг: **типове значення комплекту — `25`**
(свідоме рішення власника розгортання, 2026-08-27, після реального
інциденту ДНДІЛДВСЕ з 18 легітимними мутаціями; `0` = вимкнено, жорсткий
блок на будь-яку мутацію). Якщо мутацій за **один цикл на компонент** не
більше `N`,
синхронізація автоматично виконує ту саму rename-preserve операцію, що й
`BRAVO_BAZA_RECONCILE.ps1 -AcceptAll` (стара remote-версія →
`<ім'я>.replaced_<дата>`, нічого не видаляється, стан очищається, нову
версію заливає наступний плановий цикл) — **без** підтвердження оператора
для кожного циклу. `SyncResult.Status = 'MUTATION_AUTO_ARCHIVED'`, Health
показує це як **інформаційне** повідомлення (не CRITICAL, не "ПОТРІБНА
ДІЯ").

Понад поріг `N` за один цикл — поведінка **не змінюється**: жорсткий
блок, `MUTATION_VIOLATION`, CRITICAL, ручний `BRAVO_BAZA_RECONCILE.ps1`, як
і без цієї опції. Часткова невдача rename під час авто-архівування також
fail-closed: нерозв'язані шляхи лишаються заблокованими.

**Свідомо прийнятий ризик**, зафіксований тут, а не прихований: немає
додаткового сукупного добового/тижневого ліміту — лише per-cycle поріг.
Теоретично зловмисник міг би обходити поріг, змінюючи ≤N файлів за цикл
багато циклів поспіль. Компенсуючі фактори: rename-not-delete (стара
версія завжди відновна), Health і далі повідомляє про КОЖНЕ
авто-архівування (не тихо — оператор бачить постфактум), і будь-який
сплеск понад `N`/цикл і далі жорстко блокується. Див. `THREAT_MODEL.md`.

Вмикайте це значення свідомо, з урахуванням реального масштабу легітимних
змін на конкретному майданчику (орієнтир: реальний інцидент 21.08.2026 —
5 файлів за цикл через перегенерацію документів застосунком).

### Health синхронізує BAZA перед перевіркою

Якщо `BRAVO_ARCHIV` щойно виконав BAZA sync у цьому ж прогоні, він
передає готовий `SyncResult` вбудованому Health — повторної
синхронізації не відбувається (`ONE synchronization, ONE SyncResult`).
Якщо `BRAVO_HEALTH.ps1` запущено самостійно і свіжого результату
немає — Health спершу сам виконує один incremental sync, і лише тоді
оцінює здоров'я. Ніколи навпаки: "прочитати каталог -> побачити нові
файли -> alert".

Для `Mode = "IncrementalAppendOnly"` sync-перед-перевіркою і Fast
Health — **обов'язкові інваріанти режиму, а не опції**:
`BAZA.SynchronizeBeforeHealth = $false` або `BAZA.FastHealthEnabled =
$false` при цьому режимі **відхиляються на етапі валідації
конфігурації** з явною помилкою (немає підтримуваного «гібрида» —
incremental sync, але повний 50+ ГБ preview на Health). Стара поведінка
доступна лише явно: `BAZA.Mode = "Legacy"`.

### Remote checkpoint (`.bravo-sync.json`)

Після успішного циклу двигун публікує на SFTP поруч із даними невеликий
checkpoint-файл `.bravo-sync.json` (CycleId, час, підсумки циклу). Це
**write-only телеметрія для зовнішнього спостерігача** (оператор бачить
на SFTP-боці, коли завершився останній цикл): production Health його
**не читає назад** і не будує на ньому freshness-перевірок — здоров'я
оцінюється за локальним `SyncResult`/persisted state. Публікація —
через тимчасове remote-ім'я (`.bravo-sync.json.tmp-<guid>`) з
подальшою **явною заміною**: якщо канонічний checkpoint попереднього
циклу вже існує, він видаляється, і тимчасовий файл перейменовується на
канонічне ім'я (SFTP-rename переносимо не гарантує перезапису наявної
цілі, тому на rename-overwrite двигун не покладається). Заміна
**не атомарна** — у вузькому вікні між видаленням і перейменуванням
читач може побачити checkpoint **відсутнім**; **частково записаним** він
не буває ніколи (вміст завжди спершу повністю лягає під тимчасовим
іменем). Для write-only телеметрії це прийнятний компроміс — сильніших
гарантій generic SFTP не дає. Результат публікації видимий у
`SyncResult` (`CheckpointAttempted`/`CheckpointPublished`/`CheckpointError`);
результат видалення попереднього checkpoint теж перевіряється (WinSCP
репортує такий збій без винятку — якщо видалення не вдалося, заміна
чесно рапортується як неопублікована, старий checkpoint лишається
цілим). Збій публікації при успішному циклі — **WARNING** (самі дані в
безпеці, несправна лише телеметрія), не CRITICAL.

### Remote-шлях кандидата вже зайнятий (`REMOTE_CONFLICT`)

Перед кожною передачею двигун цільово перевіряє, чи remote-шлях самого
кандидата вже існує (WinSCP типово **перезаписує** наявні файли — без
цієї перевірки кандидат, чий шлях зайнятий, мовчки затер би immutable
BAZA-файл). Перевірка стосується **лише** кандидатів на передачу —
для сотень тисяч уже Verified файлів жодних remote-звернень не
додається.

- **Remote-файл існує з тим самим розміром** — типове crash-вікно:
  попередній цикл встиг передати файл, але впав до збереження стану.
  Кандидат визнається вже присутнім (`RecoveredRemote` у звіті),
  позначається `Verified=true` **без** повторної передачі й без
  перезапису; цикл може завершитись `COMPLETE` штатно.
- **Remote-файл існує з іншим розміром** — `Status=REMOTE_CONFLICT`:
  передача цього кандидата не виконується (нуль PutFiles), перезапис
  заборонено append-only контрактом завжди — окремої «overwrite»-опції
  навмисно немає; якщо колись знадобиться, це має бути явно названа
  операторська політика, а не тихий default. Provenance успішного циклу
  (`LastCycleId`/`LastSuccessfulSyncUtc`) не просувається, «успішний»
  checkpoint не публікується, Health — CRITICAL з точним відносним
  шляхом і обома розмірами (local/remote). Оператор мусить розібратись,
  звідки на SFTP взявся файл іншого розміру, перш ніж щось міняти.
- **Кандидат явно позначений pending Full Audit-ом** (bootstrap,
  плановий, `-ForceFullAudit` або corrupt-реконсиляція) — same-size
  recovery для нього **вимкнено**: audit порівнює за `time,size` і його
  вердикт «не збігається» (напр. `UploadUpdate`: той самий розмір,
  інший mtime) не можна мовчки скасувати збігом лише розміру. Якщо
  remote-шлях такого кандидата зайнятий — `Status=AUDIT_DRIFT` (нуль
  PutFiles, без перезапису, provenance не просувається, checkpoint не
  публікується, Health — CRITICAL з шляхом, audit `Action` і обома
  розмірами); якщо remote-шлях вільний — звичайна передача з
  верифікацією. Вердикт **стійкий між циклами**: у state-записі шляху
  персистується мінімальний блокер (`BlockReason="AuditDrift"` +
  `AuditAction`/`AuditReason`/`AuditDetectedUtc`, первинна дата
  виявлення зберігається), тому й наступні звичайні цикли БЕЗ власного
  аудиту лишаються `AUDIT_DRIFT` — жодного false-green вікна до
  наступного планового аудиту. Блокер знімається **лише позитивною
  розв'язкою**: (A) пізніший Full Audit підтвердив збіг —
  `Verified=true`, блокер зникає; або (B) remote-файл прибрано —
  звичайна цільова передача з верифікацією, `Verified=true`. Збіг
  розміру блокер не знімає ніколи — саме цей доказ audit уже визнав
  недостатнім. **Зникнення локального джерела — теж не розв'язка**:
  заблокований шлях, що зник з локального каталогу, все одно виринає
  щоциклу як `AUDIT_DRIFT` з позначкою «локальне джерело відсутнє»
  (цикл не COMPLETE, Health CRITICAL), а пізніший Full Audit не знімає
  такий блокер мовчки — розбіжність мусить вирішити оператор. Звичайні
  unverified/pending записи (без блокера) зберігають повну round-3
  crash-recovery семантику.
  `LastFullAuditUtc` при `AUDIT_DRIFT` просувається (audit **успішно**
  завершився і виявив дрейф) — це свіжість аудиту, НЕ успішність
  синхронізації (`LastSuccessfulSyncUtc` не просувається).

**Write-ahead маркер Full Audit (`RECONCILIATION_REQUIRED`).** Перед
кожним Full Audit (bootstrap чи періодичним) у файл стану атомарно
записується маркер `AuditReconciliationPending=true`; якщо цей запис не
вдався — audit **не запускається** (контрольований ERROR). Маркер
знімається лише разом з успішним **фінальним** збереженням стану після
інтеграції результатів. Тому crash або збій запису МІЖ аудитом і
фінальним збереженням не може «забути» вердикт: на диску лишається
маркер, і наступний standalone Health відмовляється fail-closed
(`Status=RECONCILIATION_REQUIRED`, CRITICAL, нуль передач, нуль
TrustedSkip старих Verified-записів), а наступний прогін `BRAVO_ARCHIV`
примусово повторює Full Audit-реконсиляцію. Звичайних (без аудиту)
циклів маркер не стосується — їхній збій збереження безпечний
(INCOMPLETE: зайва повторна робота, не втрачена довіра). Це вузький
маркер trust-переходу в state одного компонента, **не** Durable
Operation Journal.

**Один writer на remote root.** Пара `FileExists → PutFiles` — не
розподілена атомарна операція, а lock BAZA-синхронізації — machine-wide
(файловий lock на цьому сервері), не SFTP-server-wide. Режим
`IncrementalAppendOnly` розрахований на **рівно одного writer-а для
кожного керованого BAZA remote root** (штатна конфігурація BRAVO саме
така: один сервер обслуговує свій компонент). Перевірка існування
повторюється безпосередньо перед PutFiles (після підготовки
remote-каталогів), що звужує TOCTOU-вікно до мінімуму, але це
**не** абсолютна розподілена гарантія «ніколи не перезапише» при двох
незалежних writer-ах з різних машин — такої гарантії generic SFTP не
дає.

### Несумісні з SFTP імена файлів

Інкрементальний шлях перевіряє кожного кандидата на передачу тим самим
правилом (і тими самими лімітами), що й legacy-двигун
(`Get-BAZARemoteNameCompatibilityIssues`): ім'я **файлу** понад
**246** UTF-8 **байтів** (не символів — кирилиця рахується по 2 байти)
або сегмент **каталогу** понад **255** байтів несумісні з
SFTP-сервером. 246, а не 255, для файлів — тому що цільовий upload явно
вмикає WinSCP resume (`TransferOptions.ResumeSupport.State = On`, та
сама легасі-семантика `-resumesupport=on`), а resume додає до
тимчасового імені `.filepart` — 9 байт: ім'я на 247–255 байт пройшло б
перевірку і впало б уже під час передачі. Такий файл **не** передається
і **не** потрапляє в state як verified; він з'являється в
`SyncResult.IncompatibleFiles` з точним відносним шляхом і причиною,
цикл завершується явним `Status=INCOMPATIBLE_NAME` — **не** COMPLETE:
`LastSuccessfulSyncUtc` не просувається і «успішний» checkpoint не
публікується (сумісні файли того ж циклу при цьому передаються й
комітяться в state як зазвичай), а Health підіймає CRITICAL з іменем
проблемного файлу. Перевірка суто локальна (O(нові кандидати)) —
жодного сканування remote-дерева і жодних повторних remote-викликів на
несумісний файл.

### Стан пошкоджено або несумісний

`Status=STATE_INVALID` (файл стану пошкоджений JSON, порожній, або
`SchemaVersion` не підтримується) — старі файли **ніколи** не
вважаються автоматично verified. Поведінка залежить від того, хто
натрапив на пошкодження:

- **Standalone Health** (без права на відновлення): негайний
  `STATE_INVALID`, нуль передач, alert. Пошкоджений файл лишається на
  місці незайманим — це доказ для розслідування.
- **`BRAVO_ARCHIV`** (явна авторизація на реконсиляцію): наступний
  прогін Archive виконує контрольоване відновлення — спершу Full
  Audit; **лише якщо аудит вдався**, пошкоджений файл переноситься в
  карантин поруч (`<Component>.state.corrupt.<timestamp>.json`), свіжий
  стан будується **виключно** з результату аудиту (вже наявні на SFTP
  файли — `Verified=true` без повторної передачі), і догружаються лише
  файли, яких на SFTP бракує. Якщо Full Audit провалився — пошкоджений
  файл лишається незайманим, жоден файл не отримує довіру, масової
  передачі немає, цикл чесно завершується `STATE_INVALID`.

Це навмисно контрольована відмова, а не спроба вгадати.

### Одночасний запуск (`SKIPPED_CONCURRENT`)

Основний захист від паралельного BAZA sync — `SkipIfBackupTaskRunning`
(типово увімкнено для розкладу Health: якщо `BRAVO_ARCHIV`/Maintenance
тримають `BRAVO_OPERATION.lock`, Health відкладається повністю).
Додатковий, безумовний рубіж — файловий lock per-компонент
(`<StateRoot>\BAZA\<Component>.sync.lock`): якщо інший процес саме
зараз синхронізує той самий компонент (напр. ручний запуск
`BRAVO_HEALTH.ps1` без `-SkipIfBackupTaskRunning` під час роботи
Archive), другий запуск не чекає й не дублює передачу — повертає
`Status=SKIPPED_CONCURRENT`.

«Інший процес зараз працює» — **не доказ актуальності хмарної копії**,
тому Health оцінює `SKIPPED_CONCURRENT` за свіжістю останнього
успішного циклу (`LastSuccessfulSyncUtc` з persisted state): якщо
успішний цикл був нещодавно (у межах 24 год) — `INFO`/healthy
(deferred, система активно працює); якщо давно або жодного успішного
циклу ще не було — **WARNING** з явним поясненням, що стан хмарної
копії цим циклом не підтверджено. Штатне повідомлення «хмарна копія
актуальна» для `SKIPPED_CONCURRENT` не видається ніколи.

Lock розрізняє **contention** і **інфраструктурний збій**: лише
справжня sharing violation (файл утримує інший процес) дає
`SKIPPED_CONCURRENT`; відмова в доступі (ACL/readonly), неможливість
створити каталог стану, невалідний шлях чи інший I/O-збій — це
`Status=ERROR` і Health-issue, а не «хтось інший синхронізує».

**Ескалація.** `STATE_INVALID`/`MUTATION_VIOLATION` — S2 (потребує
уваги оператора, копії при цьому не втрачені). `STATE_NOT_INITIALIZED`
на standalone Health — виконайте/дочекайтесь `BRAVO_ARCHIV` (bootstrap);
якщо Archive виконувався, а статус не зник — S2. Несумісне ім'я файлу
(`IncompatibleFiles`) — S2: файл не резервується, доки його не
перейменують. `REMOTE_CONFLICT` — S2: на SFTP лежить файл того самого
шляху, але іншого розміру; з'ясуйте походження, файл не перезаписується
автоматично ніколи. `AUDIT_DRIFT` — S2: Full Audit явно позначив файл
як розбіжний (напр. інший mtime при тому самому розмірі), а його
remote-шлях зайнятий; блокер персистентний — КОЖЕН наступний цикл
лишатиметься CRITICAL, доки розбіжність не вирішено вручну (прибрати
remote-файл або досягти підтвердження наступним аудитом).
Lock `ERROR` (ACL/I-O, не contention) — S2.
`PendingWithinCutoff`/`Failed` > 0 упродовж кількох циклів поспіль —
S2, той самий рівень, що й звичайна SFTP-проблема (`50`).

## `60` — Maintenance: служби, місце, файлове господарство

**Симптом.** `Результат: ПОМИЛКА` у `BRAVO_MAINTENANCE_*.log`.

**Що означає.** Усе, що не потрапляє під `40`/`41`. Найчастіше —
недостатньо вільного місця (`Limits.MinimumFreeSpaceGB`) або керована
служба не в стані `Running`.

Примітка щодо місця: у Maintenance діє лише фіксований поріг. Двоступенева
модель з розрахунковою оцінкою (і WARNING-послабленням порогу) стосується
archive preflight у `BRAVO_ARCHIV` — див. підрозділ «Archive preflight:
перевірка вільного місця» у розділі `40`.

**Чого не робити.** Не звільняйте місце видаленням старих архівів
вручну, не звіривши політику ретенції: ви можете видалити єдину копію,
що переживе поточну проблему.

**Діагностика.**

```powershell
Get-Volume | Select-Object DriveLetter, SizeRemaining, Size
Get-Service | Where-Object { $_.Name -match 'bravo|apache' } |
    Select-Object Name, Status, StartType
```

**Ескалація.** S2; при вільному місці нижче добового приросту — S1,
бо наступна архівація вже не пройде.

### Trace: добовий накопичувальний архів (модель 5.2.0)

Trace-файли обробляє **лише** `BRAVO_MAINTENANCE` (ручний запуск і Task
Scheduler виконують одну й ту саму pipeline; розмір `TraceSRV.out` ніколи не є
тригером — без запуску Maintenance файли не чіпаються). Ланцюг одного запуску:

```text
ротація (служби зупинені)          TraceSRV.out -> TraceSRV_20260821_183005.out
        ↓ (служби вже відновлено)
Trace_20260821.mdz                 один архів на дату; лише ADD нових entries
        ↓
7z t + SHA512 + SFTP trace/        передача у <ім'я>.new -> verify -> заміна
        ↓
видалення переданих .out           ЛИШЕ після повного ланцюга verify
```

- **Джерела:** УСІ `*.out` з кореня інсталяції bravo.exe за один прохід
  (Discovery; фолбек LIMSRoot) — включно з варіантами `TraceSRV2.out`,
  `traceBIS1.out`, `!TraceSRV.out`; додатково SRV з `bravo.ini [Debug] FILE`
  і явний `maintenanceSettings.Trace.BISSourcePath`, якщо поза коренем
  (порожньо/`'off'` = нічого додаткового). Відсутність будь-якого джерела не
  блокує решту; порожній файл = SKIPPED_EMPTY.
- **exchangAPI:** той самий движок — оригінальні імена без перейменувань
  (колізія імені в призначенні = ПОМИЛКА, джерело лишається на місці),
  добовий `exchangAPI_YYYYMMDD.mdz` за датою LastWriteTime → SFTP
  `logs/exchangapi` → видалення `.log` лише після повної верифікації.
- **SFTP-структура:** нові архіви йдуть у `logs/trace` і `logs/exchangapi`
  (`sftpDirectories.TraceLogs`/`.ExchangeApiLogs`); наявні архіви зі старого
  `trace/` Maintenance одноразово (idempotent) мігрує remote-move'ом з
  верифікацією — без жодних видалень; помилка міграції видима (ERROR), не
  блокує нові передачі й повторюється наступним прогоном.
- **Immutability:** entries, що вже в `Trace_YYYYMMDD.mdz`, ніколи не
  оновлюються/замінюються; перед оновленням береться inventory (`7z l -slt`),
  у `7za a` передаються лише нові файли, після оновлення старі entries
  верифікуються за Path+Size+CRC. Однакове ім'я з іншим вмістом — ПОМИЛКА,
  нічого не перезаписується.
- **Збій SFTP:** локальний `.mdz` і ротовані `.out` лишаються; наступний
  Maintenance не додає дублікатів (звірка Size+CRC) і повторює передачу
  повного архіву. Backlog обробляє всі накопичені дати, oldest→newest.
- **Збій оновлення архіву:** попередня валідна локальна версія недоторкана
  (оновлення йде через `Trace\.work\*.partial.mdz` з атомарною публікацією);
  осиротілі `.partial`-артефакти прибираються автоматично через 48 год.
- **Пароль:** архіви шифруються тим самим паролем, що backup `.mdz`
  (Credential Manager). Якщо пароль сайту колись зміниться — оновлення
  існуючого добового архіву впаде на `7z t` (стара частина під старим
  паролем): це очікуваний fail-safe, дата залишиться в черзі; закрийте день
  (наступна дата почне новий архів) або перенесіть старий `.mdz` вручну.
  Заголовки Trace-архівів свідомо нешифровані (без `-mhe`) — як і всі backup
  `.mdz` продукту.
- **Retention:** локальний `Trace_YYYYMMDD.mdz` після успішного SFTP **не
  видаляється**. Єдиний механізм видалення — явний
  `Retention.CompressedLogDeletionEnabled = $true` + `CompressedLogDays`
  (типово `$false`: жоден стиснутий журнальний архів не видаляється за віком,
  включно з legacy `Trace_YYYY-MM-DD.mdz`). Віддалені SFTP-копії retention не
  чіпає ніколи.
- **Dry-run:** `BRAVO_DRY_RUN.ps1` показує PLAN-рядки (джерела, would
  create/update, кількість у черзі, would upload, would delete) без жодних
  змін на диску чи в мережі.
- **Перед оновленням:** журнальні архіви йдуть у `logs/trace` і
  `logs/exchangapi` (`sftpDirectories.TraceLogs`/`.ExchangeApiLogs`);
  відсутні remote-каталоги створюються автоматично (рекурсивно), але в
  облікового запису SFTP, яким користується BRAVO, мають бути права запису
  й достатня квота — так само, як для `baza_app`/`baza_www`/`model`/
  `manifests`. Брак прав/квоти проявиться помилкою на першому ж
  Maintenance-циклі з журнальними даними. Історичний `trace/` після
  успішної автоміграції лишається порожнім — можна прибрати вручну.

## `70` — health-check критичний

**Симптом.** Рядки `[ERROR] Проблема ...` у
`BRAVO_ARCHIV_HEALTH_*.log`.

**Що означає.** Копії застаріли (локальні, SFTP або SMB), або керована
служба не працює. Health нічого не архівує — він доповідає.

**Чого не робити.** Не «лікуйте» health ручним запуском
`BRAVO_ARCHIV.ps1`. Health повідомляє про **наслідок**; причина — в
лозі Archive за той день, коли копія перестала оновлюватись. Ручний
запуск може перезаписати останню хорошу копію тим самим зламаним
процесом.

**Діагностика.** Дивіться `LocalVerified`/`SftpVerified`/`SmbVerified` —
вони показують, який саме рівень зберігання відстав. Далі відкрийте
лог Archive за дату, коли відставання почалось.

**Окремо:** якщо Health завершився кодом `32`, а не `70` — SFTP-гілку
він **пропустив** через непідтверджену цілісність інструментів. Спершу
закрийте `32`, health-результат без цього неповний.

**Ескалація.** Відставання SFTP-копії понад `RemoteBackupMaxAgeHours` —
S2. Відставання **локальної** копії — S2 з вищим пріоритетом: це
означає, що архівація не працює вже кілька циклів.

## `90` — непередбачена внутрішня помилка

**Симптом.** `Write-Error` або останній `[ERROR]` перед аварійним
завершенням.

**Що означає.** Виняток, якого runtime не встиг категоризувати. Це
прогалина в обробці помилок, а не штатний стан.

**Чого не робити.** Не обмежуйтесь перезапуском завдання. `90`, який
повторюється — це дефект, а не збіг.

**Дія.** Збережіть повний лог і заведіть issue з версією
(`VERSION.json.packageVersion`, `buildId`, `sourceCommit`) і кроками.
Перезапуск як тимчасовий обхід допустимий, але не замінює issue.

## Вручну працює, а за розкладом — ні

**Що означає.** Різний контекст виконання: вручну скрипт бачить
credentials і мережеві доступи вашого облікового запису, завдання —
лише `SYSTEM`.

**Діагностика.**

```powershell
.\BRAVO_TASKS_DIAGNOSE.ps1 -ConfigPath ".\BRAVO.config" -InspectOnly
.\BRAVO_TASKS_DIAGNOSE.ps1 -ConfigPath ".\BRAVO.config" -TestAccess
```

**Типові `LastTaskResult`.**

| Код | Значення | Дія |
|---|---|---|
| `0x80070002` | не знайдено скрипт або config | перевірте шлях і `WorkingDirectory` завдання |
| `0x80070005` | відмовлено в доступі | ACL на каталог комплекту або на призначення |
| `0x8007010B` | некоректний робочий каталог | `BRAVO_SETUP.ps1 -Action Scheduler` |
| `0x8007052E` | помилка входу | обліковий запис завдання, не credentials BRAVO |

**Найчастіше виправлення:**

```powershell
.\BRAVO_CREDENTIALS_SETUP.ps1 -Action Ensure -Component Required -StoreFor Both
```

На локалізованій Windows Планувальник показує `SYSTEM` як `СИСТЕМА` —
це не помилка, інсталятор порівнює вбудовані записи за SID.

## Оновлення `7za.exe` або WinSCP

Оновлення інструмента **завжди** дає код `32`, і це правильна
поведінка, а не побічний ефект.

**Порядок — тільки такий:**

1. на **робочій станції** замінити бінарники в `Tools\`;
2. `.\ci\Update-BRAVOToolsManifest.ps1` — переглянути розбіжності;

4. `git diff -- Tools TOOLS_MANIFEST.json` — рев'ю разом із бінарником;

6. розгортання нового комплекту на сервер атомарно.

**Ніколи** не оновлюйте маніфест на сервері. Функція, здатна записати

права підмінити `7za.exe`, тим самим доступом перепише й еталон.

## Discovery знайшов не те джерело

**Симптом.** У виводі `BRAVO_SETUP.ps1 -ValidateOnly` шляхи
`MODEL_SOURCE`/`BLOG_SOURCE`/`BRAVOEXCH_SOURCE` вказують не туди, або
архів підозріло малий (спрацював `SizeSanity`).

**Що означає.** Автоматичне визначення джерел (README, розділ 3.1)
пішло за не тією службою BRAVO або за не тим `bravo.ini`.

**Чого не робити.** Не редагуйте `bravo.ini` — це конфігурація самого
BRAVO/LIMS, не backup. Змінивши її, ви вплинете на роботу LIMS.

**Діагностика.**

```powershell
.\BRAVO_SETUP.ps1 -ValidateOnly
```

Вивід показує знайдені служби, використаний `bravo.ini` і **причину**
для кожного значення — звідки воно взялось.

**Виправлення.** Задайте явний override у `BRAVO.config`
(`$global:discoverySettings`). Явно задане значення виграє над
знайденим і ніколи не перезаписується автоматично.

**Окремо про відносні шляхи.** Якщо `bravo.ini` містить відносний шлях,
він розв'язується відносно каталогу служби, а не вашої поточної
директорії — від `SYSTEM` це може дати зовсім інший каталог. У такому
разі override обов'язковий.

## Стан служб не визначає політику backup

**Архітектурний інваріант.** Стан Windows-служб (Running/Stopped/Disabled/
не встановлено) — **не** політика backup:

- служби `BRAVO`, `exchangAPI`, `BRAVO Web` у БУДЬ-ЯКОМУ стані **не**
  впливають на: створення архіву (generation), публікацію (`.mdz`/
  `.sha512`), передачу (SFTP/SMB), `ArchiveAfterMaintenance`;
- стан служб впливає ЛИШЕ на операції, що реально вимагають виключного
  доступу до MODEL: деструктивна реставрація (`bravocmd.exe r`), інші
  деструктивні MODEL-операції, ротація/перенесення відкритих журналів
  застосунку.

Нормальні, законні причини провалу backup — це виключно реальні файлові
умови: `AccessDenied`, недоступне джерело/UNC, недостатньо місця на
диску, помилка 7-Zip, провал перевірки хешу/цілісності. Якщо лог показує
відмову backup із причиною, що згадує стан служби ("Stopped"/"Disabled"/
"не встановлено") без супутньої файлової помилки — це порушення цього
інваріанта, а не очікувана поведінка; повідомте про це як про дефект.

**Виявлення джерела через службу ≠ залежність від стану служби.**
`BAZA_WWW` визначається через `Apache2.4`/`Br-a-vo.web` (WMI
`PathName` -> `httpd.conf` -> `DocumentRoot`), а `BRAVO_ROOT` — через
`BRAVO`, але в обох випадках читається лише РЕЄСТРАЦІЯ служби
(виконуваний файл), не її поточний run-state: `Disabled`-служба лишається
повністю придатною для цього — вона зареєстрована в SCM з тим самим
`PathName`, лише не запускається автоматично/вручну. Єдиний стан, який
робить автоматичне виявлення неможливим, — служба СПРАВДІ не
зареєстрована (не встановлена) і немає явного override.

Override-и — окремі одне від одного налаштування, не взаємозамінні:

- **BAZA_WWW.** `discoverySettings.WebRoot` задає лише поле `WEB_ROOT`
  (діагностика/похідні обчислення) і сам по собі `httpd.conf` НЕ шукає —
  без зареєстрованої служби `BAZA_WWW` лишиться невизначеним, навіть якщо
  `WebRoot` заданий. Потрібен саме `discoverySettings.Sources.BAZA_WWW` —
  прямий шлях до каталогу `BAZA` під DocumentRoot.
- **MODEL/BLOG/BRAVOEXCH/BAZA_APP.** `discoverySettings.BravoRoot`
  перевизначає лише `BRAVO_ROOT` усередині Discovery (звідти похідні —
  `TRACE_FILE` за відносним шляхом і fallback `BAZA_APP`, коли навіть
  MODEL/BLOG не взяті з bravo.ini). MODEL/BLOG/BRAVOEXCH завжди самі
  походять з canonical bravo.ini (або `discoverySettings.Sources.MODEL`/
  `.BLOG`/`.BRAVOEXCH`), а НЕ з `BravoRoot`.
- **LIMSRoot — окреме налаштування, не discoverySettings.** `pathSettings.
  LIMSRoot` (продукційний корінь інсталяції, потрібен переважно
  `BRAVO_MAINTENANCE`) резолвиться `Resolve-BRAVOEffectiveLimsRoot`
  НЕЗАЛЕЖНО від блоку `discoverySettings` — `discoverySettings.BravoRoot`
  його НЕ встановлює і НЕ обходить. Якщо служби BRAVO немає, а LIMSRoot
  дійсно потрібен (Maintenance), задайте явно `pathSettings.LIMSRoot`.
  `BRAVO_ARCHIV` НЕ ВИМАГАЄ LIMSRoot (не залежить від нього як від
  результату backup — free-space preflight технічно читає значення для
  sanity-перевірки, з fallback на RuntimeRoot, коли воно порожнє) — його
  відсутність не блокує backup.

Коли потрібне джерело задано override-ом, backup так само не залежить від
служби.

## Аварійне відновлення служб (ownership-маркер)

Якщо `BRAVO_MAINTENANCE` або `BRAVO_DATA_RESTORE` зупинив служби
(`BRAVO`/`exchangAPI`/`BRAVO Web`) і процес загинув ЖОРСТКО (kill, втрата
живлення — блок `finally` не виконався), служби більше не піднімуться
самі. Для цього випадку існує персистентний **ownership-маркер**:

    %ProgramData%\BRAVO\State\BRAVO_SERVICE_QUIESCENCE.json

Власник пише його ПЕРЕД першою зупинкою служби (збій запису маркера
абортує зупинку — fail-closed) і прибирає у `finally` після успішного
старту всіх служб. Плановий `BRAVO_HEALTH` (кожні 4 год) виконує watchdog:

- **маркера немає** — Health НІКОЛИ не стартує служби (лише штатний
  alert «не запущена»);
- **власник маркера живий** (перевірка pid+processStartTime, PID-реюз
  виключено) — обслуговування саме триває, жодних дій;
- **власник мертвий, `restartSuppressed=false`** (на практиці — лише
  маркер Maintenance) — Health стартує РІВНО служби зі списку маркера
  (`RestartIntent=true`), чистить маркер і шле WARNING в ALERTS
  «відновлено після аварійного переривання» — перевірте, ЩО вбило процес
  (лог власника вказано в маркері);
- **власник мертвий, `restartSuppressed=true`** — маркер DataRestore
  (він ЗАВЖДИ пишеться suppressed: аварійне переривання посеред restore
  лишає live filesystem у невизначеному стані, автостарт поверх нього
  заборонено) або неповний rollback (код `43`): Health НЕ стартує, лише
  CRITICAL-алерт про потребу ручного відновлення.

**Для техпідтримки:** регламентні роботи не потребують жодних додаткових
дій — просто зупиняйте служби штатно (`services.msc`, `Stop-Service`).
Без маркера BRAVO не запустить їх автоматично ніколи. Єдине застереження:
не плануйте роботи на вікно обслуговування (23:55) — якщо Maintenance
у цей час зупинив служби і впав, watchdog підніме їх протягом ≤4 год.

**Якщо бачите алерт про suppressed-маркер:** дійте за процедурою коду
`43` (розділ вище), після ручного відновлення видаліть маркер вручну.
Чужий маркер (інший hostname) або зіпсований JSON watchdog ігнорує.

Watchdog стартує лише служби з канонічного керованого набору
конфігурації (`maintenanceSettings.Services`); служба поза набором
отримує відмову з ERROR-алертом «можливе стороннє редагування маркера» —
у такому разі перевірте вміст маркера і хто його писав. `BRAVO_SETUP`
зміцнює ACL каталогу `%ProgramData%\BRAVO\State` (запис лише
SYSTEM/Administrators); якщо SETUP звітує «State ACL: НЕВІДПОВІДНІСТЬ»,
виконайте повний запуск SETUP з правами адміністратора.

## Ransomware або масове видалення копій

> **Рівень S1.** Найбільший незакритий ризик проєкту
> ([THREAT_MODEL.md](THREAT_MODEL.md)): SFTP-призначення доступне на
> запис тими самими обліковими даними, якими користується BRAVO.
> Immutable-сховища немає.

**Симптом.** Масове зникнення або пошкодження архівів; health показує
одночасне відставання кількох рівнів зберігання; підозрілі
розширення файлів.

**Перше — зупиніть автоматику.** Доки ви не з'ясували обсяг:

```powershell
Get-ScheduledTask -TaskPath "\BRAVO\*" | Disable-ScheduledTask
```

**Чого категорично не робити.**

- **не запускайте `BRAVO_ARCHIV.ps1`** — він завантажить на SFTP свіжі
  дані поверх копій, які ще могли вціліти;
- **не запускайте Maintenance** — ретенція видалить «застарілі» копії;
- не змінюйте пароль SFTP з тієї самої машини, якщо підозрюєте, що
  вона скомпрометована;
- не форматуйте й не перевстановлюйте нічого до зняття образів.

**Порядок дій.**

1. Від'єднати SFTP/SMB-призначення від скомпрометованої машини на
   рівні мережі або облікових даних — з іншого хоста.
2. Зафіксувати обсяг: які копії й на яку дату вціліли.
3. Оцінити найстарішу завідомо чисту точку відновлення.
4. Лише потім — відновлення (наступний розділ).

**Ескалація.** S1 без винятків. Це той сценарій, задля якого існує весь
проєкт.

## Відновлення на чистий сервер

**Передумова.** Ви маєте архів і його `.sha512`.

**Порядок.**

1. Розгорнути комплект BRAVO з репозиторію (не копіювати зі старого
   сервера — він міг бути скомпрометований).
2. Перевірити цілісність до будь-яких дій:

   ```powershell
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\BRAVO_RUNTIME_GUARD.ps1"
   .\BRAVO_SELF_TEST.ps1
   ```

3. Вибрати один `COMPLETE` `GenerationId` і перевірити весь generation
   **до** розпакування в production:

   ```powershell
   .\BRAVO_RESTORE_TEST.ps1 -GenerationId "<yyyyMMdd_HHmmss>" -ConfigPath ".\BRAVO.config"
   ```

   Це read-only: розпаковує в ізольований тимчасовий каталог, звіряє
   SHA512 і кількість файлів, нічого не змінює. MODEL, BLOG і BRAVOEXCH
   мають походити з цього самого GenerationId; independently newest files
   не утворюють логічно узгодженого restore set.

4. Тільки після `PASS` — відновлювати в production:

   ```powershell
   # Спершу без ризику: розпакувати в порожній каталог і подивитись на дані.
   .\BRAVO_DATA_RESTORE.ps1 -GenerationId "<yyyyMMdd_HHmmss>" `
       -Mode OutOfPlace -TargetPath "D:\RESTORE_CHECK" -ConfigPath ".\BRAVO.config"

   # Далі — у production-шляхи (зупиняє служби, зносить поточні дані вбік
   # у <каталог>.prerestore_<timestamp>, вимагає набрати GenerationId).
   .\BRAVO_DATA_RESTORE.ps1 -GenerationId "<yyyyMMdd_HHmmss>" `
       -Mode InPlace -ConfigPath ".\BRAVO.config"
   ```

   Ціль InPlace визначає discovery (`bravo.ini`), а не параметр. При збої
   код завершення — [`43`](#43--не-вдалося-відновити-дані-bravo_data_restoreps1);
   там же — дії, якщо процес перервано посеред відновлення.

5. Налаштувати credentials (`-StoreFor Both`) і завдання заново.
6. Перший цикл backup — під наглядом, не за розкладом.
7. `.prerestore_*` видаляти лише після підтвердженої працездатності LIMS.

**Чого не робити.** Не переносьте `TOOLS_MANIFEST.json` чи
`RUNTIME_MANIFEST.json` зі старого сервера — беріть із репозиторію.
Інакше ви перенесете разом із ними те, що на старому сервері могли
підмінити.

## Manifest-и backup generation перенесено в `MANIFESTS\` (dev.14)

Починаючи з dev.14, `BRAVO_BACKUP_<GenerationId>.json` (manifest конкретної
генерації backup: статус, компоненти, шлях кожного архіву й хешу) лежить у
`<BackupRoot>\MANIFESTS\`, а не безпосередньо в корені `<BackupRoot>`. Це
третє, окреме сховище — на додачу до `LOGS\` (операційні журнали, розділ
12) і `TEMP\` (одноразові runtime-файли): lifecycle manifest-а прив'язаний
до generation (видаляється разом з нею при retention), а не до незалежних
`LogDays`/`CompressedLogDays`.

**Перенесення старих manifest-ів — автоматичне.** Перший же запуск
`BRAVO_MAINTENANCE.ps1` після оновлення до dev.14 ідемпотентно переносить
усі `BRAVO_BACKUP_*.json`, що лежать безпосередньо в корені `BackupRoot`, у
`MANIFESTS\`. Ручних дій не потрібно. У логу Maintenance з'явиться рядок
`Міграція manifest-ів backup у MANIFESTS: перенесено N; дедубльовано N;
конфліктів N`. Повторні запуски після завершеної міграції нічого не
переносять (idempotent no-op).

**Якщо в логу є "конфліктів" > 0** — для одного й того самого
`GenerationId` в корені `BackupRoot` і в `MANIFESTS\` лежать РІЗНІ файли
(різний вміст, не просто дублікат). BRAVO жодного з них не видаляє й не
перезаписує — обидва лишаються на місці, а читання (retention, `BRAVO_HEALTH`,
`BRAVO_RESTORE_TEST`) завжди пріоритетно бере версію з `MANIFESTS\`.
Це нетипова ситуація (звичайно означає, що хтось вручну редагував чи
копіював manifest) — порівняйте обидва файли вручну (`generationId`,
`status`, `components`) і видаліть застарілий, коли переконаєтесь, який
саме коректний.

**`BRAVO_HEALTH.ps1` лишається read-only** щодо цього сховища: він лише
читає (з fallback на legacy-корінь, якщо `MANIFESTS\` ще не існує), ніколи
не створює й не переносить файли. Відсутність `MANIFESTS\` одразу після
оновлення, до першого запуску Maintenance, — не помилка, доки manifest-и
доступні для читання в старому місці.

Ніщо інше не змінюється: вміст архівів, 7-Zip, SHA512, VSS, SFTP/SMB-шляхи,
дні retention backup (`archiveRetentionDays`, `minimumRetainedVerifiedBackups`)
— усе працює так само, лише за іншого фізичного розташування manifest-файлу.

## Machine-readable статус останніх прогонів (`STATUS\`, 5.3.0)

Кожна з чотирьох основних операцій після обчислення коду завершення
пише machine-readable статус свого прогону (модуль `BRAVO.Status`,
schemaVersion 1) у
`%ProgramData%\BRAVO\State\STATUS\BRAVO_STATUS_<Operation>.json`
(`Archive`, `Health`, `Maintenance`, `RestoreVerify`). Це
compatibility-контракт для зовнішніх machine-споживачів — не редагуйте
файли вручну.

- Спільні поля: `schemaVersion`, `host`, `packageVersion`, `operation`,
  `status` (`OK`/`WARNINGS`/`ERROR` — проєкція exitCode: 0/10/інше),
  `exitCode`, `exitCodeName`, `startedAt`/`finishedAt`/`durationSeconds`,
  `details` (операційні агрегати: generation, лічильники кроків,
  verified-прапорці призначень, вік верифікації).
- Канонічним класифікатором збою лишаються **коди завершення**
  (`BRAVO.ExitCodes`); статус-файл — зручна проєкція, не заміна.
- Запис fail-soft: помилка запису лише логується як WARNING і ніколи не
  змінює код завершення чи результат операції.
- Секретів у файлах немає за контрактом (перевіряється самотестом).
- Транспорт/моніторинг (Zabbix, telemetry outbox) поверх цих файлів —
  окремий майбутній етап (ROADMAP P2.2); зараз контракт суто локальний.

## Планова перевірка відновлюваності (`BRAVO_RESTORE_VERIFY`, 5.3.0)

Щотижневий restore drill тепер автоматизований: задача Планувальника
`BRAVO_RESTORE_VERIFY` (типово Сб 04:00, `schedulerSettings.RestoreVerify`
у `BRAVO.config`: `Enabled`/`WeeklyOn`/`At`) запускає
`BRAVO_RESTORE_TEST.ps1 -NoPause -NotifyOnSuccess`: останній COMPLETE
generation розпаковується в ізольований каталог
`%ProgramData%\BRAVO\RestoreDrill\<guid>` і прибирається; production-шляхи
не змінюються, служби не зупиняються.

- Стан — `%ProgramData%\BRAVO\State\BRAVO_RESTORE_VERIFY_STATE.json`
  (compatibility-контракт, не редагувати вручну): `LastVerifiedAt`
  оновлюється лише повністю чистим прогоном (0 FAIL і 0 WARN); слабший
  результат зберігає вік останньої доведеної верифікації.
- Health-крок «Відновлюваність (restore drill)»: ERROR, якщо останній
  drill FAIL, стан пошкоджено або `LastVerifiedAt` старший за
  `restoreVerifySettings.MaxVerificationAgeHours` (типово 216 год = 9 діб);
  відсутній стан (сервер щойно оновлено) — лише нагадування в журналі.
- Нотифікації: FAIL → CRITICAL в ALERTS, WARN → WARNING в ALERTS,
  успіх scheduled-прогону → SUCCESS у GENERAL (глушиться
  `NotificationMode=errors_only`).
- **Міграція після оновлення комплекту:** задача з'являється лише після
  повторного запуску `BRAVO_TASKS_INSTALL.ps1` (діагностика —
  `BRAVO_TASKS_DIAGNOSE.ps1`). До першого прогону Health показує
  нагадування.
- Ручний `BRAVO_RESTORE_TEST.ps1` лишається доступним і теж оновлює стан;
  з 5.3.0 він проходить runtime guard (коди 33/34/35), як решта
  entrypoint-ів.

## Operator notification UX

Slack/Discord messages are first-response summaries:

- ✅ SUCCESS means the operation/check passed and no action is required.
- ⚠️ WARNING means BRAVO can continue, but the message names the concrete
  operator action.
- 🚨 CRITICAL means backup, integrity, credentials or maintenance safety is at
  risk. Do not improvise around integrity failures; follow the relevant
  runbook section and inspect the referenced log.

Large diagnostic collections (hundreds of affected files/ranges) are
summarized in operator notifications: the message carries the total count,
up to 5 representative examples and an `…і ще N` remainder line. Complete
per-item diagnostics remain available only in the local BRAVO-Toolkit log.
The notification layer additionally enforces a transport-agnostic safe
payload limit: an anomalously large message is truncated at a line boundary
with an explicit `⚠️ Повідомлення скорочено` suffix (the log-path line is
preserved) instead of being split into a series of messages.

The top of a warning/critical message contains the reason and action before
server metadata. The log path at the bottom is the source for full technical
evidence: long filenames, destination paths, thresholds and tool output remain
there.

### GENERAL vs ALERTS channels

`BRAVO.Notifications` routes messages by severity into two channels, so an
operator can put routine status in a low-noise channel and problems in a
channel that pages someone:

| Severity | Channel |
|---|---|
| SUCCESS | GENERAL |
| WARNING / ERROR / CRITICAL | ALERTS |

Routing also depends on `NotificationMode`: `none` sends nothing; `errors_only`
sends only to ALERTS (SUCCESS is suppressed); `all` sends SUCCESS to GENERAL
and everything else to ALERTS.

Each provider has two Credential Manager targets —
`BRAVO_DISCORD_GENERAL_URL`/`BRAVO_DISCORD_ALERTS_URL` and
`BRAVO_SLACK_GENERAL_URL`/`BRAVO_SLACK_ALERTS_URL` — set up via
`BRAVO_CREDENTIALS_SETUP.ps1 -Component Discord` / `-Component Slack`
(each provider group configures both route-specific credentials at once).

Required topology depends on `NotificationMode`:

| Mode | Required credentials |
|---|---|
| `none` | none |
| `errors_only` | ALERTS only |
| `all` | GENERAL + ALERTS |

**MIGRATION (5.2.1): legacy provider-wide webhooks are no longer supported.**
`BRAVO_DISCORD_URL` and `BRAVO_SLACK_URL` are ignored by the runtime: each
channel resolves exclusively through its own route-specific credential, with
no provider-wide fallback and no GENERAL↔ALERTS fallback. An installation
that only has the legacy record fails Dry Run / Setup with an explicit
diagnostic ("Знайдено лише legacy … — він більше не підтримується").
Migration command (run for both stores):

```powershell
.\BRAVO_CREDENTIALS_SETUP.ps1 -Action Ensure -Component Discord -StoreFor Both
.\BRAVO_CREDENTIALS_SETUP.ps1 -Action Ensure -Component Slack -StoreFor Both
```

The old Credential Manager records are NOT deleted automatically and are not
copied into the new channel records (one shared webhook does not identify
which Discord/Slack channel it pointed to) — configure the new topology
deliberately, then remove the legacy records manually after acceptance.
Verify real delivery to both channels with `.\BRAVO_NOTIFICATION_TEST.ps1`
(canonical pipeline; explicitly marked test messages; requires credentials
for the account it runs under — repeat under SYSTEM for scheduled tasks).

Backup health wording:

- SUCCESS: `Остання резервна копія`.
- WARNING/ERROR: `Остання успішна резервна копія`.
