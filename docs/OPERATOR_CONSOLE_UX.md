# BRAVO Operator Console UX

Цей документ фіксує цільову візуальну мову та operator-facing UX для ручних запусків основних BRAVO-скриптів. Він доповнює `docs/MANUAL_RUN_CONSOLE_UX.md`, який лишається детальним контрактом для `BRAVO_ARCHIV.ps1`.

Мета — не зробити всі скрипти однаковими, а дати їм спільну структуру, однакову семантику статусів і передбачуваний фінальний summary, зберігаючи domain-specific інформацію кожного сценарію.

## 1. Спільний каркас

Для ручного інтерактивного запуску операторські скрипти використовують спільний каркас:

```text
============================================================
 BRAVO <FUNCTION> <packageVersion>
 <InstitutionName> [<InstitutionCode>]
 <COMPUTERNAME>
 Режим: <MODE>
============================================================

<domain-specific stages / checks / plan>

------------------------------------------------------------
 РЕЗУЛЬТАТ
------------------------------------------------------------
<domain-specific summary>
------------------------------------------------------------

Натисніть будь-яку клавішу для закриття...
```

Спільні правила:

- header показує продукт/функцію, package version, установу, hostname і режим;
- ручний запуск може використовувати колір лише як додатковий visual aid;
- текстовий статус обов'язковий і не залежить від кольору;
- scheduled/non-interactive запуск не чекає клавішу;
- stack trace, raw exception, stdout/stderr і command line не засмічують normal console UX;
- при помилці оператор бачить коротку `Причина:`; технічні подробиці залишаються в логах;
- формальний BRAVO exit code і native exit code tool не змішуються;
- native exit code, якщо показується, має коротке україномовне пояснення;
- майбутній telemetry block не з'являється до фактичної реалізації FEAT-003.

## 2. BRAVO Archive — уточнення component UX

`BRAVO_ARCHIV.ps1` має використовувати той самий принцип деталізації компонента, що й цільовий UX `BRAVO_RESTORE_TEST.ps1`: рядок етапу дає статус і duration, а під ним показуються короткі фактичні атрибути artifact.

Канонічний backup artifact BRAVO — тільки `.mdz`. `7-Zip` є внутрішнім engine, а не зовнішнім форматом artifact.

Цільовий успішний component:

```text
[2/5] Архівація MODEL ........................ OK       09:41
      Архів:     MODEL_20260807_133004.mdz
      Розмір:    3.82 GB
      SHA512:    OK
      Integrity: OK

[3/5] Архівація BLOG ......................... OK       01:22
      Архів:     BLOG_20260807_133004.mdz
      Розмір:    412 MB
      SHA512:    OK
      Integrity: OK

[4/5] Архівація BRAVOEXCH .................... OK       00:18
      Архів:     BRAVOEXCH_20260807_133004.mdz
      Розмір:    43 MB
      SHA512:    OK
      Integrity: OK
```

`SHA512: OK` означає, що sidecar/hash створено та відповідає artifact згідно з фактичним archive contract. `Integrity: OK` означає, що post-create integrity test artifact пройдено. Ці поля не повинні показувати `OK`, якщо відповідна перевірка реально не виконувалась.

При failure не показуються вигадані `Архів`, `Розмір`, `SHA512` або `Integrity`:

```text
[4/5] Архівація BRAVOEXCH .................... ERROR    00:07
      Причина: 7-Zip код 2 — критична помилка
      Деталі:  Не вдалося створити архів BRAVOEXCH
```

Фінальний `РЕЗУЛЬТАТ` Archive лишається агрегованим: BRAVO exit code, час, `Створено архівів: X з Y`, загальний розмір і список artifacts із повними шляхами. Component blocks не скасовують summary, а дають оператору live/final context по кожному artifact.

## 3. BRAVO Health

Health використовує checklist-oriented UX. Основний рядок — логічна група health-check, а фінальний summary окремо агрегує кількість перевірок і проблем.

```text

 WIN-44OBNQ3R3OB
 Режим: MANUAL
============================================================

[2/7] Служби BRAVO ........................... OK       00:01

      Причина: На диску D: залишилось 8.7 GB
[6/7] SFTP ................................... OK       00:08
[7/7] SMB .................................... OK       00:03

------------------------------------------------------------
 РЕЗУЛЬТАТ
------------------------------------------------------------
Статус:           ПОПЕРЕДЖЕННЯ
Код завершення:   10 — SuccessWithWarnings

  MODEL       OK   3.82 GB   вік 14 год. 22 хв.

## 5. BRAVO Maintenance

 WIN-44OBNQ3R3OB

```

## 6. BRAVO Dry Run

Dry Run зберігає власну семантику `PASS`, `WARN`, `FAIL`, `PLAN`. Її не потрібно насильно переводити в Archive-style `OK/ERROR`.

```text
============================================================
 BRAVO Dry Run 4.5.0
 МИКОЛАЇВСЬКА РДЛ [00702245]
 WIN-44OBNQ3R3OB
 Режим: READ-ONLY
============================================================

[PASS] Конфігурація
       BRAVO.config завантажено

[PASS] Runtime integrity
       RUNTIME_MANIFEST.json відповідає комплекту

[PASS] Tools integrity
       7-Zip та WinSCP перевірені

[PASS] Credential Manager
       Необхідні записи знайдено

[WARN] SFTP
       Мережева перевірка не виконувалась
       Запустіть із -TestAccess для перевірки доступу

[PLAN] Archive
       MODEL
       BLOG
       BRAVOEXCH

[PLAN] Передача
       SFTP

------------------------------------------------------------
 РЕЗУЛЬТАТ
------------------------------------------------------------
Готовність:       ГОТОВО ДО ЗАПУСКУ

PASS:             4
WARN:             1
FAIL:             0
PLAN:             2

Production-операції не виконувались.
------------------------------------------------------------
```

При `FAIL > 0` readiness стає `НЕ ГОТОВО` і process exit code має лишатися формально ненульовим згідно з runtime contract.

## 10. Implementation direction

Ці UX-контракти мають реалізовуватися через спільний console/result layer, а не копіюванням `Write-Host` у кожний script.

Цільова архітектура:

```text
Runtime Result Model
        |
        +--> Console Renderer
        +--> Log Renderer
        +--> JSON/ResultPath
        +--> Telemetry Renderer (після FEAT-003)
```

Domain runtime визначає факти й статуси; renderer визначає лише presentation. Це не дозволяє console, log, JSON і telemetry розійтися в трактуванні одного run.

Archive і Restore Test навмисно мають схожий component-oriented presentation: Archive показує, що `.mdz` успішно створено та перевірено; Restore Test показує, що цей `.mdz` пізніше реально пройшов isolated extraction/restore drill.
