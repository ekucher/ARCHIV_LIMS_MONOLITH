# BRAVO Configuration v2 — статус завершення та обсяг робіт, що залишилися

> **ЦІЛЬОВИЙ ДОКУМЕНТ / ЩЕ НЕ ПОВНІСТЮ РЕАЛІЗОВАНО.** Цей документ описує
> обсяг робіт, що залишився для закриття FEAT-001 (`TODO_FEATURES.md`) /
> P3.1 (`ROADMAP.md`). Це довідник статусу й обсягу, а не тікет на
> реалізацію, і він навмисно коротший за повну специфікацію реалізації.
> Сам по собі він не авторизує жодних змін коду.

## Поточний стан (перевірено відносно `developer`)

P0 Configuration Foundation завершено та змерджено в `developer`
(`docs/design/BRAVO_CONFIGURATION_FOUNDATION_DESIGN.md`, CHANGELOG.md
"Не випущено (developer)" → "P0 Configuration Foundation (PR B/C)").

Завершено у Foundation:

- канонічні вбудовані значення за замовчуванням
  (`Get-BRAVODefaultConfiguration`);
- детермінований глибокий мердж (`Merge-BRAVOConfiguration`) —
  рекурсивний мердж хештаблиць, **масиви повністю замінюють масив за
  замовчуванням (а не мерджаться поелементно)**, і **явний порожній
  масив `@()` уже приймається як валідне, навмисне перевизначення** —
  перевірено безпосередньо в
  `modules/BRAVO.Configuration/BRAVO.Configuration.psm1` (коментарі
  мердж-рушія та гілка обробки масивів);
- значення за замовчуванням `maintenanceSettings.Limits.ExcludedDrives`
  **вже** дорівнює `@()` у канонічних вбудованих значеннях за
  замовчуванням — перевірено в тому ж модулі;
- розв'язання сирої конфігурації (`Resolve-BRAVORawConfiguration`);
- вилучення похідних значень (`Resolve-BRAVOConfigurationDerivation`) —
  виявлення/похідні обчислення виконуються після мерджу, а не до
  нього;
- опціональний `BRAVO.config` (конвеєр без конфігурації працює лише зі
  вбудованих значень за замовчуванням + `BRAVO.local.config`);
- явний контракт наміру `-ConfigPath` проти AUTO, послідовно
  застосований у `BRAVO_SETUP.ps1`, визначеннях завдань Task Scheduler
  та `BRAVO_CONFIGURATOR.ps1`;
- проєкція сумісності для застарілих (legacy) споживачів;
- повторна перевірка інваріантів безпеки після мерджу
  (`Test-BRAVOEffectiveSecurityInvariants` у `BRAVO_CONFIG_LOADER.ps1`):
  за замовчуванням у режимі `Enforce` ефективна конфігурація, що
  послаблює критичне для безпеки налаштування через
  `BRAVO.local.config`, відхиляється, а не приймається мовчки;
  підтримуваний режим `Warn` (`BRAVO_RUNTIME_INTEGRITY_MODE=Warn`) та
  явне перевизначення `BRAVO_ALLOW_WEAKENED_SECURITY=1` обидва
  попереджають і продовжують роботу замість відхилення, і це не
  крайові випадки, які можна проігнорувати — оператор, що використовує
  будь-який з цих режимів, не отримує безумовного відхилення.

Ефективний пріоритет сьогодні:

```text
DEFAULT < BRAVO.config (опціональний) < BRAVO.local.config (опціональний)
```

`VERSION.json` наразі декларує `"configSchemaVersion": 1`.

### `BRAVO.local.config` сьогодні — restricted-language, але все ще виконується

`BRAVO.local.config` — це опціональний файл перевизначень у форматі
даних (хештаблиця шлях-через-крапку → значення). Його продакшн-
завантажувач, перевірений у `BRAVO_CONFIG_LOADER.ps1`
(`Read-BRAVOLocalConfigurationOverrides`), робить таке:

```powershell
$localOverrideScript = [scriptblock]::Create($localOverrideText)
$localOverrideScript.CheckRestrictedLanguage([string[]]@(), [string[]]@(), $false)
$localOverrideData = & $localOverrideScript
```

Це означає, точніше:

- текст компілюється в `ScriptBlock`;
- `CheckRestrictedLanguage` із **порожніми** списками дозволених команд
  і дозволених змінних перевіряє, що блок не містить викликів cmdlet,
  викликів функцій і звернень до змінних/середовища — вони
  відхиляються ще до виклику блока;
- **це НЕ гарантія «лише літерали».** Обмежена мова даних PowerShell
  навіть із порожніми allow-списками все ще дозволяє деякі форми
  виразів (наприклад, арифметичні та діапазонні вирази). Оскільки
  перевірений `ScriptBlock` потім виконується, будь-який такий
  дозволений вираз *обчислюється*, а не просто вилучається як
  літерал;
- **перевірений `ScriptBlock` після цього викликається**
  (`& $localOverrideScript`) для отримання хештаблиці.

Отже, сьогоднішній контракт такий: **вхідні дані у форматі
restricted-language / data-shaped — без команд, без функцій, без
звернень до змінних/середовища — перевіряються перед виконанням, але
перевірений `ScriptBlock` все одно викликається, і обмежена
граматика, яку він приймає, не обмежена чистими літералами.** Це не
та сама гарантія, що «парсити без жодного виконання», і це не
еквівалентно явному literal-only AST-переліку дозволеного — це
потужне, вузьке, обмежене порожніми allow-списками виконання, а не
non-executing AST-only вилучення. Це реальний і ефективний контроль
(довільне використання команд/функцій/змінних відхиляється ще до
можливості виконання), але він архітектурно відрізняється від
цільового варіанту Configuration v2 нижче, і цей документ не має
розмивати цю відмінність.

## Прогалини, що залишилися (що ще потрібно для Config v2)

Сам `BRAVO.config` **ще не** є форматом лише даних (DATA-only). Це
досі виконуваний PowerShell-скрипт на 1300+ рядків
(`param(ConfigRoot, RuntimeRoot)`, присвоєння `$global:`, блоки
літеральних хештаблиць, перемішані з виконуваною логікою
налаштування) — перевірено безпосередньо в `BRAVO.config`. Лише шар
*локальних перевизначень* (`BRAVO.local.config`) наразі має
restricted-language / validated-before-invoke поведінку. Основний файл
конфігурації — ні, і навіть читач локальних перевизначень все ще
викликає перевірений `ScriptBlock`, замість того щоб вилучати дані,
ніколи його не виконуючи.

Ще не реалізовано:

- повністю DATA-only формат `BRAVO.config` (без `param()`, без
  присвоєння `$global:`, без виконуваних інструкцій — лише
  літеральні дані), що читається парсером, який ніколи не викликає
  його як код;
- справжній non-executing декларативний парсер (див. «Вимога до
  безпечного декларативного парсера» нижче) — сьогоднішній підхід
  «restricted-language, потім виконати» є проміжним щаблем, а не
  кінцевою ціллю;
- канонічна назва/контракт файлу `BRAVO.config.local` як
  довгострокова цільова назва файлу машинно-локального перевизначення
  (див. примітку про іменування нижче — цього файлу в рантаймі
  сьогодні не існує);
- `configSchemaVersion = 2` та пов'язаний з ним контракт
  схеми/валідації (відхилення невідомих ключів, перевірка типів),
  застосований через декларативний шлях завантаження v2, з окремим
  регресійним покриттям для v2 — базова семантика мерджу (заміна
  масивів, явний `@()`, значення за замовчуванням `ExcludedDrives`)
  вже існує у Foundation, і її не потрібно вигадувати заново — лише
  перенести та повторно довести на шляху завантаження v2;
- шлях міграції з поточної пари «виконуваний `BRAVO.config` /
  restricted-language `BRAVO.local.config`» до пари DATA-only v2;
- прийняття збереження при оновленні/апгрейді (updater/upgrade
  preservation) для формату v2 (оновлення не повинно мовчки знищувати
  або пошкоджувати локальне перевизначення v2);
- повна регресійна матриця Definition-of-Done для Configuration v2
  (невідомі ключі, невідповідність типів, заміна масивів, значення, що
  допускають null, відхилення пониження безпеки, еквівалентність
  legacy-проти-v2 на контрольних фікстурах), повторно прогнана саме
  проти декларативного шляху завантаження v2 — сьогоднішній self-test
  уже доводить заміну масивів/явний `@()`/пониження безпеки для
  *поточного* мердж-рушія Foundation; те, чого бракує — довести, що
  той самий контракт переживає перехід на парсер/схему v2, а не
  вигадати цей контракт заново.

## Цільова архітектура

```text
Built-in defaults      (канонічні, повні, частина пакета — не файл)
    <
BRAVO.config            (опціональний, DATA-only, перевизначення сайту/розгортання, configSchemaVersion 2)
    <
BRAVO.config.local      (опціональний, DATA-only, машинно-локальне перевизначення, найвищий пріоритет)
```

Вбудовані значення за замовчуванням — це канонічні, повні значення за
замовчуванням продукту/пакета — вони не «зберігаються в
`BRAVO.config`». `BRAVO.config` у цільовому варіанті v2 — це
**опціональний шар перевизначення рівня сайту/розгортання** поверх
цих значень за замовчуванням, а `BRAVO.config.local` — це додатковий
**опціональний шар машинно-локального перевизначення** з найвищим
пріоритетом. Не описуйте цільовий `BRAVO.config` як «значення за
замовчуванням пакета», «основний шар конфігурації» чи «первинну
конфігурацію, версійовану разом із пакетом» — це неправильно
представляло б, де насправді зберігаються значення за замовчуванням,
і розмивало б відмінність між рівнем сайту/розгортання та
машинно-локальним рівнем між цими двома файлами перевизначень.

Обидва файли конфігурації — це ДАНІ (DATA), а не КОД (CODE).
Продакшн-рантайм не повинен виконувати жоден з цих файлів як
PowerShell-скрипт.

### Вимога до безпечного декларативного парсера (ціль — не сьогоднішня поведінка)

Парсер v2 повинен:

1. парсити текст PowerShell в AST / еквівалентне декларативне
   представлення;
2. валідувати лише дозволені структури літеральних даних;
3. вилучати значення як ДАНІ;
4. **ніколи не викликати результуючий `ScriptBlock` конфігурації**;
5. ніколи не робити dot-source файлу конфігурації;
6. ніколи не використовувати `& $scriptBlock` (або еквівалентний
   виклик) для продакшн-файлів Configuration v2;
7. відхиляти будь-який непідтримуваний синтаксис за принципом fail
   closed;
8. не дозволяти жодних cmdlet;
9. не дозволяти жодних викликів функцій;
10. не дозволяти звернень до змінних/середовища, **за винятком** трьох
    внутрішніх літеральних констант PowerShell `$true`, `$false` та
    `$null` — вони необхідні для представлення булевих та допускаючих
    null значень конфігурації, і мають розпізнаватися явно за
    ідентичністю AST/токена як літеральні ЗНАЧЕННЯ ДАНИХ, ніколи не
    розв'язувані зі стану сесії/середовища. Усі інші форми змінних
    залишаються відхиленими: `$env:...`, `$global:...`,
    `$script:...`, `$local:...`, довільне `$foo`, `${...}` та будь-яке
    інше звернення до змінної;
11. не дозволяти довільних виразів.

Сьогоднішній підхід `CheckRestrictedLanguage` + `& $scriptBlock`, що
використовується для `BRAVO.local.config`, дає корисний прецедент для
пунктів 8–10 (без cmdlet, без викликів функцій/команд, без довільних
звернень до змінних/середовища), але **не** доводить пункти 7 чи 11 і
**порушує пункт 4**:

- пункт 4 (ніколи не викликати) — **порушено**: перевірений блок
  викликається (`& $localOverrideScript`);
- пункт 7 (fail closed на будь-якому непідтримуваному синтаксисі,
  через власний перелік дозволених літералів/data-вузлів парсера v2)
  — **не доведено** цим механізмом; `CheckRestrictedLanguage`
  застосовує власну обмежену граматику мови PowerShell, а не
  специфічний для v2 fail-closed перелік дозволених literal-AST;
- пункт 11 (без довільних виразів) — **не доведено**: як зазначено
  вище, обмежена граматика все ще дозволяє деякі форми виразів
  (наприклад, арифметичні/діапазонні вирази), і вони обчислюються під
  час виклику.

Це не є, саме по собі, цільовим парсером Configuration v2, і його не
слід описувати як такий, що вже задовольняє повний контракт пунктів
7–11. Це прецедент, що доводить: половина підходу «без
команд/без функцій/без змінних» працює; робота для v2 полягає в тому,
щоб додатково (a) замінити «перевірити, потім викликати» на
«парсити/вилучати без виклику» (пункти 1–4) і (b) додати явний
fail-closed перелік дозволених літералів/data-вузлів, що відхиляє
довільні форми виразів прямо (пункти 7 і 11), а не покладатися лише
на обмежену граматику PowerShell.

Справжній non-executing прецедент лише на основі AST уже існує в цій
кодовій базі для вужчої мети: `Test-BRAVORuntimeSecuritySettings`
(`BRAVO_RUNTIME_GUARD.ps1`) читає конкретні літерали перемикачів
безпеки з `BRAVO.config` через
`[Management.Automation.Language.Parser]::ParseFile` — парсинг AST —
**ніколи не викликаючи `BRAVO.config`**, саме тому, що завантаження
`BRAVO.config` як коду означало б виконання довільного PowerShell ще
до запуску перевірки безпеки (див. `SECURITY.md`, «Перемикачі
безпеки»). Ця функція вилучає лише невеликий фіксований набір
літеральних значень для однієї мети (перевірка перемикачів безпеки
перед виконанням); це не універсальний читач конфігурації. Вона
демонструє, що підхід без виклику вже доведено здійсненним у цій
кодовій базі, а не те, що сам Config v2 вже побудований.

### Ціль `BRAVO.config` (v2)

- опціональне, DATA-only **перевизначення рівня сайту/розгортання**
  поверх вбудованих значень за замовчуванням — не місце, де
  зберігаються значення за замовчуванням;
- несе `configSchemaVersion = 2`;
- залишається опціональним (конвеєр без конфігурації зі вбудованих
  значень за замовчуванням має продовжувати працювати, як і сьогодні).

### Ціль `BRAVO.config.local` (v2)

- опціональне, DATA-only **машинно-локальне перевизначення** з
  найвищим пріоритетом серед трьох шарів;
- шлях-через-крапку → значення (або еквівалентна структурована форма
  v2 — точна форма є частиною дизайну схеми v2, а не фіксується цим
  документом);
- це наступник у v2 сьогоднішнього `BRAVO.local.config`, а не
  перейменування його на місці, і не просто «локальне для сайту» —
  це саме машинно-локальний шар, відмінний від шару рівня
  сайту/розгортання `BRAVO.config` над ним.

### Поточне іменування проти цільового — не плутати

```text
ПОТОЧНИЙ СТАН (продакшн сьогодні):
    BRAVO.local.config
    BRAVO.local.config.example
    — restricted-language / data-shaped, валідується перед викликом
      (CheckRestrictedLanguage, потім & $scriptBlock — див. вище),
      уже випущено, уже задокументовано в README.md /
      BRAVO_SETUP.md / OPERATIONS.md.

ЦІЛЬОВИЙ СТАН (Configuration v2, ще не реалізовано):
    BRAVO.config.local
    — ще не існує в рантаймі. Операторська документація
      повинна й надалі інструктувати операторів використовувати
      BRAVO.local.config, доки v2 не буде випущено і не буде
      задокументовано шлях міграції.
```

Операторська документація (`README.md`, `BRAVO_SETUP.md`,
`OPERATIONS.md`) не повинна змінюватися так, щоб посилатися на
`BRAVO.config.local` як на щось, що оператор має створювати сьогодні.

### Перехід застарілого (legacy) `BRAVO.local.config`

- `BRAVO.local.config` не видаляється в момент випуску v2; він
  залишається читабельним/підтримуваним на період переходу;
- процедура міграції (dry-run, поетапна конвертація — за зразком
  цільової моделі FEAT-001 у `TODO_FEATURES.md`) конвертує наявний
  `BRAVO.local.config` у проміжний, неактивний кандидат
  `BRAVO.config.local` (див. «Міграція: конвертація проти активації»
  нижче); резервне копіювання та відкат стосуються пізнішої
  транзакції активації, а не створення проміжного кандидата як
  такого;
- legacy та v2 повинні давати еквівалентну ефективну конфігурацію на
  контрольних фікстурах протягом перехідного вікна.

### Межа безпеки legacy/v2 під час переходу

Поки завантажувач приймає обидва формати протягом вікна міграції, ці
два шляхи мають залишатися суворо розділеними:

- файл у форматі v2 (`configSchemaVersion = 2`) завжди лише парситься
  й вилучається як ДАНІ — він ніколи не виконується як код, навіть
  якщо не проходить валідацію;
- файл у застарілому форматі використовує лише наявний, уже
  перевірений шлях сумісності legacy (сьогоднішній виконуваний
  `BRAVO.config` / restricted-language-then-invoke
  `BRAVO.local.config`);
- недійсний або пошкоджений файл v2 **fail closed** — він
  відхиляється, і ніколи не повинен мовчки повторно оброблятися через
  виконуваний шлях legacy. Файл не стає виконуваним лише тому, що
  його парсинг v2 зазнав невдачі.

### Активний режим набору конфігурації (контракт визначення формату)

Завантажувач може класифікувати окремі файли, але перш ніж мерджити
чи викликати будь-який шар, він повинен визначити **один узгоджений
активний режим конфігурації** для інсталяції. Він ніколи не повинен
незалежно обирати legacy для одного активного шару та v2 для іншого
й мовчки мерджити змішаний результат.

**Визначення формату завжди non-executing.** Класифікація
`BRAVO.config` як legacy чи v2 ніколи не повинна виконувати файл для
виявлення його формату — визначення використовує статичний аналіз
(наприклад, явний маркер `configSchemaVersion`, знайдений через
AST/non-executing парсинг), узгоджено з правилом fail-closed вище:
недійсний файл v2 ніколи мовчки не повторно обробляється як
legacy-виконання, а файл ніколи не виконується лише для визначення
того, чим він є.

**Матриця активного режиму та наміру (AUTO проти EXPLICIT).**
Наведена нижче матриця містить окремий вимір **наміру** — AUTO
(оператор не вказав явно `-ConfigPath`) проти EXPLICIT (оператор
явно вказав `-ConfigPath <шлях>`). Канонічний інваріант: **EXPLICIT
`-ConfigPath` означає, що явно вибраний основний файл ПОВИНЕН
існувати.** Тому EXPLICIT + відсутній основний файл = FAIL CLOSED
незалежно від наявності legacy-local / наявності v2-local /
відсутності локального файлу. Режими з відсутнім основним файлом
(лише built-in, лише legacy-local, лише v2-local) є валідними ТІЛЬКИ
для наміру AUTO. Класифікація набору режимів ніколи не послаблює вже
наявний контракт «мусить існувати» для EXPLICIT (цей наявний контракт
уже перевірений в іншому місці репозиторію —
`selftest/BRAVO_SELF_TEST.ConfigLoader.ps1` та `ConfigIntent.ps1` —
цей документ не повинен йому суперечити).

**Підтримувані активні режими (намір AUTO, доки не вказано інше):**

| # | `BRAVO.config` | `BRAVO.local.config` | `BRAVO.config.local` | Намір | Результат | Пріоритет |
|---|---|---|---|---|---|---|
| A | відсутній | відсутній | відсутній | AUTO | SUPPORTED — лише built-in (нейтрально до формату) | `DEFAULT` |
| B | розпізнаний legacy | відсутній | відсутній | AUTO/EXPLICIT | SUPPORTED — LEGACY MODE | поточний пріоритет legacy, без змін |
| C | розпізнаний legacy | присутній | відсутній | AUTO/EXPLICIT | SUPPORTED — LEGACY MODE | поточний пріоритет legacy, без змін протягом вікна міграції |
| D | відсутній | присутній | відсутній | AUTO | SUPPORTED — LEGACY MODE (вже підтримуваний шлях built-in + локальне перевизначення) | `DEFAULT < BRAVO.local.config` |
| E | валідний v2 | відсутній | відсутній | AUTO/EXPLICIT | SUPPORTED — V2 MODE | `DEFAULT < BRAVO.config` |
| F | валідний v2 | відсутній | валідний v2 | AUTO/EXPLICIT | SUPPORTED — V2 MODE | `DEFAULT < BRAVO.config < BRAVO.config.local` |
| G | відсутній | відсутній | валідний v2 | AUTO | SUPPORTED — V2 MODE (перевизначення рівня сайту залишається опціональним) | `DEFAULT < BRAVO.config.local` |

**Заборонені комбінації для наміру EXPLICIT з відсутнім основним
файлом — fail closed незалежно від стану локальних файлів:**

| # | `BRAVO.config` | `BRAVO.local.config` | `BRAVO.config.local` | Намір | Результат |
|---|---|---|---|---|---|
| H | відсутній | відсутній | відсутній | EXPLICIT | FAIL CLOSED — явно вибраний основний шлях не існує |
| I | відсутній | присутній | відсутній | EXPLICIT | FAIL CLOSED — явно вибраний основний шлях не існує, наявність legacy-local не рятує |
| J | відсутній | відсутній | валідний v2 | EXPLICIT | FAIL CLOSED — явно вибраний основний шлях не існує, наявність v2-local не рятує |

**Явно заборонені змішані режими — fail closed, без неявного
пріоритету:**

| Комбінація | Результат |
|---|---|
| legacy `BRAVO.config` + `BRAVO.config.local` | UNSUPPORTED MIXED MODE — FAIL CLOSED. Ніколи не виконувати legacy-основний файл, а потім мерджити локальне перевизначення v2. |
| v2 `BRAVO.config` + `BRAVO.local.config` | UNSUPPORTED MIXED MODE — FAIL CLOSED. Ніколи не парсити основний файл v2, а потім викликати legacy локальне перевизначення. |
| одночасна наявність `BRAVO.local.config` і `BRAVO.config.local` | CONFLICT — FAIL CLOSED. Немає неявного правила «новіша назва файлу перемагає», «стара назва файлу перемагає» чи «найновіший файл перемагає»; оператор/updater повинен явно завершити міграцію або відкотитися. |
| `BRAVO.config` декларує v2 (`configSchemaVersion = 2`), але не проходить валідацію v2 | FAIL CLOSED — ніколи не відкочується до legacy-виконання (див. «Межа безпеки legacy/v2 під час переходу» вище). |
| формат `BRAVO.config` невідомий/неоднозначний | FAIL CLOSED. |
| `BRAVO.config.local` (v2-local) недійсний/непідтримуваний, немає основного файлу (AUTO) | FAIL CLOSED — найвищий пріоритет серед трьох шарів недійсний; порожній основний файл не рятує цей шар. |
| валідний v2 `BRAVO.config` + недійсний/непідтримуваний `BRAVO.config.local` | FAIL CLOSED — ніколи не відкочується до конфігурації лише з основного файлу (див. «Недійсний найвищий пріоритетний шар» нижче). |
| `BRAVO.config.local` декларує непідтримуваний/невідомий `configSchemaVersion` | FAIL CLOSED. |
| `BRAVO.config.local` містить невідомий ключ | FAIL CLOSED (той самий валідатор схеми, що й для основного файлу). |
| `BRAVO.config.local` провалює валідацію типів | FAIL CLOSED (той самий валідатор схеми, що й для основного файлу). |

`BRAVO.local.config` — це назва файлу, специфічна лише для legacy
машинно-локального рівня протягом перехідного вікна;
`BRAVO.config.local` — це назва файлу, специфічна лише для v2
машинно-локального рівня. Якщо присутні обидва — це конфігураційний
**конфлікт**, а не питання пріоритету — ці дві назви файлів
специфічні для формату, а не синоніми з неявним правилом розв'язання
конфлікту.

**Недійсний найвищий пріоритетний шар.** `BRAVO.config.local`
(v2-local) — найвищий за пріоритетом із трьох шарів (`DEFAULT <
BRAVO.config < BRAVO.config.local`). Це вимагає, щоб він також мав
найсуворішу семантику відмови: будь-який malformed, непідтримуваний
чи такий, що провалює схему v2, `BRAVO.config.local` **fail closed**
— незалежно від того, чи основний файл `BRAVO.config` присутній,
відсутній, валідний v2 чи legacy. Обов'язкові інваріанти:

- недійсний `BRAVO.config.local` НІКОЛИ не призводить до мовчазного
  повернення до конфігурації лише з основного файлу/DEFAULT
  («NO FALLBACK»);
- недійсний `BRAVO.config.local` НІКОЛИ не призводить до часткового
  мерджу підмножини валідних ключів разом з відхиленими
  («NO PARTIAL MERGE»);
- недійсний `BRAVO.config.local` НІКОЛИ не ігнорується мовчки на
  користь продовження без нього («NO IGNORE-AND-CONTINUE»);
- завантажувач повинен валідувати/класифікувати локальний шар ДО
  прийняття фінальної ефективної конфігурації — синтаксична чи
  схемна невдача цього шару зупиняє побудову ефективного набору
  конфігурації повністю, тим самим методом fail-closed, що й
  недійсний основний файл v2 (див. рядок вище: «`BRAVO.config`
  декларує v2, але не проходить валідацію v2»);
- це узгоджується з, а не послаблює, збережену семантику fail closed
  для EXPLICIT з відсутнім основним файлом (рядки H–J вище) —
  наявність чи відсутність `BRAVO.config.local` не рятує відсутній
  явно вибраний основний шлях, а недійсний `BRAVO.config.local`
  також ніколи не рятується наявністю валідного основного файлу.

### Схема v2

`configSchemaVersion` — це назва поля/семантичний ідентифікатор
маркера версії схеми. Оскільки завантажувач v2 парсить файл як
PowerShell AST/DATA, єдина канонічна серіалізована форма цього
маркера — `configSchemaVersion = 2` (PowerShell hashtable-присвоєння);
форма з двокрапкою (`configSchemaVersion: 2`) НЕ є валідним
PowerShell DATA-синтаксисом і ніде в цьому документі не позначає
фактичний вміст файлу v2 — серіалізатор повинен завжди emit-ити лише
форму зі знаком рівності, а класифікатор/парсер не повинен покладатися
на невалідний альтернативний запис із двокрапкою.

- явний маркер `configSchemaVersion = 2`, що перевіряється під час
  завантаження;
- невідомі ключі провалюють валідацію (fail-closed, а не
  warn-and-ignore);
- недійсні типи провалюють валідацію;
- масиви повністю замінюють відповідний масив за замовчуванням — **вже
  поведінка мердж-рушія Foundation сьогодні**; схема v2 повинна
  перенести це через новий декларативний шлях завантаження й повторно
  довести, а не реалізувати заново;
- явний порожній масив (`@()`) є валідним, навмисним перевизначенням
  — **уже приймається сьогодні** у мердж-рушії Foundation; схема v2
  повинна зберегти це й додати регресійне покриття для шляху
  завантаження v2;
- значення за замовчуванням `Limits.ExcludedDrives` дорівнює `@()` —
  **уже вбудоване значення за замовчуванням сьогодні**; схема v2 не
  повинна це регресувати.

### Канонічний конвеєр валідації v2

Канонічний конвеєр валідації для конфігурації v2 (застосовується як
під час поетапної конвертації у PR B, так і продакшн-завантажувачем
у PR C — див. «Рекомендований розподіл PR» нижче):

```text
текст → PowerShell parse → строга валідація дозволеного синтаксису → non-executing вилучення ДАНИХ →
валідація версії схеми → валідація невідомих ключів → валідація типів → мердж сирого шару →
похідні обчислення → перевірка ефективних інваріантів безпеки
```

Поетапне стейджування кандидата в PR B повинно проходити всі етапи
парсингу/схеми, застосовні до самостійного кандидата, перш ніж
називати його validated; продакшн-завантажувач у PR C повинен
викликати ту саму бібліотеку парсера/схеми — не другу, окрему
реалізацію.

### Міграція: конвертація проти активації

Міграція має дві окремі стадії, які не можна змішувати:

```text
CONVERSION:
legacy config -> validated staged v2 candidate

ACTIVATION:
staged v2 candidate -> active production v2 configuration
```

**Конвертація / стейджування (доступно починаючи з PR B):**

- `BRAVO_CONFIG_MIGRATE.ps1` (або еквівалентна канонічна точка входу
  для міграції, згідно з конвенціями точок входу репозиторію)
  конвертує лише поля, чия провенанс (provenance) доведена як
  специфічна для сайту згідно з контрактом провенансу нижче — а не
  просто «явно ідентифіковані» без визначення способу ідентифікації;
- виявлені/згенеровані значення ніколи не стають постійними
  перевизначеннями через міграцію;
- вихідний(і) legacy-файл(и) читаються, але ніколи не змінюються
  конвертацією;
- сконвертований кандидат записується в неактивне місце стейджування
  — шлях, який поточний продакшн-завантажувач не споживає — ніколи в
  активні продакшн-назви файлів `BRAVO.config` / `BRAVO.config.local`;
- проміжний кандидат валідується non-executing парсером PR A, тим
  самим валідатором схеми (див. «Канонічний конвеєр валідації v2»
  вище) і порівнюється з ефективною конфігурацією legacy на предмет
  еквівалентності, перш ніж вважатися валідним кандидатом;
- проміжний кандидат може бути відкинутий і перегенерований у
  будь-який момент без впливу на активну інсталяцію; вихідний файл,
  що передував міграції, залишається недоторканим, а не просто
  «збереженим як резервна копія»;
- сама конвертація ніколи не змінює те, що читає продакшн-завантажувач.

**Контракт провенансу перед фільтрацією legacy-полів.** Виконуваний
legacy `BRAVO.config` присвоює повну модель конфігурації через блоки
`$global:*` незалежно від того, чи оператор колись редагував
конкретне значення. Сам факт наявності присвоєння в файлі — це
**ідентичність знімку джерела (source snapshot identity)**, а НЕ
**походження поля (field provenance)**. Наявний хеш/базова лінія
джерела, що використовується захистом дрейфу шляху активації, доводить
лише, що джерело не змінилося ПІСЛЯ стейджування кандидата — він НЕ
доводить, які значення є оператор-вибраними перевизначеннями. PR B не
може одночасно (а) серіалізувати лише специфічні для сайту поля і (б)
довести ефективну еквівалентність, якщо просто діффити активний
legacy-файл проти довільного «поточного» набору значень за
замовчуванням: закріплення застарілих поставлених значень за
замовчуванням стає постійним, а немарковані реальні перевизначення
можуть бути втрачені.

*Джерела провенансу.* Міграція може класифікувати поле лише на основі
довірених доказів, таких як: (1) точна ідентичність лінії/релізу
legacy-конфігурації; (2) точна pristine поставлена базова лінія, що
відповідає доведеній лінії; (3) довірені метадані провенансу
інсталятора/updater'а, якщо такі метадані існують у майбутній
реалізації (**PLANNED/PROPOSED** — сьогодні не існує й не
стверджується як існуючий механізм); (4) явний вибір/підтвердження
міграції з боку оператора. Точні шляхи зберігання та назви полів —
деталь реалізації.

*Заборона порівняння з непов'язаним поточним значенням за
замовчуванням.* Визначення оператор-перевизначень шляхом простого
порівняння старого персистентного legacy-конфіга з поточним
`BRAVO.config` репозиторію, поточними значеннями за замовчуванням
пакета, цільовими значеннями за замовчуванням v2 чи значеннями за
замовчуванням останнього релізу — ЗАБОРОНЕНО, якщо ця база не доведена
як pristine базова лінія саме для тієї лінії legacy-конфігурації, що
мігрується. Інсталяція могла зберегти свій legacy `BRAVO.config` через
декілька оновлень toolkit-у. Тому **поточна версія пакета НЕ
дорівнює автоматично версії провенансу конфігурації**. Якщо лінію
неможливо довести: провенанс = AMBIGUOUS.

*Семантичне порівняння.* Там, де точний pristine провенанс доступний,
порівнюються нормалізовані семантичні legacy-поля, а не текстове
форматування/коментарі. Концептуальний конвеєр: активне legacy-джерело
→ виділена legacy-екстракція → нормалізована сира конфігурована модель
↔ відповідна pristine legacy-базова лінія → та сама сумісна
нормалізація → pristine сира конфігурована модель → порівняння
семантики полів → класифікація провенансу. Це виконується ДО
виявлення/деривації. Згенеровані/похідні значення лишаються
виключеними з постійних v2-перевизначень.

*Класифікація полів.* Кожне мігроване поле повинно завершитися одним
явним класом: PROVEN OPERATOR / LOCAL DEVIATION; PROVEN SHIPPED
DEFAULT; DERIVED / GENERATED; EXPLICITLY CONFIRMED BY OPERATOR;
AMBIGUOUS (точні назви enum — деталь реалізації). Правила: активне
семантичне значення відрізняється від точної доведеної pristine
базової лінії ⇒ кандидат на локальне відхилення (local deviation);
активне значення дорівнює точній доведеній pristine базовій лінії ⇒
кандидат на shipped-default — якщо тільки довірений явний провенанс
оператора не каже, що значення навмисно закріплене як перевизначення.
Згенеровані/похідні поля НІКОЛИ не серіалізуються лише тому, що вони
з'являються в ефективному legacy-стані. Неоднозначні поля НІКОЛИ не
вгадуються мовчки.

*Неоднозначний провенанс.* Якщо довірена лінія/pristine базова лінія
недоступна: НЕОБСЛУГОВУВАНА (unattended) автоматична фільтрація
ПОВИННА fail closed. PR B усе ще може випустити dry-run/звіт, що
показує поле, ефективне/сире legacy-значення, статус провенансу,
причину неоднозначності й кандидатську дію — але не повинен мовчки
вирішувати «перевизначення проти shipped-default». Обов'язковий
безпечний шлях: оператор явно переглядає/підтверджує вибір поля →
кандидат перегенерується → звичайна валідація парсера/схеми/
безпеки/еквівалентності. Жоден неоднозначний непідтверджений кандидат
не може стати eligible для активації.

*Дрейф значення за замовчуванням між релізами.* Якщо стара доведена
поставлена база за замовчуванням відрізняється від цільового
значення за замовчуванням v2 — це повинно бути явно повідомлене як
delta міграції, а не мовчки вирішене на користь «закріпити старе
назавжди» чи «мовчки прийняти нову поведінку». Оператор-володіні/
доведені значення перевизначень повинні зберігатися точно; доведені
shipped-default значення зазвичай лишаються опущеними як
перевизначення; але розбіжність між старою поставленою базою й
цільовим значенням за замовчуванням v2 повинна бути покрита або
задокументованою продуктовою політикою міграції, або явним
підтвердженням/вибором оператора — до активації.

*Уточнення «ефективної еквівалентності».* Твердження про повну
«еквівалентність» стейджованого v2-кандидата ефективній legacy-
конфігурації уточнюється так: усі доведені/підтверджені
оператор-контрольовані значення вимагають точного семантичного
збереження; згенеровані/похідні значення повторно виводяться за
канонічними правилами v2, а не персистуються; shipped-default значення
підпорядковуються політиці провенансу/дрейфу за замовчуванням вище.
Якщо стара поставлена база за замовчуванням == цільова база за
замовчуванням v2 — опущення зберігає ефективну еквівалентність. Якщо
вони відрізняються — потрібна явна обробка delta міграції перед
активацією. Це усуває контраст, де shipped-defaults навмисно
опускаються, але водночас нібито кожне старе ефективне
shipped-default значення мало б завжди серіалізуватися/зберігатися.

*Метадані кандидата.* Неактивний стейджований кандидат/звіт міграції
повинен нести достатню ідентичність провенансу, щоб запобігти пізнішій
активації проти іншого джерела/базової лінії — концептуально:
ідентичність/хеш legacy-джерела, ідентичність провенансу/базової лінії
legacy, ідентичність цільової схеми/значень за замовчуванням,
ідентичність підтвердження оператора (якщо вимагається), ідентичність/
хеш кандидата (точні назви полів — деталь реалізації). Захист дрейфу
шляху активації повинен перевіряти, що ці ідентичності не зазнали
дрейфу. Не плутати це з журналом міграції, що використовується під
час активації PR D.

**Активація (доступно починаючи з PR D, явно контрольована — див.
«Активація міграції та відкат» нижче):**

- просуває валідованого проміжного кандидата в активну конфігурацію
  за ефективним активним основним шляхом (див. «Ефективний активний
  основний шлях» нижче) — не обов'язково за фіксованими назвами
  файлів `BRAVO.config` / `BRAVO.config.local`;
- вимагає, щоб двоформатний зчитувач PR C уже був присутній у
  запущеній інсталяції;
- є окремою, пізнішою, явно контрольованою операцією — сама
  конвертація (PR B) не надає можливості активації;
- метадані проміжного кандидата фіксують достатньо ідентифікаційної
  інформації, щоб запобігти активації проти неправильної цілі, як
  мінімум: намір AUTO-проти-EXPLICIT `-ConfigPath`, точний розв'язаний
  ефективний основний шлях, ефективний каталог конфігурації, шлях
  legacy-local за наявності, цільовий шлях v2-local за застосовності,
  базову лінію джерела/хеш (або еквівалентну ідентичність дрейфу) та
  ідентичність/хеш кандидата — точні назви полів є деталлю реалізації,
  а не фіксуються цим документом.

### Ефективний активний основний шлях (AUTO проти EXPLICIT)

Міграція та активація повинні визначатися в термінах **ефективного
активного основного шляху конфігурації**, а не припущення, що
основний файл завжди `<ConfigRoot>\BRAVO.config`. Наявний контракт
AUTO/EXPLICIT для `-ConfigPath` (`BRAVO_SETUP.ps1`, визначення
завдань Task Scheduler, `BRAVO_CONFIGURATOR.ps1`) уже розрізняє два
режими, і міграція повинна зберігати цю відмінність:

**Режим AUTO** — оператор явно не вказав `-ConfigPath`:

```text
effective primary path = <ConfigRoot>\BRAVO.config
```

якщо основне перевизначення взагалі існує (воно залишається
опціональним).

**Режим EXPLICIT** — оператор явно вказав `-ConfigPath <шлях>`
(наприклад, `C:\BRAVO\CONFIGS\SERVER1.config`): точний розв'язаний
шлях є наміром оператора й **повинен залишатися активним основним
шляхом протягом усієї міграції**. Він не повинен мовчки
перетворюватися на `<RuntimeRoot>\BRAVO.config` чи
`<ConfigRoot>\BRAVO.config`.

**Бажана канонічна модель активації — зберегти шлях, змінити
формат:**

```text
застарілі (legacy) дані/код за точним ефективним шляхом
    -> міграція ->
дані v2 за ТИМ САМИМ точним ефективним шляхом
```

Назва файлу/шлях не визначає legacy проти v2 — це робить визначення
формату/схеми (див. «Активний режим набору конфігурації» вище), а
PR C вже визначено як двоформатний зчитувач. Тому активація зазвичай
**не повинна** вимагати перенацілення запланованих завдань чи
лаунчерів. Керівний принцип: **міграція змінює формат/вміст активної
конфігурації, а не явний намір оператора щодо основного шляху.**

Машинно-локальне перевизначення v2 слідує тому ж ефективному каталогу
конфігурації, що й сьогодні: для явного основного шляху
`C:\BRAVO\CONFIGS\SERVER1.config` відповідний `BRAVO.config.local`
(за використання) розв'язується з
`C:\BRAVO\CONFIGS\BRAVO.config.local`, згідно з контрактом імені
локального файлу v2 — він не переноситься мовчки в `RuntimeRoot`. Для
режиму AUTO/без-основного-файлу застосовується задокументована
поведінка на основі `ConfigRoot`. `RuntimeRoot` не обов'язково є
`ConfigRoot`, а `ConfigRoot` не обов'язково є каталогом, що мається
на увазі місцем розташування пакета; міграція повинна зберігати
ефективне розташування конфігурації.

Після активації кожен наявний персистентний споживач повинен і надалі
розв'язувати активну конфігурацію v2: точний `-ConfigPath`
запланованого завдання, точний `-ConfigPath` ручного лаунчера та
будь-який інший персистентний споживач залишаються незмінними,
оскільки той самий ефективний основний шлях тепер містить ДАНІ v2.
Якщо майбутня реалізація натомість обере перенацілення шляху, це
інший, ризикованіший дизайн, і вона ПОВИННА атомарно оновити кожного
персистентного споживача всередині захищеної відкатом транзакції
активації (див. «Активація міграції та відкат» нижче) — перенацілення
не є бажаним/дизайном за замовчуванням.

### Збереження при оновленні (updater preservation)

- оновлення/апгрейд toolkit на місці ніколи не повинне мовчки
  перезаписувати, знищувати чи пошкоджувати жоден з двох файлів
  перевизначення v2 — `BRAVO.config` (перевизначення
  сайту/розгортання) чи `BRAVO.config.local` (машинно-локальне
  перевизначення) — а також, протягом перехідного вікна, legacy
  `BRAVO.local.config`. Обидва файли v2 є шарами перевизначення, що
  належать користувачу, а не вмістом, що постачається пакетом, і
  пакет ніколи не повинен скидати їх до заводських значень за
  замовчуванням під час оновлення;
- виконуваний legacy `BRAVO.config` ніколи не повинен мовчки
  замінюватися пакетним v2 `BRAVO.config` до того, як резервне
  копіювання/міграція/обробка сумісності безпечно з ним впораються —
  оновлення не повинне перезаписувати наявний файл конфігурації сайту
  лише тому, що пакет постачає новий файл за замовчуванням;
- це повинно бути покрите явними регресійними випадками, а не лише
  задокументоване як очікування, включно як мінімум із:
  1. v2 `BRAVO.config` переживає оновлення без змін;
  2. v2 `BRAVO.config.local` переживає оновлення без змін;
  3. legacy `BRAVO.local.config` переживає перехід/оновлення без змін,
     доки не буде явно мігрований;
  4. виконуваний legacy `BRAVO.config` ніколи мовчки не замінюється
     пакетним v2-файлом.

Рутинні оновлення пакета на місці (не активація міграції) ніколи не
змінюють активний режим набору конфігурації; транзакція резервного
копіювання/відкату, описана в «Активація міграції та відкат» нижче,
стосується саме активації міграції, а не кожного оновлення.

### Активація міграції та відкат (PR D)

Активація просуває валідованого проміжного кандидата v2 (див.
«Міграція: конвертація проти активації» вище) у діючий набір
конфігурації, за ефективним активним основним шляхом (див.
«Ефективний активний основний шлях» вище) — вона не припускає, що
основний файл завжди `<ConfigRoot>\BRAVO.config`. Вона оперує повним
набором конфігурації як однією транзакцією, ніколи файл-за-файлом за
принципом best effort, і повинна переживати раптове переривання
(вбивство процесу, аварію хоста, перезавантаження, втрату живлення),
а не лише перехоплені в процесі збої.

**Синхронізація читання та активації (контракт блокування) — закриває
вікно TOCTOU.** Між попередньою перевіркою відновлення (recovery
preflight) та фактичним початком активації існує вікно стану гонки:
звичайний читач може пройти перевірку наявності незавершеного журналу,
а потім активація почне просування саме в той момент, коли читач
зчитує проміжний, наполовину просунутий стан. Сама наявність журналу
не є достатнім механізмом синхронізації для закриття цього вікна.
Явний контракт спільного читача / ексклюзивного writer'а обов'язковий:

- **звичайний завантажувач:** перед попередньою перевіркою
  відновлення та перед читанням/класифікацією активної конфігурації
  отримує спільну/read-side транзакційну блокування конфігурації
  (shared/read-side configuration transaction lock). Утримує це
  блокування безперервно протягом: перевірки стану відновлення,
  визначення формату, класифікації набору конфігурації, вилучення
  конфігурації, захоплення вхідних даних для мерджу. Звільняє
  блокування лише після отримання одного узгодженого незмінного
  знімку (snapshot) конфігурації;
- **активація/відновлення:** вимагає ексклюзивної/write-side
  блокування (exclusive/write-side lock), яка конфліктує з кожним
  звичайним читачем. Активація не повинна починати просування, доки
  будь-який уже наявний звичайний читач утримує спільне блокування.
  Жоден новий звичайний читач не може увійти, доки активація/
  відновлення володіє ексклюзивним блокуванням;
- це закриває гонку: попередня перевірка читача → активація
  починається → читач читає посеред просування;
- не покладатися лише на наявність журналу як на механізм
  синхронізації.

**Канонічний порядок отримання блокування** (щоб уникнути
гонок/дедлоків):

Звичайне завантаження:
1. отримати спільне/read блокування;
2. перевірити журнал міграції/стан відновлення;
3. якщо потрібне відновлення: звільнити/підвищити відповідно до
   канонічного шляху відновлення (відновлення отримує ексклюзивне
   володіння);
4. інакше прочитати/класифікувати/вилучити узгоджену конфігурацію;
5. звільнити спільне блокування.

Активація/відновлення:
1. отримати ексклюзивну транзакційну блокування;
2. перевірити володіння журналом/транзакцією;
3. виконати транзакцію/відновлення;
4. звільнити лише після досягнення стабільного узгодженого режиму.

Не вигадувати небезпечне підвищення блокування (lock upgrade), що
призводить до дедлоку — якщо підвищення не може бути атомарним:
звільнити спільне блокування, отримати ексклюзивне блокування,
повторно перевірити журнал/стан з нуля.

**Активація на основі перевірки шляху (виконується перед усім
іншим):** перед зміною будь-якого активного файлу активація
перевіряє:

- поточний ефективний основний шлях усе ще відповідає ефективному
  основному шляху, зафіксованому в цілі проміжної міграції;
- намір AUTO/EXPLICIT `-ConfigPath` не змінився з моменту
  стейджування;
- вихідна legacy-конфігурація не зазнала дрейфу з моменту генерації
  кандидата (збіг базової лінії/хешу);
- очікувана ідентичність локальної конфігурації не змінилася;
- кандидат належить саме цій цілі активації.

Будь-яка невідповідність **fail closed** — активація не
продовжується, і оператор повинен перегенерувати/повторно валідувати
кандидата.

**Довговічний write-ahead журнал активації.** Оскільки перехоплений
`try`/`catch`/`finally` не може захистити від завершення процесу,
аварії хоста, перезавантаження чи втрати живлення між мутаціями
файлів, активація використовує довговічний write-ahead журнал, що
зберігається поза файлами, які просуваються, у захищеному місці
рантайм/стану (точний постійний шлях є деталлю реалізації канонічного
кореня стану міграції, не фіксується цим документом). Журнал
концептуально фіксує: ID активації; ідентичність цільового
хоста/інсталяції; намір AUTO/EXPLICIT `-ConfigPath`; точний активний
основний шлях; стан активного локального шляху; ідентичність набору
резервної копії; ідентичність набору кандидата; поточну фазу/стан
активації; а також мітки часу/версію/схему за потреби. Точні назви
полів є деталлю реалізації.

**Контекст авторизованої перевірки власника активації (Fix B).**
Активація вже володіє ексклюзивною транзакційною блокуванням. Журнал
містить ID активації / ідентичність транзакції. Виклик верифікації
повинен нести ту саму ідентичність транзакції/здатність (capability),
що й активна транзакція. Завантажувач перевіряє: ексклюзивне
блокування належить саме цій транзакції; ID активації збігається з
власником журналу; фаза журналу явно дозволяє верифікацію власником.
Лише тоді верифікація, що належить активації, може інспектувати щойно
просунутий набір v2, не запускаючи rollback-first відновлення проти
самої себе. Звичайні процеси НЕ ПОВИННІ мати можливість запросити чи
обійти цей режим просто встановивши звичайний CLI-прапорець/змінну
середовища — це внутрішня довірена транзакційна можливість (trusted
transaction capability). Якщо володіння не може бути доведене: FAIL
CLOSED, без обхідних шляхів. Шлях верифікації власником НЕ ПОВИНЕН
послаблювати валідацію — він використовує ТОЙ САМИЙ парсер v2,
валідатор схеми, перевірку типів, класифікацію режиму, семантику
мерджу, інваріанти безпеки та перевірки ефективної конфігурації, що й
звичайне продакшн-завантаження. Лише попередня перевірка «неповний
власний журнал активації означає відкат» є транзакційно-обізнаною
(transaction-aware). Не створювати другу, слабшу реалізацію
валідації.

**Необхідний порядок транзакції:**

1. отримати ексклюзивне володіння транзакцією;
2. перевірити поточний активний набір legacy;
3. перевірити повний проміжний кандидат v2;
4. перевірка на дрейф шляху/наміру/джерела (activation path guard);
5. створити повну резервну копію активного набору та перевірити
   резервну копію;
6. довговічно створити write-ahead журнал;
7. просунути набір кандидата через write-ahead переходи фаз;
8. забезпечити узгоджений активний набір v2 без конфліктів;
9. авторизована власником, продакшн-еквівалентна перевірка (це
   контекст верифікації Fix B вище);
10. перевірка ефективної еквівалентності/безпеки/персистентних
    споживачів;
11. довговічно записати фазу `Committed`;
12. усиновлення (adoption) тепер підтверджене фактом `Committed`;
13. опціональні похідні метадані усиновлення можуть бути
    записані/узгоджені;
14. відкладене очищення згідно з політикою зберігання;
15. звільнити ексклюзивне володіння.

**Канонічне авторитетне правило стану підтвердження/усиновлення
(Fix C).** Довговічний журнал, що досягає фази `Committed`, є
авторитетним атомарним сигналом усиновлення (adoption) міграції.
Порядок: успішна верифікація → довговічно зберегти `Committed` →
похідно виставити/деривувати adoption=confirmed САМЕ З `Committed`.
Якщо існує окремий індекс/маркер усиновлення для операційного
пошуку, це похідний стан, а не авторитет, і він може бути
персистований лише ПІСЛЯ `Committed`; відновлення повинне узгоджувати
його з авторитетного журналу. Обов'язковий інваріант: якщо журнал !=
`Committed`, інсталяція НЕ є довговічно усиновленою. Аварія до
`Committed` ⇒ обробляється за точною розбивкою фаз нижче (не кожна
pre-commit невдача означає повне відновлення активного набору —
див. «Відкат до `Committed`» нижче); усиновлення не підтверджене,
доки `Committed` не досягнуто. Аварія після `Committed`, але до
оновлення похідного маркера ⇒ конфігурація залишається усиновленою,
похідний маркер відновлюється з `Committed`. Ніякого «розщеплення
мозку» (split-brain) не допускається.

**Відкат до `Committed` (pre-commit failure) — точна розбивка фаз.**
Неправильно трактувати БУДЬ-ЯКУ невдачу кроків 1–10 як таку, що
вимагає відновлення повного попереднього набору конфігурації:
відновлення активного набору можливе лише тоді, коли справді існує
верифіковане джерело відкату (резервна копія) І мутація активного
набору вже почалася чи могла початися. До того — немає що
відновлювати, і немає з чого. Розбивка за фазами:

- **PRE-MUTATION PREFLIGHT** (крок 1: отримання ексклюзивного
  володіння). Якщо ексклюзивне володіння транзакцією не отримано:
  НЕМАЄ володіння транзакцією, НЕМАЄ активної мутації, НЕМАЄ
  відкату — це FAIL/ABORT, а не подія відкату. Забороняється
  ініціювати відновлення чи відкат без володіння необхідним
  ексклюзивним транзакційним блокуванням. Невдача отримання
  блокування **не є** подією rollback;
- **PRE-MUTATION PREFLIGHT** (кроки 2–4: перевірка активного
  legacy-набору, перевірка проміжного кандидата v2, перевірка
  дрейфу шляху/наміру/джерела). До того, як існує верифікована
  резервна копія, і до будь-якої мутації активного файлу: FAIL
  CLOSED, ABORT ACTIVATION, активна конфігурація лишається
  НЕЗМІННОЮ, операція ВІДНОВЛЕННЯ НЕ виконується. Ексклюзивне
  володіння звільняється звичайним чином після досягнення
  стабільного стану невдачі. Не вигадувати фіктивну вимогу відкату
  для активного набору, який ніколи не змінювався;
- **BACKUP PREPARATION** (крок 5: створення й перевірка повної
  резервної копії). Резервна копія стає валідним джерелом відкату
  лише ПІСЛЯ того, як повний набір резервної копії створено І
  перевірено. Якщо створення чи перевірка резервної копії
  провалюється: активна конфігурація МАЄ лишатися незмінною;
  НЕПОВНА/НЕПЕРЕВІРЕНА резервна копія НІКОЛИ НЕ використовується як
  джерело відновлення. Активація переривається. Частковий артефакт
  резервної копії може бути збережений для діагностики чи безпечно
  очищений згідно з політикою реалізації, але він не є авторитетним
  матеріалом для відновлення;
- **JOURNAL PREPARATION** (крок 6: довговічне створення write-ahead
  журналу). Мутація активного набору не повинна починатися, доки не
  існують ОДНОЧАСНО: верифікована повна резервна копія І довговічний
  write-ahead журнал. Якщо створення журналу не може бути довговічно
  завершене: активна конфігурація МАЄ лишатися незмінною, ABORT,
  ВІДНОВЛЕННЯ АКТИВНОГО НАБОРУ НЕ ПОТРІБНЕ. Верифікована резервна
  копія може лишитися невикористаним артефактом відновлення, але
  активація не повинна продовжуватися;
- **MUTATION-МЕЖА.** Явна концептуальна межа: «МУТАЦІЯ НЕ
  РОЗПОЧАТА» проти «МУТАЦІЯ МОГЛА РОЗПОЧАТИСЯ». Довговічний журнал
  повинен містити достатньо інформації про фазу/стан, щоб відновлення
  могло розрізнити ці два випадки (точні назви фаз — деталь
  реалізації). Обов'язковий порядок: верифікована резервна копія →
  підготовлений довговічний журнал → стан журналу дозволяє мутацію →
  перша активна мутація. Ніколи навпаки: спочатку мутація, а потім
  виявлення, що резервна копія/журнал були недійсними;
- **ACTIVE MUTATION** (кроки 7–10: просування кандидата, узгоджений
  активний набір v2, авторизована власником перевірка, перевірка
  ефективної еквівалентності/персистентних споживачів). Лише коли
  ОДНОЧАСНО існують: верифіковане джерело відкату, довговічна
  ідентичність транзакції/журнал, і активна мутація вже почалася чи
  могла початися — застосовується rollback-first відновлення повного
  попереднього набору конфігурації. Для pre-`Committed` невдачі на
  цій фазі: відновити повний попередній набір під ексклюзивним
  володінням, використовуючи верифіковану резервну копію, пов'язану
  саме з цією транзакцією — ніколи частковий відкат, ніколи
  резервна копія з іншої транзакції, ніколи вгадана резервна копія.
  Відновлення на рівні набору відновлює один узгоджений попередній
  режим (наприклад, «legacy-основний + legacy-локальний»
  відновлюється разом, якщо це був стан до міграції), ніколи
  частковий змішаний результат. Відкат ніколи не повинен залишати
  одночасно активними і `BRAVO.local.config`, і `BRAVO.config.local`,
  окрім випадку, коли один з них перебуває лише в явно неактивній
  зоні резервної копії/стейджування. Транзакція лишається НЕ
  усиновленою.

**Відновлення після аварії/перезавантаження для pre-commit фаз.**
Відновлення повинне fail closed, якщо не може довести: ідентичність
транзакції; ексклюзивне володіння; ідентичність верифікованої
резервної копії; стан журналу; зв'язок між резервною копією й
транзакцією. Якщо журнал вказує, що мутація могла початися, але
пов'язана з нею верифікована резервна копія відсутня/пошкоджена/
неперевірювана: FAIL CLOSED, зберегти наявні докази, вимагати
оператора/задокументований шлях відновлення — НІКОЛИ не вгадувати
іншу резервну копію, не продовжувати звичайне завантаження, не
виконувати best-effort частковий відкат. Якщо стан довговічного
журналу доводить, що активна мутація ніколи не починалася —
відновлення активного набору НЕ потрібне; відновлення може
завершити/очистити покинуту підготовлену транзакцію згідно з
задокументованою політикою.

**`Committed` — точка неповернення для усиновлення (post-commit
failure).** Щойно фаза `Committed` довговічно записана (крок 11),
БЕЗ ВІДКОТУ ДО LEGACY. Це застосовується до будь-якої невдачі ПІСЛЯ
цієї точки, включно з:

- відновленням/ремонтом похідного підтвердження чи маркера
  усиновлення;
- опціональним узгодженням похідних метаданих усиновлення (крок 13);
- відкладеним очищенням (крок 14);
- очищенням legacy-резервної копії;
- іншим явно post-commit господарським очищенням.

Жодна з цих невдач НЕ повинна відновлювати старий (legacy) набір
конфігурації. Натомість:

- активна v2-конфігурація лишається авторитетною;
- журнал лишається `Committed`;
- невдача звітується як відновлювана (repairable) post-commit
  помилка метаданих/очищення, а не як провал транзакції усиновлення;
- похідний маркер може бути пересозданий/відремонтований з
  `Committed`;
- очищення є ідемпотентно повторюваним під час пізнішого
  обслуговування/відновлення;
- звичайне відновлення НІКОЛИ не повинне робити висновок «не
  усиновлено» з відсутності чи невдачі похідних метаданих, коли
  журнал перебуває у стані `Committed`.

Це узгоджується з інваріантом Fix C вище ("якщо журнал != `Committed`,
інсталяція НЕ усиновлена" має зворотний бік: коли журнал ==
`Committed`, інсталяція Є усиновленою, і жодна post-commit
господарська невдача цього не скасовує).

**Відновлення після аварії/перезавантаження незалежне від пам'яті
процесу.** Відновлення повинне коректно працювати з абсолютно нового
процесу й не повинне залежати від `catch`/`finally`, змінних у
пам'яті чи того, що оригінальний процес PowerShell усе ще працює.
Перш ніж звичайний шлях класифікації режиму конфігурації/мерджу
споживає активні файли, попередня перевірка відновлення міграції
перевіряє наявність незавершеного журналу активації; якщо такий
існує, першим запускається відновлення — звичайний завантажувач
ніколи не повинен просто натрапити на наполовину просунуту змішану
конфігурацію й трактувати це як звичайну помилку оператора. Політика
— **rollback-first**: для будь-якої незавершеної/незафіксованої
активації повний попередній активний набір конфігурації відновлюється
з перевіреної резервної копії, після чого відновлений набір повторно
валідується як один узгоджений підтримуваний режим (див. «Активний
режим набору конфігурації» вище). Лише після завершення відновлення
може продовжуватися звичайне завантаження.

**Невдача відновлення fail closed.** Якщо відновлення не може
безпечно відновити попередній повний набір конфігурації, воно fail
closed: не вгадує пріоритет, не видаляє журнал чи резервні копії, не
продовжує частково, показує конкретну помилку відновлення міграції
та зберігає криміналістичні докази/докази для відновлення.

**Єдиний writer (single writer).** Активація та відновлення не
повинні виконуватися одночасно. Одна інсталяція може мати щонайбільше
одну активну транзакцію міграції одночасно, використовуючи
канонічний загальномашинний підхід блокування/стану репозиторію, коли
той реалізований; якщо інша активація/відновлення вже володіє
транзакцією, нова fail closed як «зайнято», а не починає другу
міграцію. Цей контракт єдиного writer'а доповнюється явним контрактом
блокування читач/writer вище (Fix A): звичайні читачі можуть
співіснувати між собою через спільне блокування, але жоден читач не
може співіснувати з ексклюзивним writer'ом активації/відновлення.

**Відновлення ідемпотентне.** Відновлення повинне бути безпечним для
повторного запуску — якщо саме відновлення перерване, наступний
виклик відновлення повинен усе одно безпечно збігтися, і жодна
повторна спроба відновлення не може пошкодити останню перевірену
резервну копію.

### Регресійні вимоги / вимоги Definition-of-Done

Перш ніж Configuration v2 можна позначити завершеним у `ROADMAP.md`,
повинні існувати й проходити такі перевірки:

- тест на відхилення невідомих ключів (новий для v2);
- тест на відхилення невідповідності типів (новий для v2);
- тест «заміна масиву, а не мердж» **на декларативному шляху
  завантаження v2** (базова семантика вже існує й уже протестована
  для сьогоднішнього мердж-рушія Foundation — цей пункт про повторне
  доведення, що вона переживає перехід на парсер v2, а не про
  винайдення її заново);
- тест обробки значень, що допускають null (новий для v2);
- тест «явний порожній масив є валідним перевизначенням» **на
  декларативному шляху завантаження v2** (те саме застереження, що й
  вище для заміни масивів);
- тест на відхилення пониження безпеки (віддзеркалює вже реалізований
  інваріант P0 Foundation, повторно перевірений проти шляху схеми v2);
- тест еквівалентності legacy-проти-v2 щонайменше на одній
  нетривіальній контрольній фікстурі;
- покриття контракту провенансу міграції (див. «Контракт провенансу
  перед фільтрацією legacy-полів» вище):
  - відома точна pristine база + поле відрізняється ⇒ поле
    зберігається як локальне відхилення;
  - відома точна pristine база + поле незмінне ⇒ поле опускається як
    shipped-default;
  - незмінне базове значення + довірений явний pin оператора ⇒ поле
    зберігається;
  - згенероване/виявлене legacy-значення ⇒ не персистується;
  - лінія джерела legacy невідома ⇒ неконтрольована (unattended)
    міграція заблокована як неоднозначна;
  - legacy-конфіг персистований через кілька оновлень + доступна лише
    поточна база пакета ⇒ поточна база НЕ повинна вважатися
    провенансом;
  - старий shipped-default == цільовий v2-default ⇒ опущення зберігає
    ефективне значення;
  - старий shipped-default != цільовий v2-default ⇒ вимагається явна
    обробка delta міграції;
  - підтверджене оператором неоднозначне поле ⇒ кандидат може бути
    перегенерований і провалідований;
  - джерело/базова лінія змінюються після стейджування ⇒ активація
    відхиляється захистом дрейфу;
- доказ non-invocation: тест, що демонструє, що шкідливий або
  пошкоджений файл конфігурації v2 не може спричинити виконання коду,
  навіть якщо він містить синтаксично правдоподібний PowerShell поза
  межами літеральних даних — тобто доведення властивості 4 вимоги до
  безпечного парсера, а не лише того, що невалідний синтаксис
  відхиляється;
- доказ fail-closed-no-fallback: тест, що демонструє, що файл, який
  декларує `configSchemaVersion = 2` і не проходить валідацію v2,
  відхиляється прямо й ніколи мовчки не відкочується до виконуваного
  legacy-завантажувача;
- покриття активного режиму набору конфігурації (див. «Активний
  режим набору конфігурації» вище), що охоплює всі сім підтримуваних
  комбінацій, три нові комбінації EXPLICIT-з-відсутнім-основним-файлом
  (Fix D нижче) і всі десять fail-closed комбінацій, перелічених
  там (5 початкових змішаних/невідомих режимів + 5 комбінацій
  недійсного `BRAVO.config.local`);
- регресійні випадки для матриці AUTO проти EXPLICIT (Fix D):
  - AUTO + основний файл відсутній + немає локального => підтримується,
    лише built-in;
  - AUTO + основний файл відсутній + є legacy-локальний =>
    підтримується, лише legacy-local;
  - AUTO + основний файл відсутній + є v2-локальний => підтримується,
    лише v2-local;
  - EXPLICIT + основний файл відсутній + немає локального => fail
    closed;
  - EXPLICIT + основний файл відсутній + є legacy-локальний => fail
    closed;
  - EXPLICIT + основний файл відсутній + є v2-локальний => fail
    closed;
- покриття стейджування/активації міграції:
  - стейджування PR B залишає кожен живий файл конфігурації побайтово
    незмінним;
  - проміжний кандидат v2 не виявляється продакшн-завантажувачем
    legacy;
  - активація PR D просуває повний, узгоджений набір v2;
  - невдача активації відновлює повний попередній набір legacy;
  - відкат не може залишити активними обидві локальні назви файлів
    одночасно;
  - невалідний v2 ніколи не відкочується до legacy-виконання,
    повторно перевірено на рівні набору конфігурації, а не лише на
    рівні одного файлу;
  - міграція з явним зовнішнім `-ConfigPath` (EXPLICIT) зберігає
    точний шлях; командний рядок запланованого завдання, що містить
    `-ConfigPath "<explicit path>"`, незмінний після успішної
    активації, що зберігає шлях; ручний лаунчер, що використовує
    явний ефективний шлях конфігурації, залишається валідним;
    основний файл v2 завантажується саме з цього явного шляху після
    активації; локальне перевизначення v2 розв'язується поряд з
    ефективною конфігурацією згідно з контрактом локального файлу v2;
  - активація відхиляє проміжного кандидата, коли ефективний
    `-ConfigPath` чи базова лінія джерела змінилися після стейджування
    (activation path guard вище);
  - режим AUTO залишається канонічним і не порушується захистом
    EXPLICIT-шляху;
  - покриття синхронізації читача/writer'а та відновлення TOCTOU
    (Fix A): звичайний читач, що отримав спільне блокування до старту
    активації, не бачить наполовину просунутого стану; активація не
    починає просування, доки не звільниться будь-яке наявне спільне
    блокування; жоден новий читач не входить, доки триває активація/
    відновлення;
  - покриття верифікації власника активації (Fix B): неавторизований
    виклик без дійсної ідентичності транзакції відхиляється fail
    closed; авторизована власником верифікація використовує ту саму
    реалізацію валідації, що й звичайне завантаження, і не запускає
    rollback-first відновлення проти власної щойно просунутої
    транзакції;
  - покриття авторитетного стану `Committed`/усиновлення (Fix C):
    аварія до `Committed` залишає усиновлення непідтвердженим і
    відновлює legacy; аварія після `Committed`, але до оновлення
    похідного маркера, залишає конфігурацію усиновленою й відновлює
    похідний маркер з журналу;
  - покриття переривання/відновлення після аварії: раптове
    переривання, ін'єктоване (1) після створення журналу, але до
    будь-якої мутації активного файлу, (2) після просування основного
    файлу, але до просування локального, (3) під час або після
    просування локального v2, (4) до/після виведення з експлуатації
    legacy-локального, (5) після всіх просувань файлів, але до
    верифікації v2, (6) після верифікації, але до маркера `Committed`,
    і (7) під час оновлення самого довговічного журналу — після
    симульованого перезапуску/відновлення кожен випадок повинен
    довести: відновлення не залежить від пам'яті старого процесу;
    відновлюється (чи, для випадку (1), лишається незміненим — див.
    застереження нижче) один узгоджений підтримуваний режим
    конфігурації; жоден змішаний режим legacy/v2 не стає видимим для
    звичайного завантаження; явний ефективний `-ConfigPath`
    зберігається; заплановані/персистентні споживачі все ще
    націлені на валідну конфігурацію; резервна копія/журнал
    залишаються, якщо відновлення зазнає невдачі; а успішне
    відновлення ідемпотентне. **Застереження для випадку (1)** (узгоджено
    з «Відкат до `Committed` — точна розбивка фаз» нижче): якщо
    відновлення доводить із довговічного журналу, що жодна активна
    мутація файлу не почалася, воно НЕ відновлює/не змінює активні
    файли — коєрентний активний набір, що вже існував до спроби
    активації, лишається недоторканим як є. Це не суперечність із
    «відновлюється узгоджений режим» вище: властивість задовольняється
    тривіально, оскільки набір, що лишається недоторканим, сам є тим
    єдиним узгодженим підтримуваним режимом. Відновлення/заміна файлів
    із резервної копії застосовується лише до випадків (2)–(7), де
    мутація активного файлу вже почалася чи могла початися;
  - ідемпотентність відновлення: саме відновлення перерване, і
    наступний виклик відновлення все одно безпечно збігається без
    пошкодження останньої перевіреної резервної копії;
- покриття точної розбивки фаз відкату (див. «Відкат до `Committed`
  — точна розбивка фаз» вище):
  - крок 1 (отримання ексклюзивного володіння) провалюється ⇒ ABORT
    без спроби відкату — це НЕ подія rollback;
  - крок 2/3/4 (preflight-перевірки) провалюється ⇒ активний набір
    лишається незмінним, ВІДНОВЛЕННЯ НЕ виконується;
  - створення резервної копії провалюється ⇒ активний набір
    незмінний, неповна резервна копія ніколи не використовується як
    джерело відновлення;
  - перевірка резервної копії провалюється ⇒ активний набір
    незмінний, неперевірена резервна копія ніколи не використовується
    як джерело відновлення;
  - створення довговічного журналу провалюється до початку активної
    мутації ⇒ ABORT, відновлення активного набору НЕ потрібне;
  - аварія після довговічного створення журналу, але до активної
    мутації ⇒ відновлення доводить, що мутації не було, і не вимагає
    відновлення активних файлів;
  - невдача/аварія після першої активної мутації, але до `Committed`
    ⇒ повний попередній набір відновлюється з верифікованої резервної
    копії саме цієї транзакції;
  - журнал mutation-фази посилається на відсутню/пошкоджену резервну
    копію ⇒ fail closed, жодної вгаданої резервної копії;
  - невдача після `Committed` ⇒ без відкату до legacy (незмінний
    інваріант Fix C вище);
- прийняття збереження при оновленні (не вимагає real-server
  acceptance для того, щоб бути задокументованим як «done» на рівні
  кодової регресії, але real-server acceptance вимагається до того,
  як це буде описано як доведене в продакшні, згідно з політикою
  валідації репозиторію).

### Рекомендований розподіл PR

Віддзеркалює прецедент P0 Foundation (PR A/B/C) за духом, але додає
окремий PR для міграції, відокремлює безпечний парсер від переходу
завантажувача та розділяє «v2 стає доступним» від «legacy нарешті
видалено» на два окремо контрольовані етапи — щоб найризикованіші
частини (ніколи не викликати недовірений текст конфігурації, і
залишити немігровану інсталяцію без підтримки) можна було переглянути
й протестувати окремо, перш ніж щось від них залежатиме.

**Обмеження порядку (чому міграція йде перед переходом):** наявна
інсталяція все ще може мати виконуваний legacy `BRAVO.config` на
момент злиття будь-якого з цих PR. Якби продакшн-завантажувач
перестав приймати legacy-формат (остаточний перехід, див. PR E
нижче) до появи підтримуваного шляху міграції, `BRAVO.config` такої
інсталяції не зміг би завантажитися без доступного шляху конвертації
— змерджений, випущений проміжний стан, що перестає працювати для
наявних розгортань. Тому робота з міграції/сумісності повинна бути
доступна *до* остаточного переходу, а не після нього.

**Доступність міграції не є завершенням міграції:** випуск PR B
робить шлях міграції *доступним*; він не доводить, що будь-яка
конкретна розгорнута інсталяція насправді його запустила. Прямий
апгрейд до релізу, що містить PR C чи пізніший, усе ще може
натрапити на сервер, чий основний файл конфігурації — виконуваний
legacy `BRAVO.config`, незалежно від того, як довго існує PR B. Тому
завантажувач повинен продовжувати приймати й коректно завантажувати
legacy-формат сам по собі, через явне визначення формату/схеми, доки
відкрите вікно міграції — до окремо контрольованого остаточного
переходу (PR E), що видаляє підтримку legacy, а не просто тому, що
вище за течією існує інструмент конвертації. PR B також нічого не
*активує*: він генерує лише проміжні, неактивні кандидати v2 (див.
«Міграція: конвертація проти активації» вище) — інсталяція не
вважається мігрованою просто тому, що для неї згенеровано кандидата;
вона мігрована лише після успіху контрольованої активації PR D.

**PR A — Безпечний декларативний парсер AST/даних + валідатор схеми**

- безпечний non-executing парсер;
- вилучення AST/даних;
- fail-closed контракт синтаксису;
- визначення схеми Config v2, придатне для повторного використання;
- повторно використовуваний валідатор схеми (той самий, що й у
  PR B/PR C — див. «Канонічний конвеєр валідації v2» вище), відхилення
  невідомих ключів, перевірка типів;
- юніт-тести парсера й валідатора схеми, включно з доказом
  non-invocation вище;
- ще без переходу продакшн-завантажувача — наявна поведінка
  `BRAVO.config` / `BRAVO.local.config` цим PR не змінюється.

**PR B — Підготовка міграції / сумісності (лише неактивне
стейджування)**

- точка входу міграції (`BRAVO_CONFIG_MIGRATE.ps1` або канонічний
  еквівалент репозиторію);
- шлях конвертації виконуваний legacy `BRAVO.config` → DATA-only v2,
  що записує лише в неактивне місце стейджування — ніколи в активну
  назву файлу `BRAVO.config`;
- шлях конвертації `BRAVO.local.config` → `BRAVO.config.local`, що
  записує лише в неактивне місце стейджування — ніколи в активну
  назву файлу `BRAVO.config.local`;
- **сторона джерела (legacy) — окремий, явно відділений від парсера
  PR A конвеєр**, оскільки реальний виконуваний legacy `BRAVO.config`
  містить `param()`, `$global:`-присвоєння й виконувану setup-логіку,
  тоді як парсер PR A приймає ЛИШЕ літеральні декларативні v2 DATA:

  ```text
  legacy BRAVO.config
      → явно вибраний шлях legacy-імпорту/екстракції
      → нормалізована legacy-модель (семантична/effective)
      → детерміноване перетворення/серіалізація
      → неактивний стейджований v2-кандидат
  ```

  Шлях legacy-імпорту/екстракції може використовувати підтримувану
  сьогоднішню legacy-семантику завантаження (виконуваний
  `BRAVO.config` / restricted-language `BRAVO.local.config`),
  необхідну для інтерпретації реальної виконуваної legacy-конфігурації
  під час явної міграції. RAW LEGACY-ТЕКСТ НІКОЛИ не подається
  напряму в парсер PR A — це не валідний вхід для нього;

- **сторона кандидата (v2) — той самий канонічний конвеєр валідації
  v2, що й продакшн-завантажувач:**

  ```text
  текст стейджованого v2-кандидата
      → парсинг PowerShell (PR A)
      → строгий syntax allowlist (PR A)
      → non-executing DATA-екстракція (PR A)
      → валідація configSchemaVersion
      → відхилення невідомих ключів
      → перевірка типів
      → мердж
      → похідні обчислення (derivation)
      → security-інваріанти
      → перевірка еквівалентності effective-значень
  ```

  Той самий валідатор схеми PR A, що використовує продакшн-завантаження
  v2, валідує стейджований v2-кандидат — LEGACY SOURCE VALIDATION ≠
  V2 CANDIDATE VALIDATION;

- dry-run, валідація проміжного кандидата стороною кандидата вище
  (з використанням парсера PR A і того самого валідатора схеми
  PR A — див. «Канонічний конвеєр валідації v2»), відкидання/
  перегенерація;
- тести еквівалентності legacy-проти-v2 на контрольних фікстурах:
  реальний/репрезентативний legacy-ввід спочатку проходить сторону
  джерела (legacy-імпорт/екстракція → серіалізація як v2) і лише ПОТІМ
  парситься/валідується стороною кандидата (парсер PR A); еквівалентність
  порівнюється між legacy-моделлю й effective-результатом стейджованого
  v2-кандидата. Проміжний кандидат ніколи не активується й не переводить
  *продакшн*-завантажувач на себе — продакшн-завантажувач у цьому PR
  продовжує використовувати сьогоднішній шлях виконуваний-`BRAVO.config`/
  restricted-language-`BRAVO.local.config`, незмінений і неторканий;
- **жорсткий інваріант: PR B не має можливості активації/просування.**
  Він не може замінити, перезаписати чи перейменувати проміжний вивід
  в активні назви файлів `BRAVO.config` / `BRAVO.config.local`, і не
  надає жодної команди, здатної зробити проміжну пару живою. Див.
  «Міграція: конвертація проти активації» вище;
- оскільки PR B ніколи не торкається активного набору конфігурації,
  продакшн-резервне копіювання/відкат не потрібні лише для створення
  чи відкидання проміжного кандидата — ця транзакція належить
  активації міграції (PR D, див. «Активація міграції та відкат»
  вище);
- результат: наприкінці цього PR кожна інсталяція, яка пізніше буде
  переведена, вже має підтримуваний, протестований спосіб *створити
  й валідувати* кандидата міграції v2 — повністю неактивного — до
  того, як PR C введе шлях завантаження v2, і задовго до того, як
  контрольована активація PR D чи остаточний перехід PR E повністю
  видалить підтримку legacy.

**PR C — Введення завантажувача v2 (двоформатний, не перехід лише
на v2)**

- продакшн-завантажувач отримує non-executing декларативний шлях
  завантаження v2 (через парсер PR A і той самий валідатор схеми
  PR A — жодної другої, дубльованої реалізації схеми) *на додаток
  до*, а не замість наявного шляху завантаження legacy — цей PR
  вводить підтримку v2, не видаляючи підтримку legacy;
- явне, детерміноване визначення формату/схеми обирає парсер v2 для
  файлу у форматі v2 та наявний шлях legacy для немігрованої
  інсталяції — завантажувач не припускає, що кожна інсталяція
  мігрувала просто тому, що PR B випустив інструмент міграції;
- DATA-only `BRAVO.config` (формат v2) та канонічний
  `BRAVO.config.local` стають валідними, розпізнаваними вхідними
  даними;
- `configSchemaVersion = 2`;
- пріоритет `DEFAULT < BRAVO.config < BRAVO.config.local` для
  інсталяцій, що вже на v2;
- валідація схеми (невідомі ключі/типи fail closed) для вводу v2, з
  використанням того самого валідатора схеми, що й у PR A/PR B — не
  другої реалізації;
- повторно доводить заміну масивів, явний `@()` та значення за
  замовчуванням `ExcludedDrives` на новому шляху завантаження;
- **правило fail-closed:** файл, що декларує себе v2
  (`configSchemaVersion = 2`), але не проходить валідацію v2, повинен
  бути відхилений прямо — він ніколи не повинен мовчки відкочуватися
  до виконуваного legacy-завантажувача. Вибір формату явний і
  детермінований; невдача парсингу v2 ніколи не трактується як
  «спробувати legacy натомість»;
- виконуваний legacy `BRAVO.config` / restricted-language
  `BRAVO.local.config` залишаються підтримуваними через legacy-шлях
  завантажувача протягом вікна міграції — PR C не робить v2 «єдиним
  прийнятим шляхом завантажувача»; це окремий, пізніший контроль
  (див. PR E);
- **PR C володіє базовим контрактом збереження при оновленні
  (updater preservation) для кожного персистентного шару
  конфігурації, який PR C робить активним чи продовжує підтримувати
  протягом вікна двоформатності** (див. «Збереження при оновленні»
  вище) — щонайменше: `BRAVO.config`, `BRAVO.config.local`, а також
  legacy `BRAVO.local.config`, доки legacy-завантаження лишається
  підтримуваним. Обов'язковий інваріант: **перший реліз, що активно
  споживає персистентний v2-файл конфігурації, повинен уже вміти
  зберігати цей файл під час звичайного in-place оновлення.** Не
  повинно існувати підтримуваного проміжного релізу, де v2-конфіг
  вже операційний, але звичайне оновлення могло б його
  перезаписати/видалити. Це — базовий контракт збереження, окремий
  від контракту явної міграції (див. нижче); PR D пізніше
  повторно валідує це покриття в ширшому контексті активації/
  відновлення/відкату, а не вводить збереження вперше;
- **звичайне оновлення на місці відрізняється від явної міграції
  конфігурації.** Звичайне оновлення НЕ ПОВИННО: мовчки
  перезаписувати/видаляти персистентну конфігурацію, що належить
  оператору; неявно конвертувати формати; неявно перейменовувати
  legacy-локальне перевизначення у v2-локальне; переінтерпретовувати
  конфігурацію лише тому, що з'явився новіший рантайм. Явна
  трансформація конфігурації можлива лише через задокументовані
  контракти міграції PR B / активації PR D. Отже: ЗБЕРЕЖЕННЯ ≠
  МІГРАЦІЯ. Для зовнішнього EXPLICIT шляху конфігурації звичайне
  оновлення toolkit-у НЕ ПОВИННО мовчки замінювати, переміщувати чи
  перенацілювати обраний оператором файл — вимога полягає в
  збереженні шляху/посилання й неруйнуванні стану оператора, а не в
  тому, що updater володіє довільними зовнішніми файлами;
- **регресійне покриття PR C для звичайного in-place оновлення**
  (мінімум): v2 `BRAVO.config` переживає звичайне оновлення без
  мовчазної заміни/видалення; v2 `BRAVO.config.local` переживає
  звичайне оновлення без мовчазної заміни/видалення; обидва v2-шари
  одночасно переживають оновлення зі збереженням пріоритету `DEFAULT
  < BRAVO.config < BRAVO.config.local`; legacy `BRAVO.local.config`,
  наявний протягом вікна двоформатності, не знищується мовчки
  звичайним оновленням PR C; явний зовнішній `-ConfigPath`
  залишається авторитетним точним шляхом оператора після оновлення;
  AUTO лишається AUTO — updater не синтезує EXPLICIT-намір; звичайне
  оновлення не виконує неявну міграцію лише щоб задовольнити вимогу
  збереження.

**PR D — Контроль активації/усиновлення зі збереженням шляху +
довговічне відновлення після аварії + повторна валідація збереження
при оновленні в контексті активації + підготовка документації/DoD**

- логіка активації міграції, що реалізує атомарну транзакцію
  просування/перевірки/відкату (див. «Активація міграції та відкат»
  вище), включно з перевіркою шляху активації, довговічним
  write-ahead журналом, rollback-first відновленням після
  аварії/перезавантаження, незалежним від пам'яті процесу, явним
  контрактом блокування читач/writer із закриттям вікна TOCTOU
  (Fix A), а також авторизованою власником верифікацією активації
  (Fix B) — це перший PR, авторизований переміщувати проміжного
  кандидата v2 в активний набір конфігурації;
- активація зберігає ефективний активний основний шлях (AUTO чи
  EXPLICIT `-ConfigPath`, див. «Ефективний активний основний шлях»
  вище), а не припускає `<ConfigRoot>\BRAVO.config`, тож персистентні
  споживачі (заплановані завдання, лаунчери) залишаються валідними
  без перенацілення;
- повторна валідація збереження при оновленні (базовий контракт уже
  володіється й покритий регресійно з PR C — див. «Збереження при
  оновленні» вище й новий пункт PR C вище) у ширшому контексті
  активації/відновлення/відкату — включно з поведінкою збереження під
  час і після транзакції активації, а не лише під час звичайного
  оновлення поза активацією; PR D розширює покриття, але НЕ є першим
  релізом, у якому `BRAVO.config`/`BRAVO.config.local`/legacy
  `BRAVO.local.config` захищені;
- операторська документація оновлена, щоб описувати v2 як доступний
  (ще не як єдиний підтримуваний шлях);
- завершена фінальна регресійна матриця, включно з доказом
  non-invocation, випадком fail-closed-no-fallback-on-invalid-v2 та
  матрицею активного режиму набору конфігурації, включно з виміром
  наміру AUTO проти EXPLICIT (Fix D — див. «Активний режим набору
  конфігурації» вище та регресійний перелік вище);
- задокументований, тестований механізм підтвердження усиновлення
  міграції, авторитетно похідний із фази журналу `Committed` (Fix C
  — див. «Активація міграції та відкат» вище) — наприклад, комбінація:
  підтвердженого стану конвертації, preflight-перевірки updater'а, що
  безпечно мігрує перед активацією нового рантайму, безпечної
  автоматичної міграції з використанням non-executing парсера
  міграції, або явного маркера розгортання/міграції з відкатом;
- real-server acceptance заплановано окремо згідно з політикою
  валідації репозиторію;
- `ROADMAP.md` P3.1 залишається IN PROGRESS після цього PR —
  двоформатна підтримка завершена й механізм відстеження усиновлення
  існує, але виконуваний legacy-завантажувач ще не видалено.

**PR E — Остаточне видалення legacy-завантажувача / перехід
продакшну лише на v2**

- продакшн-рантайм повністю перестає приймати шлях завантаження
  виконуваний legacy `BRAVO.config` / restricted-language
  `BRAVO.local.config`;
- може бути злитий лише після того, як PR D доведе активацію зі
  збереженням шляху, довговічне відновлення після аварії, збереження
  явного `-ConfigPath` та підтвердження усиновлення міграції, усе
  задоволено й регресійно протестовано — самого лише наявного на
  диску інструменту міграції (PR B) чи двоформатного завантажувача
  (PR C) недостатньо для обґрунтування;
- після цього PR продакшн-рантайм ніколи не повинен виконувати
  `BRAVO.config` чи `BRAVO.config.local` як код PowerShell, і жодного
  legacy-шляху завантаження не залишається;
- `ROADMAP.md` P3.1 переходить у DONE лише після цього PR;
- **гейт злиття (реліз/merge-гейт) вище — необхідна, але
  недостатня умова для активації v2-only рантайму на конкретній
  інсталяції.** Готовність PR D/PR E на рівні репозиторію доводить
  лише, що механізм активації/усиновлення *існує й протестований*;
  вона не доводить, що *ця конкретна інсталяція* вже застосувала
  його. Окремий, обов'язковий per-installation deployment-гейт
  визначений нижче й повинен бути задоволений перед тим, як
  updater/deployment-шлях замінить чи активує v2-only рантайм на
  цьому хості.

**Гейт реліз/merge проти гейту активації на інсталяції.** Ці два
гейти незалежні й обидва обов'язкові:

1. **RELEASE / MERGE GATE** (репозиторний рівень, вище) — PR E не
   може бути злитий, доки механізм активації/усиновлення PR D не
   реалізований, не є crash-recoverable, не зберігає шлях, не
   доведений сумісним із двоформатним переходом і не покритий
   регресійно. Цей гейт лишається незмінним і не послаблюється.
2. **PER-INSTALLATION DEPLOYMENT GATE** (рівень конкретного хоста,
   новий) — незалежно від готовності релізу PR E, v2-only рантайм НЕ
   ПОВИНЕН встановлюватися чи активуватися на конкретній інсталяції
   лише тому, що сам PR E готовий до релізу. Сервер може прямо
   оновитися до релізу, що містить PR E, усе ще маючи виконувану
   legacy-конфігурацію (`BRAVO.config` / `BRAVO.local.config`);
   щойно PR E видаляє шлях legacy-завантаження, така інсталяція може
   опинитися без робочого шляху завантаження конфігурації
   («застрягла» — stranded).

**Прямий перехід legacy-інсталяції на реліз, що містить PR E.**
Updater/deployment-шлях повинен явно покривати цей сценарій — він не
повинен «застрягати» інсталяцію:

- перед незворотною заміною legacy-здатного (dual-format) рантайму
  updater/deployment-шлях виконує per-installation preflight цього
  гейту активації;
- якщо ефективна конфігурація цієї інсталяції ще не усиновлена (v2
  не є `Committed`), updater обирає одну з двох підтримуваних
  безпечних дій, поки legacy-здатний рантайм і інструментарій PR D
  усе ще доступні:
  - (A) виконати підтримувану транзакцію
    міграції+активації й продовжити лише після довговічного
    `Committed`;
  - (B) заблокувати v2-only оновлення до заміни наявного рантайму й
    вимагати явної міграції/активації спершу;
- заборонено: мовчазне продовження без адаптації, видалення
  старого рантайму до перевірки усиновлення, чи дозвіл v2-only
  рантайму виконувати legacy-конфігурацію.

**Три незалежні авторитети усиновлення (adoption authorities).**
Per-installation deployment-гейт складається зі спільного fail-closed
preflight (перевірки нижче: відсутність незавершеної транзакції,
відсутність активної legacy-конфігурації, відсутність змішаного/
неоднозначного/недійсного стану) ТА рівно одного валідного
авторитету усиновлення:

- **A. Migrated-v2** (інсталяція, що мала legacy-конфігурацію й
  пройшла міграцію) — авторитет: `journal == Committed` (розбивка
  нижче);
- **B. Native-v2** (інсталяція, що ніколи не мала legacy-конфігурації
  для міграції) — авторитет: довірений провенанс/докази усиновлення
  native-v2 (див. «Native-v2 інсталяція» нижче);
- **C. Default-only / migration-not-required** (вузька категорія без
  жодних конфігураційних файлів) — авторитет: **довірений довговічний
  default-only-провенанс** (durable-клас `DEFAULT-ONLY-ADOPTED`, див.
  «Джерела провенансу default-only» нижче) **ТА** **успішно пройдений**
  no-config preflight на цьому провенансі (див. «Виняток: journal-free
  default-only AUTO-інсталяція» нижче). Ні провенанс без поточного
  preflight, ні сама лише поточна відсутність файлів без довговічного
  провенансу НЕ утворюють Authority C окремо одне без одного — обидва
  обов'язкові одночасно (див. «Fix 3987521226» нижче). Провалений,
  невизначений чи невідомий результат preflight НІКОЛИ не авторизує
  v2-only рантайм через цей авторитет, так само як і сама лише поточна
  відсутність файлів без довговічного провенансу.

Це не три незалежні політики безпеки — це один гейт з трьома
взаємовиключними шляхами доведення легітимності. Інсталяція, що не
може довести жоден з трьох авторитетів, класифікується як AMBIGUOUS і
fail closed (див. «Неоднозначний config-bearing стан» нижче).

**Довговічна класифікація усиновлення — взаємовиключність і
детерміновані переходи (Fix 3987521208).** Три авторитети усиновлення
не обчислюються незалежно й без пам'яті на кожному знімку — кожна
інсталяція повинна мати рівно одну персистовану (durable)
класифікацію усиновлення з множини `{MIGRATED-v2,
NATIVE-v2-CONFIG-BEARING, DEFAULT-ONLY-ADOPTED, UNCLASSIFIED}` (точні
назви полів — деталь реалізації). Ця durable-класифікація, а не лише
поточний знімок файлової системи, визначає, який авторитет взагалі
оцінюється:

```text
migration-required/legacy lineage присутній (журнал існує чи
історично існував, чи доведена legacy-історія)
    → оцінюється ВИКЛЮЧНО Authority A (recovery-first, якщо
      journal != Committed)

інакше, якщо durable-клас == NATIVE-v2-CONFIG-BEARING
    → оцінюється ВИКЛЮЧНО Authority B

інакше, якщо durable-клас == DEFAULT-ONLY-ADOPTED
    → оцінюється ВИКЛЮЧНО Authority C

інакше (durable-клас == UNCLASSIFIED і жоден шлях вище не
застосовується)
    → AMBIGUOUS / FAIL CLOSED
```

Це гарантує взаємовиключність: жодна інсталяція не може одночасно
задовольняти два авторитети, оскільки вибір авторитету робиться за
durable-класом, а не незалежним повторним обчисленням усіх трьох умов
на кожному знімку.

**Обов'язковий детермінований перехід C → B.** Коли інсталяція з
durable-класом `DEFAULT-ONLY-ADOPTED` створює свій перший підтримуваний
v2-конфіг через довірений підтримуваний workflow (див. «Сценарій:
default-only, потім config-bearing native-v2» нижче), той самий
workflow, що створює конфігураційний файл, ПОВИНЕН атомарно/довговічно
оновити durable-клас на `NATIVE-v2-CONFIG-BEARING` до чи одночасно з
тим, як файл стає активним для preflight. Заборонено:

- залишати durable-клас `DEFAULT-ONLY-ADOPTED`, поки конфігураційний
  файл вже активний (вікно, де і C, і B можуть одночасно видатися
  істинними);
- виводити перехід C→B лише з поточної наявності файлу без
  довговічного оновлення durable-класу.

**B → C не є симетричним і не автоматичним.** Видалення всіх активних
v2-файлів з інсталяції durable-класу `NATIVE-v2-CONFIG-BEARING` НЕ
повертає durable-клас до `DEFAULT-ONLY-ADOPTED` мовчки лише через
відсутність файлів — файли можуть зникнути тимчасово (див. «Fix
3987521226» нижче) без втрати native-v2-походження. Якщо перехід B→C
взагалі підтримується, він вимагає того самого явного,
operator-підтвердженого reconciliation-workflow, що й початкове
встановлення Authority C-провенансу (див. «Джерела провенансу
default-only» нижче), і того самого довговічного оновлення
durable-класу.

**A є термінальним і незворотним для durable-класу.** Інсталяція з
durable-класом `MIGRATED-v2` (чи з доведеною legacy-історією, навіть
якщо журнал ще не `Committed`) лишається класифікованою під Authority
A назавжди — видалення її активних v2-конфігураційних файлів НЕ
перекласифіковує її як B чи C. Відсутність файлів на мігрованій
інсталяції оцінюється під Authority A (чи це дозволений «усі три файли
відсутні» v2-стан при `Committed`, чи розбіжність стану, що потребує
відновлення) — ніколи мовчазний перехід на інший авторитет.

**Авторитет A — Migrated-v2: авторитетний сигнал усиновлення для
per-installation-гейту** (узгоджено з Fix C, «Активація міграції та
відкат» вище) — застосовується до **config-bearing / migration-
required інсталяції**, для якої доведено, що вона дійсно мала
legacy-конфігурацію, яка вимагала транзакції міграції/активації (див.
винятки авторитетів B і C нижче):

- `journal != Committed` ⇒ інсталяція НЕ усиновлена; v2-only
  розгортання БЛОКУЄТЬСЯ;
- `journal == Committed` ⇒ інсталяція усиновлена; v2-only
  розгортання ДОЗВОЛЕНЕ, за умови відсутності незавершеної
  транзакції активації/відновлення й класифікації поточної активної
  конфігурації як дозволеного v2-стану;
- самого похідного маркера усиновлення недостатньо: похідний
  маркер — це відновлювані метадані (repairable metadata), а не
  авторитетне джерело істини. Відсутність похідного маркера при
  `journal == Committed` НЕ є доказом провалу усиновлення (узгоджено
  з «`Committed` — точка неповернення» вище);
- навпаки, наявність похідного маркера при `journal != Committed`
  НІКОЛИ не авторизує v2-only розгортання;
- для наміру EXPLICIT збережений `-ConfigPath` повинен усе ще
  ідентифікувати саме той усиновлений ефективний набір v2 —
  preflight перевіряє, що ефективний explicit-шлях відповідає
  усиновленому набору, а не лише те, що якийсь журнал десь
  `Committed`.

**Виняток: journal-free default-only AUTO-інсталяція (міграція не
вимагається).** Таблиця активного режиму набору конфігурації вище вже
підтримує рядок A (AUTO, усі три файли відсутні ⇒ SUPPORTED, лише
built-in). Безумовне застосування правила «`journal != Committed` ⇒
заблоковано» до цього рядка назавжди блокувало б чисту/default-only
інсталяцію, оскільки їй немає що мігрувати, і вона ніколи природно не
породить журнал активації. Це НЕ послаблення гейту для
config-bearing інсталяцій вище — це окрема, вузько визначена
категорія:

- **A. Config-bearing / migration-required інсталяція** — зберігає
  незмінний авторитетний контракт `journal == Committed` вище;
- **B. Journal-free default-only AUTO-інсталяція** — v2-only рантайм
  МОЖЕ розгортатися без журналу міграції ЛИШЕ КОЛИ deployment-
  preflight доводить ОДНОЧАСНО все з переліку:
  - **довірений довговічний default-only-провенанс встановлений**
    (durable-клас `DEFAULT-ONLY-ADOPTED`, див. «Джерела провенансу
    default-only» нижче) — сама по собі поточна відсутність трьох
    файлів БЕЗ цього довговічного провенансу НЕ задовольняє цю умову
    (див. «Fix 3987521226» нижче);
  - намір = AUTO (не EXPLICIT);
  - журнал міграції ВІДСУТНІЙ (не «присутній, але не `Committed`» —
    це інший, fail-closed випадок, див. нижче);
  - немає незавершеної транзакції активації/відновлення;
  - `BRAVO.config` відсутній;
  - `BRAVO.config.local` відсутній;
  - `BRAVO.local.config` відсутній;
  - немає активної legacy-конфігурації;
  - немає змішаного/неоднозначного стану конфігурації;
  - немає недійсного шару конфігурації.

  Цей стан НЕ є «усиновленою міграцією» — це **«міграція не
  вимагається»** (migration not required), оскільки ефективна
  конфігурація складається виключно з вбудованих значень за
  замовчуванням. Використовуй термінологію
  **DEFAULT-ONLY / NO-CONFIG ELIGIBILITY**, а не штучно синтезований
  стан `Committed`.

  Цей виняток НЕ узагальнюється на випадок «журнал існує, але !=
  `Committed`» — наявний незафіксований журнал означає стан
  активації/відновлення й лишається fail-closed/recovery-first
  (рядок вище: «журнал != `Committed` ⇒ заблоковано» для
  config-bearing інсталяції застосовується тут без винятку). Цей
  виняток так само НЕ дозволяє обійти fail-closed для `EXPLICIT` з
  відсутнім основним шляхом — «`EXPLICIT` + відсутній основний файл»
  лишається FAIL CLOSED незалежно від стану журналу (узгоджено з
  рядками H–J вище).

  **Fix 3987521226 — поточна відсутність файлів є доказом стану, а не
  доказом провенансу.** Умова «`BRAVO.config` відсутній +
  `BRAVO.config.local` відсутній + `BRAVO.local.config` відсутній» у
  переліку вище — це ОБОВ'ЯЗКОВА поточна умова стану, яку durable-
  провенанс-Authority C усе одно повинен задовольняти при кожному
  preflight; вона НІКОЛИ не є САМА ПО СОБІ доказом того, що міграція
  ніколи не вимагалася. Тимчасова відсутність може виникнути з причин,
  що не мають нічого спільного з «конфігурація ніколи не існувала»:
  перейменування оператором, тимчасово недоступний том/шлях, часткове
  некероване відновлення, зовнішнє відновлення, що ще не завершене,
  ручне переміщення legacy-конфігурації чи інше тимчасове зникнення.
  Тому для будь-якої НАЯВНОЇ інсталяції (на відміну від щойно створеної
  v2-обізнаним інсталятором) відсутність журналу міграції РАЗОМ з
  відсутністю файлів БЕЗ довговічного довіреного default-only-
  провенансу НЕ авторизує PR E — результат AMBIGUOUS/BLOCKED, доки
  підтримуваний workflow усиновлення/узгодження не встановить
  довговічний провенанс (див. нижче). Не фабрикувати `Committed`-
  журнал міграції для цього стану — «файли відсутні + журнал відсутній
  + AUTO» без провенансу НЕ є еквівалентом `Committed`.

  **Джерела провенансу default-only** (концептуально, точні назви
  полів і місце зберігання — деталь реалізації, за аналогією з
  «Джерела провенансу native-v2» нижче):

  1. свіжа v2-обізнана інсталяція/setup, що явно фіксує довговічне
     походження DEFAULT-ONLY / NO-LEGACY одночасно зі створенням
     інсталяції;
  2. довірені метадані інсталятора/updater'а, що засвідчують
     створення/усиновлення цієї інсталяції без legacy-конфігурації
     (**PLANNED/PROPOSED**, як і аналогічне джерело для native-v2 —
     сьогодні не існує й не стверджується як наявний механізм);
  3. явна operator-підтверджена reconciliation/adoption-транзакція для
     вже наявної інсталяції — той самий клас підтримуваного
     operator-керованого workflow, що й для неоднозначного
     config-bearing стану нижче, з додатковою явною відміткою
     оператора, що жодна legacy-конфігурація НЕ очікується повернутися
     для цього хоста.

  **Негативний випадок: тимчасова відсутність файлів на існуючій
  інсталяції без довговічного провенансу.** Обов'язковий випадок:
  раніше config-bearing (чи невідомого походження) інсталяція,
  оператор тимчасово переміщує/перейменовує всі три конфігураційні
  файли, журнал міграції відсутній, довговічний default-only-провенанс
  не встановлено → Authority C НЕ задовольняється попри те, що
  поточний знімок показує «файли відсутні». Очікуваний результат:
  AMBIGUOUS/BLOCKED, а не «default-only виведений із поточної
  відсутності файлів». Це дзеркальне доповнення до «Негативний
  випадок: ручна заміна legacy на v2-подібний файл» нижче й так само
  не підлягає послабленню.

  **Прямий перехід fresh/default-only AUTO-інсталяції на реліз з PR
  E:** ДОЗВОЛЕНО, але лише після успішного проходження no-config
  preflight вище. **Прямий перехід legacy/config-bearing інсталяції
  на реліз з PR E:** лишається BLOCKED або безпечно мігрованим
  спершу, як уже визначено вище — цей виняток його не торкається.

  **Синхронізація no-config preflight — недостатня сама по собі.**
  Знімок стану no-config, узятий під звичайним контрактом
  синхронізації читач/writer (спільне/read-side блокування, що
  звільняється одразу після отримання одного узгодженого знімку —
  див. «Синхронізація читання та активації» вище), доводить лише, що
  стан був узгодженим У МОМЕНТ ЗНІМКУ. Він НЕ доводить, що стан
  лишається таким самим до фактичної заміни рантайму. Це саме по
  собі недостатньо для авторизації переходу PR E — див. «Атомарність
  фінального переходу PR E» нижче, яка визначає обов'язковий гейт,
  через який ОДНАКОВО повинні проходити всі три авторитети
  усиновлення (A, B, C) безпосередньо перед незворотною заміною
  рантайму.

**Атомарність фінального переходу PR E (закриття гонки
розгортання).** Успішний знімок eligibility (для будь-якого з трьох
авторитетів — Migrated-v2, Native-v2 чи Default-only) сам по собі НЕ
Є достатньою авторизацією заміни рантайму. Між моментом знімку й
фактичною заміною рантайму можлива гонка: AUTO/no-config хост може
здобути чи відновити legacy-конфігурацію ПІСЛЯ того, як цей знімок
захоплено, але ДО того, як updater активує рантайм PR E — preflight
уже пройдений, а хост усе одно може опинитися застряглим на v2-only
завантажувачі. Звичайний контракт читача вище звільняє спільне
блокування одразу після захоплення знімку й не продовжує володіння
через заміну рантайму, і не вимагає участі writer'ів конфігурації в
тому самому контракті синхронізації — цього недостатньо для
незворотної операції розгортання.

**Розрізнення: узгодженість знімку читача проти атомарності
cutover'а розгортання.** Це НЕ те саме, і одне не повинно підміняти
інше:

- **звичайний завантажувач:** спільне/read-side блокування →
  узгоджений знімок вхідних даних конфігурації → звільнення. Це
  достатньо для звичайного завантаження, яке не змінює, яка
  інсталяція рантайму є активною;
- **активація/відновлення (PR D):** ексклюзивне writer-блокування
  транзакції (незмінно, див. «Активація міграції та відкат» вище);
- **PR E deployment/runtime cutover:** вимагає СИЛЬНІШОЇ межі, ніж
  звичайний читач, тому що ця операція змінює, ЯКИЙ РАНТАЙМ
  встановлений на хості — незворотна дія, що не належить до
  контракту "прочитати і забути".

**Обов'язковий контракт фінального гейту розгортання PR E.** Перед
тим як PR E замінює legacy-здатний (dual-format) рантайм на v2-only
рантайм на конкретній інсталяції, updater/deployment-шлях повинен:

1. отримати ексклюзивне володіння deployment/configuration-
   транзакцією (той самий канонічний контракт блокування
   репозиторію, що й активація/відновлення, чи явно доведений
   еквівалентний атомарний механізм ревалідації — не новий,
   слабший, паралельний механізм блокування);
2. під тим самим володінням повторно виконати авторитетний
   ФІНАЛЬНИЙ deployment-preflight з поточного стану — не
   покладатися на більш ранній знімок, узятий до отримання цього
   володіння;
3. повторно оцінити всі авторитети усиновлення й усі спільні
   fail-closed умови;
4. виконати заміну рантайму лише тоді і лише якщо поточна
   інсталяція все ще задовольняє РІВНО один валідний авторитет
   усиновлення і кожну спільну fail-closed умову;
5. безперервно утримувати ексклюзивне володіння аж до моменту,
   коли заміна на v2-only рантайм довговічно/стабільно встановлена;
6. звільнити володіння лише після досягнення інсталяцією
   стабільного стану, що відповідає щойно перевіреному рішенню.

Між ФІНАЛЬНИМ рішенням про eligibility/усиновлення і фактичною
заміною рантайму НЕ ПОВИННО існувати вікна
розблокування/повторного блокування — якщо тільки реалізація не
використовує інший явно задокументований атомарний механізм, що
виявляє будь-яку зміну стану й переривається до активації v2-only.

**Вимога участі writer'ів.** Deployment-блокування достатнє лише
тоді, коли КОЖНА операція, здатна змінити релевантний для eligibility
стан, бере участь у тому самому контракті синхронізації. Це
щонайменше: writer'и, що можуть створювати, відновлювати,
перейменовувати, замінювати, активувати, мігрувати, відновлювати
після аварії чи інакше змінювати `BRAVO.config`, `BRAVO.config.local`,
`BRAVO.local.config`; стан журналу міграції/усиновлення; стан
native-v2 усиновлення/провенансу; стан транзакції
активації/відновлення; персистований `-ConfigPath`/намір
AUTO-проти-EXPLICIT. НЕ стверджувати, що ексклюзивне блокування
запобігає гонкам від довільних зовнішніх (некерованих) записів у
файл, якщо реалізація фактично не може це гарантувати. Тому:
керовані/конфігураційні writer'и ПОВИННІ брати участь у канонічному
контракті блокування; для ризику зовнішньої/некерованої мутації
потрібна або фінальна ревалідація ідентичності/хешу/версії
безпосередньо перед незворотною заміною рантайму, або еквівалентний
fail-closed механізм. Будь-яка зміна релевантного стану ПОВИННА
робити рішення гейту недійсним.

**Застосовується однаково до всіх трьох авторитетів.** Це не
розв'язання вузького прикладу лише для Authority C, залишаючи
загальну гонку розгортання деінде:

- **Authority A (Migrated-v2):** фінальне рішення про заміну
  рантайму повинно повторно підтвердити, що журнал усе ще `Committed`
  і що спільний preflight усе ще проходить — під фінальною межею
  синхронізації розгортання, а не з раніше кешованого знімку;
- **Authority B (Native-v2):** фінальне рішення повинно повторно
  підтвердити, що довірений native-v2 провенанс усе ще авторитетний
  і що спільний preflight усе ще проходить;
- **Authority C (Default-only):** фінальне рішення повинно повторно
  довести УСІ умови no-config preflight (намір AUTO; журнал
  ВІДСУТНІЙ; немає незавершеної транзакції активації/відновлення;
  `BRAVO.config` відсутній; `BRAVO.config.local` відсутній;
  `BRAVO.local.config` відсутній; немає активної legacy-конфігурації;
  немає змішаного/неоднозначного стану; немає недійсного шару; немає
  невирішеного наміру EXPLICIT) саме під ексклюзивним володінням
  фінального розгортання — знімок, узятий ДО отримання цього
  володіння, НЕ Є авторитетним фінальним рішенням про cutover.

Якщо релевантний стан змінюється після більш раннього (попереднього)
знімку: цей більш ранній PASS вважається застарілим (stale); фінальна
перевірка ПОВИННА повторно валідувати з нуля під ексклюзивним
володінням.

**Fail-closed поведінка фінальної валідації розгортання.** Якщо
ексклюзивне володіння deployment-транзакцією не може бути отримане:
ABORT/BUSY, заміна рантайму НЕ виконується. Якщо фінальна ревалідація
відрізняється від більш раннього знімку: ABORT, заміна рантайму НЕ
виконується, стан переоцінюється/узгоджується заново. Якщо поточний
авторитет усиновлення стає неоднозначним під час фінальної
ревалідації: FAIL CLOSED, заміна рантайму НЕ виконується (див.
«Неоднозначний config-bearing стан» вище). Якщо потрібне відновлення:
СПОЧАТКУ ВІДНОВЛЕННЯ (recovery-first), а потім повністю новий
фінальний deployment-preflight — ніколи не продовжувати з PASS, що
передував відновленню чи отриманню блокування.

**Регресійні випадки для фінального гейту розгортання PR E
(мінімум):**

- CASE 1 — default-only-стан змінюється до фінального блокування:
  ранній no-config-знімок = PASS; з'являється legacy/config-
  артефакт; фінальний ексклюзивний preflight бачить його ⇒ PR E
  cutover ЗАБЛОКОВАНО;
- CASE 2 — спроба керованого writer'а під час cutover'а: deployment
  утримує ексклюзивне володіння; конфігураційний writer намагається
  виконати мутацію ⇒ writer не може вклинитися до стабільної заміни
  рантайму;
- CASE 3 — стан змінюється між попередньою й фінальною валідацією:
  попередній adoption-гейт = PASS; стан змінюється; фінальна
  валідація != попередній стан ⇒ старий PASS відкидається ⇒ cutover
  ПЕРЕРВАНО;
- CASE 4 — стає необхідним відновлення: рання eligibility = PASS;
  виявляється незавершена транзакція ⇒ recovery-first ⇒ жодної
  заміни рантайму до успіху свіжого фінального preflight-у.

**Fix 3987521218 — довговічна crash-recoverable транзакція
розгортання рантайму, окрема від журналу міграції конфігурації.**
Ексклюзивне володіння deployment-транзакцією, визначене вище, запобігає
КОНКУРЕНТНІЙ мутації, але воно волатильне — аварія процесу чи хоста між
захопленням володіння й довговічним завершенням заміни рантайму
знищує це блокування, не залишаючи доказу того, наскільки далеко
просунулася заміна. Тому cutover рантайму PR E повинен мати ОКРЕМИЙ
довговічний контракт транзакції розгортання:

```text
ЖУРНАЛ МІГРАЦІЇ КОНФІГУРАЦІЇ (Fix C, «Активація міграції та відкат»)
!=
ЖУРНАЛ РОЗГОРТАННЯ РАНТАЙМУ (цей розділ)
```

Журнал міграції конфігурації авторитетний лише для Authority A
(усиновлення конфігурації). Журнал розгортання рантайму авторитетний
лише для факту й фази заміни виконуваного рантайму. Один НЕ замінює й
НЕ переносить власника іншого; не перевикористовувати й не
перевантажувати журнал міграції конфігурації записами про заміну
рантайму.

**Обов'язкові передумови перед ПЕРШОЮ мутацією активного рантайму.** До
того, як updater внесе першу зміну в чинний виконуваний рантайм,
повинні бути задоволені всі умови:

- ексклюзивне deployment/configuration-володіння (розділ вище);
- успішний фінальний adoption/preflight (розділ вище);
- перевірено ПОВНИЙ backup попереднього рантайму АБО наявна незмінна/
  версіонована попередня ціль рантайму, придатна для атомарного
  відкату;
- довговічно створений журнал розгортання у фазі ДО мутації (див.
  фази нижче).

Журнал розгортання ідентифікує щонайменше:

- ідентичність транзакції;
- ідентичність/версію/шлях старого рантайму;
- ідентичність/версію/шлях цільового рантайму;
- перевірене джерело відкату (rollback source);
- фазу/стан;
- чи могла вже початися мутація активного рантайму.

Точні назви полів — деталь реалізації.

**Фази транзакції розгортання.** Детермінований довговічний state
machine, концептуально еквівалентний:

```text
Prepared → Switching → Verified → Committed
```

(точні назви фаз можуть відрізнятися, семантика — ні):

1. отримати ексклюзивне володіння;
2. виконати фінальний adoption/preflight під цим володінням;
3. перевірити повноту джерела відкату / попереднього рантайму;
4. довговічно створити журнал розгортання у фазі `Prepared` — на
   цьому кроці мутація активного рантайму доказово ще НЕ розпочата;
5. довговічно перевести журнал у фазу `Switching` / зафіксувати
   `mutationMayHaveBegun = true` — цей durable-запис ПОВИНЕН
   завершитися успішно ДО будь-якої фактичної мутації активного
   рантайму; якщо durable-перехід у `Switching` не вдається: ABORT,
   жодна мутація рантайму НЕ виконується;
6. лише ПІСЛЯ успішного durable-переходу в `Switching` виконати першу
   фактичну мутацію/перемикання рантайму;
7. перевірити, що новий v2-only рантайм повний і внутрішньо
   узгоджений;
8. довговічно позначити розгортання `Verified`;
9. довговічно позначити розгортання `Committed`;
10. лише потім виконати опціональне прибирання;
11. звільнити володіння лише після досягнення стабільного
    `Committed`-стану.

**Обов'язковий інваріант durable-межі мутації (закриття crash-вікна).**
Перехід `Prepared` → `Switching` ПОВИНЕН бути durably записаний ДО
першої фактичної мутації активного рантайму — не після неї і не
«одночасно за задумом» без гарантії, що durable-запис передує запису
файлу. `Prepared` доводить, що мутація рантайму ще не розпочата, ЛИШЕ
доки durable-запис `Switching`/`mutationMayHaveBegun = true` ще не
відбувся. Щойно `Switching` durably зафіксовано, транзакція назавжди
трактується як «мутація МОГЛА початися» — навіть якщо аварія сталася
одразу після запису маркера `Switching` і до першого фактичного запису
файлу рантайму. Recovery НІКОЛИ не виводить «мутації не було» лише
тому, що фактичний перший запис міг ще не відбутися.

Атомарний дизайн version-pointer/перемикання каталогу може замінити
поетапну заміну кількох файлів, якщо він надає еквівалентні гарантії
(атомарність перемикання, перевірюваність цілі, можливість
детермінованого відкату).

**Crash recovery для розгортання рантайму.** Будь-який startup/
deployment-preflight, що бачить незавершену транзакцію розгортання,
ПОВИНЕН виконати RUNTIME DEPLOYMENT RECOVERY ПЕРШИМ, до звичайного
продовження розгортання:

- **`Prepared`, без durable `Switching`** (журнал у фазі `Prepared`, І
  `Switching`/`mutationMayHaveBegun = true` НІКОЛИ не було durably
  зафіксовано для цієї транзакції — обидві умови обов'язкові разом):
  попередній активний рантайм лишається недоторканим; зайве відновлення
  НЕ виконується; транзакція безпечно очищається/повторюється.
- **`Switching` durably зафіксовано (незалежно від `Verified`), але не
  `Committed`**: щойно `Switching`/`mutationMayHaveBegun = true` durably
  записано, recovery ЗАВЖДИ трактує мутацію як «МОГЛА початися» —
  навіть якщо аварія сталася одразу після запису маркера `Switching`,
  до першого фактичного запису файлу рантайму. Recovery НІКОЛИ не
  робить висновок «мутації не було» лише тому, що фактичний перший
  запис міг не відбутися; семантика `Prepared` тут НЕ застосовується.
  Використовується ВИКЛЮЧНО перевірене джерело відкату, що належить
  цій конкретній транзакції розгортання: (a) доводиться, що старий
  рантайм усе ще byte-/identity-узгоджений, і він лишається
  недоторканим; АБО (b) відновлюється точне перевірене джерело відкату;
  АБО (c) детерміновано завершується доведений атомарний перехід
  вказівника версії. Не вгадувати інший backup. Якщо джерело/докази
  відкату відсутні чи недійсні: FAIL CLOSED, докази зберігаються,
  жодного вгадування, жоден частково замінений рантайм НЕ подається як
  здоровий.
- **Невідома/пошкоджена фаза чи невизначена межа мутації**: FAIL
  CLOSED — recovery ніколи не вгадує фазу чи стан мутації, коли журнал
  розгортання нечитабельний, суперечливий чи не відповідає жодній
  визначеній фазі.
- **Після `Committed`**: збій прибирання/метаданих НЕ повинен мовчки
  відновлювати попередній рантайм. Такий збій — це відновлювана
  проблема метаданих/прибирання розгортання, а не привід для
  автоматичного відкату версії; явний окремо авторизований відкат
  версії — єдиний шлях розгортання назад. Межа коміту розгортання
  рантайму лишається окремою від межі `Committed` журналу міграції
  конфігурації.

**Інваріант доступності рантайму.** Після аварії/перезапуску
інсталяція завжди розв'язується РІВНО в один узгоджений рантайм: або
перевірений попередній двоформатний рантайм, або повністю перевірений
`Committed` v2-only рантайм. Ніколи — часткова суміш файлів старого й
нового рантайму. Самого лише deployment-блокування недостатньо як
доказу цього інваріанту — необхідна довговічна транзакція розгортання
з описаних вище фаз.

**Регресійні випадки для crash-recoverable cutover'а рантайму
(мінімум):**

- CASE R1 — аварія у фазі `Prepared`, ДО durable-запису `Switching` ⇒
  мутація доказово не розпочата; попередній рантайм незмінний; зайвого
  відновлення не відбувається;
- CASE R2 — `Switching`/`mutationMayHaveBegun = true` durably
  зафіксовано, аварія ДО першого фактичного запису файлу рантайму ⇒
  recovery трактує мутацію як МОГЛА початися; застосовується
  `Switching`-контракт відновлення (звірка ідентичності старого
  рантайму, точний rollback чи детермінований атомарний перехід) —
  НІКОЛИ семантика `Prepared`;
- CASE R3 — аварія ПІСЛЯ першої фактичної мутації рантайму ⇒ той самий
  `Switching`-контракт відновлення: точний rollback або детерміноване
  завершення атомарного переходу;
- CASE R4 — аварія після перевірки нового рантайму (`Verified`), до
  `Committed` ⇒ детерміноване відновлення за `Switching`-контрактом;
  частковий рантайм ніколи не подається як здоровий;
- CASE R5 — аварія/збій після `Committed`, до прибирання ⇒ зафіксований
  новий рантайм лишається авторитетним; прибирання відновлюється
  пізніше; автоматичного відкату немає;
- CASE R6 — джерело відкату відсутнє/пошкоджене, поки `Switching`
  durably зафіксовано (мутація могла початися) ⇒ FAIL CLOSED, жодного
  вгаданого відновлення;
- CASE R7 — керований writer конфігурації намагається виконати мутацію
  під час cutover'а рантайму ⇒ не може вклинитися до стабільного
  `Committed`-стану розгортання (той самий контракт участі writer'ів,
  що й для конфігураційного deployment-гейту вище);
- CASE R8 — журнал розгортання нечитабельний/суперечливий чи фаза не
  відповідає жодній визначеній фазі ⇒ FAIL CLOSED, жодного вгадування
  фази чи межі мутації.

**Зв'язок із P3.2a / роботою updater'а.** Crash-safe заміна рантайму НЕ
стверджується як уже наявна — вона все ще проектується/реалізується.
**PR E v2-only cutover НЕ ПОВИНЕН ставати придатним до розгортання
(deployable), доки не реалізовано вимаганий тут crash-recoverable
механізм розгортання рантайму.** Якщо власником цього механізму є P3.2a
(`ROADMAP.md`), PR E явно залежить від його обов'язкової спроможності —
цей документ не редагує й не дублює володіння `ROADMAP.md`, лише
фіксує залежність.

**Авторитет B — Native-v2 інсталяція (провенанс без журналу
міграції).** Хост може легітимно потрапити в Configuration v2 без
жодної legacy-конфігурації, яку взагалі треба було б мігрувати:
свіжа інсталяція, створена напряму v2-обізнаним інсталятором/setup;
інсталяція, ініціалізована валідною DATA-only v2-конфігурацією; уже
native/default-only v2-інсталяція, що пізніше створює свій перший
`BRAVO.config` чи `BRAVO.config.local` через підтримуваний v2-шлях.
Для такого хоста НІКОЛИ природно не виникне журнал міграції, що
досягає `Committed` — і вимагати його означало б фабрикувати фіктивну
транзакцію міграції для інсталяції, якій нема що мігрувати.

- **МІГРАЦІЙНО-ПОХІДНИЙ доказ усиновлення (Authority A) і NATIVE-v2
  провенанс інсталяції (Authority B) — це НЕ те саме.** Один не може
  маскуватися під інший. Похідний маркер усиновлення з міграційного
  журналу (Fix C) залишається недостовірним авторитетом, коли журнал
  `!= Committed` (незмінний інваріант вище) — це не скасовується
  наявністю окремого native-v2 провенансу; вони перевіряються
  незалежно.
- **Валідний вміст v2-файлу САМ ПО СОБІ — НЕ доказ native-v2
  походження.** Це критичне правило безпеки: якщо просто «журнал
  відсутній + `BRAVO.config` синтаксично валідний v2» автоматично
  означало б native-v2, legacy-інсталяція могла б обійти міграцію,
  вручну замінивши свій виконуваний legacy-файл чимось, що виглядає
  як v2. Native-v2-статус повинен походити з довіреного провенансу
  інсталяції/setup/updater'а чи іншого явно задокументованого
  авторитетного шляху усиновлення — ніколи лише з вмісту файлу.
- **Джерела провенансу native-v2** (концептуально, точні назви полів
  і місце зберігання — деталь реалізації): (1) факт створення
  ефективної конфігурації безпосередньо v2-обізнаним
  інсталятором/setup-шляхом; (2) довірені метадані
  інсталятора/updater'а, що засвідчують відсутність legacy-джерела
  для цього хоста, якщо такі метадані існують у майбутній реалізації
  (**PLANNED/PROPOSED** — сьогодні не існує й не стверджується як
  наявний механізм); (3) підтверджений результат явного
  operator-керованого workflow узгодження (reconciliation, нижче).
- **Неоднозначний config-bearing стан.** Для комбінації: валідні
  v2-файли присутні + журнал відсутній + native-v2 провенанс
  відсутній/недоведений — гейт класифікує інсталяцію як AMBIGUOUS,
  якщо жоден інший задокументований авторитетний шлях узгодження не
  доводить усиновлення. Результат: FAIL CLOSED. Native origin
  НІКОЛИ не вгадується мовчки з самого факту валідного v2-вмісту.
  Можливий шлях відновлення: явний operator-керований workflow
  узгодження/усиновлення → валідація поточного набору v2 → доведення
  відсутності (чи вирішення наявності) legacy-стану → виконання
  необхідних семантичних/міграційних перевірок → встановлення
  авторитетного провенансу усиновлення.
- **Доказ legacy домінує над native-shortcut.** Native-v2-авторитет
  НІКОЛИ не обходить: активний legacy `BRAVO.config`; активний
  legacy-локальний шар `BRAVO.local.config`; змішаний legacy/v2 стан;
  недійсний v2-шар; невідомий формат; незавершений/не-`Committed`
  журнал міграції; невирішений намір EXPLICIT-шляху. Зокрема:
  `journal existує І journal != Committed` продовжує означати
  «потрібне відновлення/preflight, native/default-only shortcut
  недоступний» — це зберігає інваріанти транзакції з розділу
  «Активація міграції та відкат» вище без винятку.
- **Сценарій: свіжа v2-обізнана інсталяція.** Підтримуваний сценарій:
  legacy-конфігурація ніколи не існувала → створена/обрана валідна
  v2-конфігурація → native-v2 провенанс встановлений підтримуваним
  шляхом setup/install → журнал міграції відсутній → per-installation-
  гейт PR E PASS. Без фіктивної міграції, без вимоги журналу
  `Committed`.
- **Сценарій: default-only, потім config-bearing native-v2.**
  Підтримуваний сценарій: AUTO default-only хост легітимно проходить
  no-config-гейт (Authority C, довговічний провенанс + успішний
  preflight) → входить у native-v2 lifecycle → підтримуваний workflow,
  що створює перший `BRAVO.config` і/або `BRAVO.config.local`,
  ОБОВ'ЯЗКОВО й атомарно/довговічно оновлює durable-клас усиновлення
  цієї інсталяції з `DEFAULT-ONLY-ADOPTED` на
  `NATIVE-v2-CONFIG-BEARING` (див. «Обов'язковий детермінований перехід
  C → B» вище) — Authority C ПЕРЕСТАЄ бути авторитетним джерелом для
  цієї інсталяції з цього моменту, а не продовжує існувати паралельно
  з Authority B → оператор може безпечно додавати конфігурацію →
  журнал міграції все ще не вимагається. Нові файли, звісно, усе одно
  повинні пройти non-executing парсер, схему, відхилення невідомих
  ключів, валідацію типів, мердж, деривацію та інваріанти безпеки.
- **Негативний випадок: ручна заміна legacy на v2-подібний файл.**
  Обов'язковий випадок: історично legacy/config-bearing хост →
  оператор вручну замінює legacy `BRAVO.config` файлом у формі v2 →
  журнал міграції відсутній → авторитетного native-v2 провенансу
  немає. Очікуваний результат: BLOCKED/AMBIGUOUS — а не «native-v2
  виведений із вмісту файлу». Це розрізнення обов'язкове й не
  підлягає послабленню.
- **Намір EXPLICIT для native-v2.** Зберігається інваріант: `EXPLICIT`
  + відсутній основний шлях = FAIL CLOSED. Для native-v2 EXPLICIT-
  інсталяцій точна explicit-ціль повинна бути саме валідованою/
  усиновленою v2-основною ціллю. Native-v2-провенанс не авторизує
  перенацілення чи мовчазний відкат до AUTO.

**Розбіжний стан (`Committed`, але активні файли не v2/змішані).**
Якщо журнал `Committed`, але фактичний активний набір конфігурації на
диску класифікується як legacy, змішаний чи недійсний — це є
розбіжністю стану (state divergence), а не доказом безпеки. З самого
факту `Committed` НЕ можна робити висновок, що v2-only розгортання
безпечне: preflight повинен fail closed і вимагати відновлення
(recovery) чи підтримуваний шлях узгодження (reconciliation) з боку
оператора перед активацією v2-only рантайму.

**Per-installation preflight також перевіряє:**

- відсутність незавершеної транзакції активації/відновлення;
- відсутність активного виконуваного legacy-основного файлу;
- відсутність активного legacy-локального шару `BRAVO.local.config`;
- відсутність змішаного стану legacy/v2;
- відсутність неоднозначного/невідомого формату;
- відсутність недійсного v2-шару (основного чи локального — див.
  «Недійсний найвищий пріоритетний шар» вище).

**Регресійні випадки для per-installation deployment-гейту (мінімум):**

- `Committed` + валідний усиновлений набір v2 ⇒ v2-only розгортання
  дозволене;
- журнал не `Committed` ⇒ v2-only розгортання заблоковане;
- відсутній журнал / legacy-інсталяція ⇒ прямий перехід на реліз з
  PR E заблокований або безпечно мігрований до заміни рантайму;
- лише похідний маркер, журнал не `Committed` ⇒ заблоковано;
- `Committed` + активний legacy/змішаний/недійсний набір ⇒
  заблоковано (розбіжність стану, потрібне відновлення/preflight);
- незавершений журнал ⇒ вимагається відновлення/preflight, активація
  v2-only заблокована;
- EXPLICIT `-ConfigPath` коректно усиновлений ⇒ прийнятний лише
  тоді, коли ефективна explicit-ціль є саме усиновленим набором v2;
- AUTO + журнал відсутній + немає конфігураційних файлів + доведений
  довговічний default-only-провенанс ⇒ v2-only розгортання ДОЗВОЛЕНЕ
  як default-only/migration-not-required (виняток вище, Authority C);
- AUTO + журнал відсутній + немає конфігураційних файлів на ІСНУЮЧІЙ
  інсталяції БЕЗ доведеного довговічного default-only-провенансу ⇒
  AMBIGUOUS/BLOCKED (Fix 3987521226 — сама лише поточна відсутність
  файлів не авторизує Authority C);
- AUTO + незавершений/незафіксований журнал + немає конфігураційних
  файлів ⇒ заблоковано / потрібне відновлення (виняток НЕ
  застосовується — журнал уже існує);
- AUTO + журнал відсутній + присутня legacy-конфігурація ⇒
  заблоковано / потрібна міграція (config-bearing контракт, а не
  default-only виняток);
- AUTO + журнал відсутній + присутня валідна v2-конфігурація ⇒ НЕ
  класифікується мовчки ані як default-only, ані як автоматично
  native-v2 — оцінюється за Authority B (native-v2 провенанс
  доведений ⇒ дозволено) чи, за відсутності доведеного провенансу,
  AMBIGUOUS ⇒ FAIL CLOSED (див. «Авторитет B — Native-v2 інсталяція»
  вище);
- EXPLICIT + відсутній шлях + журнал відсутній ⇒ FAIL CLOSED (виняток
  для default-only не застосовується до EXPLICIT);
- migrated-хост + журнал `Committed` + валідний v2 ⇒ дозволено
  (Authority A);
- migrated/незавершений журнал + валідний v2 ⇒ заблоковано/
  recovery-first;
- свіжа інсталяція + довірений native-v2 провенанс + валідний
  v2-конфіг + журнал відсутній ⇒ дозволено (Authority B);
- свіжа native-v2 default-only інсталяція + журнал відсутній +
  доведений довговічний default-only-провенанс ⇒ дозволено (Authority
  C, до появи конфігураційних файлів);
- default-only native-v2 хост пізніше додає валідний v2-конфіг ⇒
  дозволено без журналу міграції; durable-клас атомарно оновлюється
  `DEFAULT-ONLY-ADOPTED` → `NATIVE-v2-CONFIG-BEARING` (Authority B, а
  не паралельне співіснування з Authority C — див. «Обов'язковий
  детермінований перехід C → B» вище);
- видалення всіх v2-файлів з інсталяції durable-класу
  `NATIVE-v2-CONFIG-BEARING` ⇒ durable-клас лишається
  `NATIVE-v2-CONFIG-BEARING` (НЕ мовчазний відкат до Authority C) —
  перехід B→C, якщо підтримується, вимагає явного operator-керованого
  reconciliation-workflow;
- мігрована інсталяція (durable-клас `MIGRATED-v2`) з подальшим
  видаленням активних v2-файлів ⇒ лишається класифікованою під
  Authority A; оцінюється як розбіжність стану/потребує відновлення,
  НЕ мовчазний перехід на B чи C;
- валідний v2-конфіг + журнал відсутній + недоведений native-v2
  провенанс ⇒ AMBIGUOUS/заблоковано;
- історичний legacy-хост, вручну замінений v2-подібним файлом, без
  `Committed`-міграції ⇒ заблоковано;
- native-v2 провенанс + активний legacy-шар ⇒ заблоковано (legacy
  домінує над native-shortcut);
- native-v2 провенанс + незавершений журнал ⇒ заблоковано/
  recovery-first;
- migration-похідний маркер + не-`Committed` журнал ⇒ заблоковано
  (незмінно, незалежно від native-v2 авторитету);
- EXPLICIT з відсутнім основним шляхом + native-v2 докази ⇒ усе одно
  FAIL CLOSED;
- native-v2 валідний конфіг провалює схему/безпекову валідацію ⇒
  заблоковано.

Не поєднуйте введення завантажувача v2 (PR C) з основою парсера
(PR A) в одній зміні — це ускладнило б перегляд найризикованішої
частини (коректність/non-invocation парсера) окремо від частини з
нижчим ризиком (схема/підключення пріоритету). Не поєднуйте PR C з
роботою з міграції/сумісності (PR B) також — їх поєднання відтворило
б той самий небезпечний проміжний стан, якого цей порядок покликаний
уникнути, зробивши неможливим постачання шляху міграції як незалежно
перевірюваного, вже доступного кроку до того, як від нього залежатиме
підтримка v2. Не поєднуйте роботу з контролю міграції/усиновлення
(PR D) з остаточним видаленням legacy-завантажувача (PR E) також — їх
злиття усунуло б окремо тестований контроль усиновлення, для якого
існує цей поділ, і зробило б «інструмент міграції існує» невідрізненим
від «ця інсталяція мігрувала», що є саме тим змішуванням, якого цей
документ повинен уникати.

Кожен PR повинен незалежно проходити найвужчу відповідну підмножину
self-test плюс повний прогін `BRAVO_SELF_TEST.ps1` перед злиттям і
повинен бути зеленим за повним набором обов'язкових перевірок перед
злиттям у `developer`/`master` — `RELEASE_POLICY.md` (розділ захисту
гілок) перелічує поточні обов'язкові перевірки: "Parser / BOM / JSON",
"PSScriptAnalyzer", "BRAVO_SELF_TEST.ps1", "Secret scanning
(gitleaks)", "GitGuardian Security Checks". (`.claude/rules/*` —
закомічені файли політики репозиторію, які контриб'ютор, що робить
checkout цього коміту, може прочитати, і на них можна посилатися як
на доповнення. Але вони НЕ замінюють цей документ як джерело істини
для security/архітектурних вимог Config v2: цей документ повинен
лишатися явним і самодостатнім щодо власного production-контракту,
а `.claude/rules/*` — допоміжна, а не єдина точка визначення цього
контракту.)

## Фінальний цільовий контракт (для довідки — ще не повністю реалізовано)

```text
Вбудовані значення за замовчуванням є повними (частина пакета, а не файл).
BRAVO.config — опціональне перевизначення для сайту/розгортання.
BRAVO.config.local — опціональне машинно-локальне перевизначення.
DEFAULT < BRAVO.config < BRAVO.config.local
Файли конфігурації є ДАНИМИ, а не КОДОМ.
Продакшн-рантайм ніколи не викликає файли конфігурації Configuration v2 як код.
configSchemaVersion = 2
Limits.ExcludedDrives default = @()
Масиви замінюють, а не мерджуються.
Явний @() є валідним перевизначенням.
Невідомі ключі не проходять валідацію.
Некоректні типи не проходять валідацію.
Похідні обчислення рантайму відбуваються після сирого мерджу.
Секрети залишаються поза конфігурацією.
```

З цього контракту сьогодні в продакшні вже виконується таке:

- вбудовані значення за замовчуванням повні;
- `BRAVO.config` опціональний;
- `DEFAULT < BRAVO.config < BRAVO.local.config` (поточна назва файлу;
  файл v2 — це `BRAVO.config.local`, ще не випущений);
- похідні обчислення рантайму виконуються після сирого мерджу;
- секрети залишаються поза конфігурацією (Windows Credential
  Manager);
- значення за замовчуванням `Limits.ExcludedDrives` дорівнює `@()` —
  уже правда сьогодні, не прогалина, специфічна лише для v2;
- масиви замінюють, а не мерджуються — уже правда сьогодні в
  мердж-рушії Foundation, не прогалина, специфічна лише для v2;
- явний `@()` є валідним перевизначенням — уже правда сьогодні, не
  прогалина, специфічна лише для v2.

Що залишається лише цільовим (ще не є правдою в продакшні):

- сам `BRAVO.config` є ДАНИМИ, а не КОДОМ (сьогодні це все ще
  виконуваний скрипт);
- рантайм ніколи не *викликає* файли конфігурації як код —
  сьогоднішній читач `BRAVO.local.config` перевіряє-потім-викликає,
  що вужче за «ніколи не викликати»;
- `configSchemaVersion = 2`;
- `BRAVO.config.local` існує як назва файлу, що постачається;
- перевірка невідомих ключів / типів, застосована через схему v2;
- повна регресійна матриця Definition-of-Done для v2, включно з
  доказом non-invocation, прогнана саме проти шляху завантаження v2.
